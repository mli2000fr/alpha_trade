## 1. Contexte du système

- **Projet** : α-Trade — trading long/short ML sur actions US mid-caps.
- **Stack** : Python 3.14 (venv `.venv`), MySQL `alpha_trade` (root/root), Windows/PowerShell.
- **Pipeline ML** :
  1. **Global Ranking** (Phase 1) : CatBoost RMSE/YetiRank (champion automatique vs LightGBM/XGBoost) classe chaque symbole par rendement futur attendu → `global_rank_h ∈ [0,1]` sur 5 horizons H3/H5/H10/H15/H20.
     - Target : forward return vol-scalé (H≥5) → winsorize 1%/99% → rank intra-date → **sector-neutral** (médiane secteur soustraite) → **factor-neutral** (OLS size+value+momentum) → re-rank.
     - ~155-177 features (OHLCV expert, cross-sectional, fondamentales, facteurs CAPM, volume P3-5).
     - Walk-forward 8 splits × 252 j, train max 756 j, demi-vie 360 j, purge dynamique par horizon.
  2. **Modèles directionnels** : per-sector (11 secteurs GICS × 5 horizons, LightGBM+CatBoost, target-mode **regression**) OU per-symbol (LSTM/LightGBM/CatBoost). Le per-sector est `research_only` (F1 WF ≈ 0.33 = hasard).
  3. **Cascade de trading** : pour chaque date → rang global top 10 % (rank > 0.90) ET proba long > seuil → candidat LONG ; bottom 10 % (rank < 0.10) ET proba short > seuil → candidat SHORT. Score = rank × proba.
- **Données** : barres `stock_bars_daily` jusqu'au 2026-07-10 ; scores jusqu'au 2026-06-25 ; univers = `config/ticket_recherche.txt` (400 symboles).
- **Tables clés** : `global_rank_history` (PK symbol,date,batch_id — les rangs de chaque batch coexistent), `model_predictions`, `model_training_batch`, `stock_bars_daily`.

## 2. Coûts et mécanique backtest (alignés Alpaca, fixés le 2026-08-14)

- Commission **1 bps**, slippage **2 bps**, **spread réel** (médiane ~44 bps sur l'univers), marge **7.5 %/an**, levier **2×**.

## 3. Le problème : OOS 2026 catastrophique

### 3.1 Backtests B25 sur 2026-01-02 → 2026-05-31 (coûts canoniques, k=2.5)

| Run | Retour | Sharpe | DD | Trades | Note |
|---|---|---|---|---|---|
| TP prod (min 3×ATR,7%) | **−53.0 %** | −2.61 | 63.3 % | 42 | 100 % shorts, win 38.1 % |
| TP legacy (12 %/2R) | **−41.4 %** | −1.83 | 58.1 % | 33 | 100 % shorts |
| + `--bull-strict-mode no_shorts` | −40.8 % | — | 54.2 % | 34 | 56 shorts bloqués → gain 12 pts seulement |

- **SPY sur la même fenêtre : 683.17 → 756.48 = +10.7 %** (creux intra-fenêtre −16.5 % à 631.97).
- Frais estimés : ~51 bps × 19.2 tours d'equity ≈ **9.8 % d'equity** — les frais n'expliquent que ~19 % de la perte.
- In-sample B25 (2019→2024-06, **chevauchant l'entraînement**) : +274 % (TP prod) / +300.8 % (legacy), ~380 trades, win 47 % — l'écart in-sample/OOS est donc massif.
- OOS 2025 B25 : **positif** (+28 % equal / +33.4 % rank_weighted, adopté 2026-08-13).

### 3.2 Pourquoi 0 trade long en 2026 (mécanique)

- Les modèles sectoriels sont en `target_mode=regression` → sortie = score continu, **side = signe du score**, `proba_long`/`proba_short` = NULL. La cascade fabrique `long_prob = |score|` (P0-5).
- Seuil effectif de la cascade : **`min_prob_regression = 0.10`** (le 0.55 = `min_prob_classification`, utilisé seulement si une proba ternaire non-nulle existe dans le jeu). Le même seuil s'applique aux 2 côtés.
- Croisement rang × proba sur les prédictions 2026 (DB, B25) :
  - Longs : 922 lignes, mais **11 seulement** satisfont `|score|>0.10 ET rank>0.90` (96 jours). Cause : |score| long médiane **0.094** ET 744/894 longs en **mid-rank** (le modèle sectoriel dit « long » là où le rang global les classe au milieu — les 2 modèles se contredisent).
  - Shorts : 213 candidats `|score|>0.10 ET rank<0.10` (102 jours) ≈ les ~202 entrées sélectionnées → 42 exécutées.
- Le rang global est un classement **relatif** (cross-sectionnel, neutralisé secteur+facteurs) : le bottom 10 % existe toujours, même en marché haussier. Il ne prédit pas la baisse absolue.

### 3.3 Preuve de l'inversion du rang (B25, 2026)

Retours forward H10 **bruts** par bande de rang (jan→mai 2026) :

| Bande | Moyenne | Médiane | n |
|---|---|---|---|
| Bottom 10 % (shorts) | **+0.59 %** | +0.10 % | 3 237 |
| Milieu | −0.26 % | −0.50 % | 26 643 |
| Top 10 % (longs) | **−0.30 %** | −0.44 % | 3 320 |

→ En 2026, le top décile baisse et le bottom décile monte : **le classement est inversé**.

### 3.4 Régimes — état des lieux

- Backtest : `regime_filter` (bear = SPY < SMA200×0.98 → bloque TOUTES les entrées ; défaut OFF) ; `bull_strict` (no_shorts : SPY > SMA200 ET ret60 > +3 % → bloque les shorts ; défaut OFF). **Les runs OOS de base n'avaient AUCUN régime actif.**
- Production : `market_regimes.enabled: true` — règles de STRESS (VIX > 30, VXN > 23, spike 10Y, sentiment < seuil) → `capital_preservation` ; `close_longs_on_defensive_regime: true` (force-close des LONGS en défensif). **Aucune règle ne bloque les shorts en marché haussier.**
- En in-sample (2019-2024), les shorts GAGNAIENT en bull strict (+202k) → l'overlay bull_strict a été REJETÉ in-sample (P2-3 : 140.1 % vs control 205.9 %). En OOS 2026 c'est l'inverse → le filtre n'est pas adoptable par défaut sans choisir quelle période on croit.

## 4. Protocole de test T1/T2/T3 (décidé avec l'utilisateur le 2026-08-14)

**Question** : le modèle global est-il inadapté à 2026, ou le classement cross-sectionnel est-il structurellement fragile ?

- **T1** : B44 (config B41, train 2016→2024-12-31) → OOS **2025**
- **T2** : abandonné (B43 supprimé ; était : même batch → OOS 2026)
- **T3** : B41 (train 2016→2025-12-31) → OOS **2026** ✅ FAIT

**Méthode** : pas de backtest complet — analyse « event study » sur les rangs :
1. Générer `global_rank_history` du batch sur la fenêtre OOS (backfill `predict_global_rank_history`, ~24 s/jour, parallélisé par plages contiguës).
2. Script `scripts/analyze_rank_horizons.py <batch_id> <start> <end>` :
   - charge rangs + barres (symboles des rangs uniquement) + SPY ;
   - calcule les **forward returns bruts** H5/H10/H15/H20 (`LEAD(close,h)/close−1`, non neutralisés — c'est le P&L réel) ;
   - bandes : TOP = rank_h > 0.90, BOTTOM = rank_h < 0.10 ;
   - régime : bull = SPY > SMA200, bear = SPY < SMA200×0.98, neutre sinon ; bull_strict = bull ET ret60 > +3 % ;
   - **4 variantes par horizon** : (1) sans gate ; (2) gate A = bottom sans les jours bull_strict ; (3) gate B = top sans bear + bottom sans bull ; (4) segmentation bull/bear/neutre sans blocage ;
   - benchmark SPY (retour forward moyen par horizon) ;
   - rapport écrit dans `logs/analyze_ranks_report.txt`.

## 7. Questions ouvertes pour l'analyse externe

1. **Pourquoi le classement cross-sectionnel s'inverse-t-il en 2026 ?** Hypothèses candidates :
   a. Régime de marché 2026 spécifique (bull fort + basse dispersion → la neutralisation secteur/facteurs détruit l'alpha absolu ?) ;
   b. Les features/relations apprises 2016-2025 ne généralisent pas (dérive de régime, features « mortes ») ;
   c. La **neutralisation secteur + facteurs** de la target : le modèle apprend du RELATIF, mais le trading est en ABSOLU → divergence structurelle en marché directionnel ;
   d. Univers 400 mid-caps : concentration de facteurs communs en 2026 ;
   e. Le décile spread d'entraînement est faible (0.02-0.03) → le moindre bruit de régime inverse le classement ;
   f. Petite taille d'échantillon 2026 (94 jours) — inversion = bruit ?
2. **Les gates A/B sont-ils structurellement inutiles** quand le rang est inversé (ils coupent un signal déjà faux) ? Un gate ne peut-il que réduire l'exposition, jamais créer de l'alpha ?
3. **Le spread négatif est maximal en H15** — hasard ou information (l'horizon le plus utilisé par best_horizon) ?
4. **T1 (B44 → OOS 2025) tranchera** : si 2025 est sain, le problème est 2026-spécifique ; si 2025 est aussi inversé, le classement cross-sectionnel ne généralise pas du tout.
5. Le **pivot per-symbol** (décision utilisateur) est-il la bonne réponse, ou faut-il d'abord corriger la conversion relatif→absolu (neutralisation) ?

### 24.8 Incident de fidélité découvert au 1er run (10:35) — RÉSOLU

- **Symptôme** : le 1er run production-parity (2026 baseline) a produit **0 trade** — la phase 2 rejette tous les candidats avec `ML_FIRST_REJECT missing_ml_prediction` (bridge `backtesting/risk_bridge.py::_build_ml_selection_inputs_from_day`).
- **Cause racine** : la sélection phase 2 est **ML-first** et exige des probas ternaires (`proba_long/proba_flat/proba_short` non-nulles + `run_id`). Or les prédictions B25 per-sector sont en `target_mode=regression` → probas NULL (cf. §3.2). Seules les lignes `{batch}_globalrank_synth` (générées par le pipeline live via `modelFactory/synthesize_global_rank_predictions.py`) portent les probas ternaires — et elles n'existaient en DB que jusqu'au 2025-12-31 puis à partir du 2026-07-10 (le live n'a jamais tourné sur 2022 ni 2026 Q1-Q2).
- **Conséquence pour le test** : la pile de prod ne peut pas rejouer l'historique sans ces lignes. Rien à voir avec le filtre momentum : baseline ET loose étaient également à 0 trade → l'A/B serait vide.
- **Fix** : backfill `_globalrank_synth` pour B25 depuis `global_rank_history` (déjà couverte 2022 + 2026-01→05-31) via le synthétiseur officiel (`python -m modelFactory.synthesize_global_rank_predictions --batch-id model-factory-20260811223551-ef2cd0 --best-h 10`, 449 102 lignes, ON DUPLICATE KEY UPDATE → idempotent). La proba dérivée est monotone dans le rang → l'ordre de sélection reste exactement celui du rang global (même input que la cascade naked).
- **Vérifié** : 92 360 lignes backfillées sur 2022, 40 000 sur 2026 Q1-Q2 ; au relancement, prédictions chargées = **42 925 lignes** (vs 2 925) et la cascade bascule en `mode=classification min_prob=0.55` (les probas ternaires sont présentes) — les candidats/jour passent de 2-9 à 64-76.
- ⚠️ **Nuance à documenter** : la cascade naked (recherche) tournait en mode regression (min_prob 0.10) ; la chaîne prod tourne en mode classification (min_prob 0.55). L'A/B production-parity (baseline vs loose) reste causal (seule diff = le flag) mais la comparaison naked vs prod inclut cette différence de mode de sélection — c'est une composante légitime de la « pile de prod ».
- **À noter pour le futur** : tout test production-parity sur une fenêtre historique exige ce backfill préalable (gap structurel de la parité backtest↔live).

### 24.9 Deux bugs de parité corrigés dans la chaîne phase 2 (10:50)

1. **`backtesting/risk_bridge.py::_build_predictions` — proba 0.0 détruite + écrasement par doublon** : le code utilisait `row.get("proba_flat") and pd.notna(...)` → `proba_flat=0.0` (valeur NORMALE du synth : flat) devenait None → `ML_FIRST_REJECT`. - ⚠️ Note : en live avec kelly actif, le sizing Kelly dépend de `model_directional_oos_metrics` (rempli par le pipeline live). En backtest historique, ces stats n'existent pas → kelly off (comportement du preset 2-5k) est la bonne baseline ; un backfill des métriques directionnelles OOS serait nécessaire pour tester la variante kelly.
- ⚠️ Effet secondaire observé : le warmup OHLCV dépend de `correlation_lookback_days` du preset → nouveau cache key → premier run en cold load (scan complet ~15-20 min), les 3 runs suivants prennent le cache.

3. **`backtesting/execution_bridge.py` + `execution_replay.py` — SIDE-FLIP des shorts** : `portfolio_entries_to_execution_targets` et `_entry_to_target` écrivaient `side="buy"` EN DUR pour toutes les entrées → les shorts acceptés par la phase 2 (Option C sells) devenaient des LONGS dans la chaîne 3-7 (constaté sur le run 2026 baseline : short_pnl=0, tous les trades buy, TP au-dessus de l'entrée). Fix : mapper `entry.side` (buy/sell) vers `ExecutionTarget.side`.
4. **Gate de couverture ML live sur l'historique** : `ml_coverage_gate` (seuil 95 % depuis le preset) bloque les runs pipeline avec `sys.exit(1)` — la couverture B25 sur 2022 n'est que 77.3 % (236 symboles sans prédiction ML en 2022, rangs/preds historiques incomplets) → les 2 runs 2022 sont morts silencieusement. Fix : `--min-ml-coverage-ratio 0` sur les runs 2022 UNIQUEMENT (même relâchement des deux côtés → A/B causal ; documenté comme écart de parité historique).

5. **Colonne `side` absente des signaux phase 3** (`execution_replay.replay_rows`) → le simulateur défautait `buy` → tous les shorts exécutés en longs. Fix : `"side": intent.side` dans les lignes signals + export trades direction-aware (`report.py` : colonne side + inversion du signe P&L des shorts).

6. **Replay exits long-only** : `exit_lifecycle_replay` (garde stop « sous le prix d'entrée » + trailing `peak_high×(1−pct)` + `resolve_intrabar_exit` sans side) et `protection_watcher_replay` (`_find_trigger_date` sur high uniquement) → shorts jamais stoppés, TP déclenché le jour même. Fix : branche short (stop au-dessus, trailing `trough_low×(1+pct)`, watcher sur low) + passage du `side`.

7. **CRASH cash=inf (root cause du 05-29)** : dans `simulator._try_close_positions`, la branche `protection_replay` calculait le trailing des SHORTS avec la formule long (`previous_peak_high×(1−pct)`, inactif → `-inf`) → `hit_ts` toujours vrai pour un short → exit à −inf → `settled_cash -= (−inf)` = **+inf**. Instrumentation NaN/Inf (`NaN_EQUITY`/`NaN_BUDGET`/`NaN_EXIT`) + garde `available_entry_budget=0` si non-fini. Fix direction-aware (short inactif → `+inf`).
