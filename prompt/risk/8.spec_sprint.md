## 1. Objectif

La passe précédente activait la promotion `stop initial -> trailing dynamique` **pendant** l’exécution du run, sur une fenêtre bornée par la durée de vie de `execute_run`.

Cette approche posait une limite métier claire :

- si le trigger n’était pas atteint avant la fin du run,
- la transition n’était plus surveillée,
- même si la position restait ouverte et que le scénario se validait plus tard.

L’objectif de cette passe était donc de **décorréler la surveillance de transition du run d’exécution**.

Le lifecycle devient désormais :

- `execute_run` pose l’entry, le take-profit et le stop initial natif ;
- puis un **watcher post-run dédié** relit les stops initiaux encore actifs ;
- il surveille le trigger métier après coup ;
- et il effectue la promotion vers le trailing quand le marché la justifie.

---

## 2. Design retenu

## 2.1 Exécution recentrée sur la pose de protection initiale

### `execution_engine/executor.py`

`ProductionExecutor._submit_children(...)` ne déclenche plus la surveillance bloquante du trailing dynamique.

Concrètement :

- le moteur continue de soumettre :
  - le `take_profit`
  - le `initial_stop` broker-side si possible
- il **n’attend plus** un trigger de marché dans la même exécution
- il laisse la suite du lifecycle au watcher dédié

### Effet métier

Le run d’exécution revient à sa responsabilité principale :

- **entrer en position** ;
- **poser la protection immédiate** ;
- **terminer rapidement**.

La promotion dynamique n’est plus contrainte par la durée de vie du process d’exécution.

---

## 2.2 Watcher post-run dédié

### `execution_engine/protection_watcher.py`

Ajout d’un nouveau composant métier :

- `ProtectionTransitionWatcher`

Responsabilités :

1. charger les stops initiaux encore actifs ;
2. recalculer le trigger métier de trailing ;
3. lire le prix de marché courant via le broker ;
4. annuler le stop initial si le trigger est atteint ;
5. soumettre ensuite le `trailing_stop` ;
6. auditer la transition sur le `exec_run_id` source ;
7. publier un résumé métier dédié `execution_protection_watch`.

### Modes d’exécution

Le watcher est lançable :

- via le module Python ;
- via un runner dédié.

Fichiers ajoutés :

- `execution_engine/protection_watcher.py`
- `run_execution_protection_watch.py`

### Exemples d’usage

```powershell
python -m execution_engine.protection_watcher --exec-run-id exec_20260426_001
```

```powershell
python run_execution_protection_watch.py --account default --limit 100
```

Le watcher continue d’écrire les événements sur le `exec_run_id` d’origine, ce qui garde un historique métier continu côté exécution.

## 5. Ce que cette passe couvre réellement

### Côté exécution
- le run ne bloque plus pour surveiller la transition ;
- il pose uniquement les protections immédiates ;
- la fin du run ne coupe plus la possibilité d’activer le trailing.

### Côté watcher
- relit les stops initiaux actifs ;
- évalue le trigger métier avec prix de marché courant ;
- annule le stop initial ;
- soumet le trailing dynamique ;
- audite la transition sur le run source.

### Côté observabilité
- résumé séparé pour la surveillance post-run ;
- page exécution enrichie ;
- métriques de transition plus lisibles.

---

## 6. Limites restantes / prochaines étapes naturelles

1. **ordonnancement automatique du watcher**
   - le watcher est dédié et relançable ;
   - l’étape naturelle suivante est de le brancher sur un scheduler ou un service persistant.

2. **idempotence distribuée plus forte**
   - la logique évite les transitions déjà effectuées en relisant les ordres enfants ;
   - une étape supplémentaire serait d’introduire un claim explicite ou une table de leasing pour exécutions concurrentes.

3. **fallback encore plus robuste après annulation réussie**
   - si l’annulation du stop initial réussit mais que la soumission trailing échoue, l’échec est audité ;
   - une amélioration naturelle serait un mécanisme de réarmement automatique d’une protection de secours broker-side.

4. **service long-lived / watcher continu**
   - aujourd’hui le composant est prévu pour être relancé périodiquement ;
   - une version suivante pourrait tourner en boucle contrôlée avec heartbeat et supervision.

---

## 7. Verdict

Cette passe fait franchir une étape importante au lifecycle de protection :

- la pose de protection immédiate reste dans `execute_run` ;
- la promotion vers trailing dynamique devient **post-run, dédiée et relançable**.

Le système n’est donc plus limité par la fenêtre de vie du run d’exécution pour activer un trailing sur trigger métier.

On passe d’un trailing “opportuniste pendant le run” à une **surveillance métier décorrélée**, mieux alignée avec la réalité d’une position qui continue à vivre après la fin du process de soumission.
