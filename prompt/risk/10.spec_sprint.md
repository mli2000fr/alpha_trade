## 1. Objectif

La passe précédente a rendu le watcher de protection exploitable en mode `service` persistant.

L’étape suivante logique était de le rendre **déployable réellement sur Windows**, sans demander à l’exploitant de reconstruire lui-même :

- le launcher ;
- la commande du scheduler ;
- l’encapsulation NSSM ;
- la lecture de santé dans l’IHM.

L’objectif de cette passe était donc triple :

1. fournir un **packaging Windows prêt à l’emploi** ;
2. rendre l’installation **idempotente** ;
3. exposer une **santé de service lisible** côté IHM.

## 2. Design retenu

## 2.1 Launcher PowerShell commun

### `scripts/windows/protection_watcher_launcher.ps1`

Ajout d’un lanceur PowerShell unique pour centraliser :

- la résolution du workspace ;
- la résolution de l’interpréteur Python ;
- le `Set-Location` ;
- la construction des arguments watcher ;
- la redirection optionnelle des logs stdout/stderr.

### Résolution Python

Le launcher cherche successivement :

- `-PythonExePath` si fourni ;
- `.venv\Scripts\python.exe` ;
- `venv\Scripts\python.exe` ;
- `.python\Scripts\python.exe` ;
- puis `python.exe` ou `py.exe` sur le PATH.

### Effet

Les scripts d’installation Windows n’ont plus besoin de dupliquer la logique de boot du watcher.

Ils s’appuient tous sur une même enveloppe d’exécution.

---

## 2.2 Packaging Task Scheduler

### `scripts/windows/install_protection_watcher_task.ps1`

Ajout d’un installateur idempotent pour Windows Task Scheduler.

### Comportement

Le script :

1. résout le launcher ;
2. crée un dossier de logs si nécessaire ;
3. construit une action `powershell.exe -File protection_watcher_launcher.ps1 ...` ;
4. installe une tâche répétée toutes les `N` minutes ;
5. supprime la tâche existante si elle existe déjà ;
6. réinstalle ensuite la nouvelle définition.

### Paramètres principaux

- `-TaskName`
- `-WorkspacePath`
- `-PythonExePath`
- `-Account`
- `-ExecRunId`
- `-Mode`
- `-FrequencyMinutes`
- `-Limit`
- `-RunAs Interactive|System`
- `-UserId`
- `-LogDirectory`
- `-LogLevel`

### Usage cible

Le mode recommandé avec Task Scheduler reste :

- `--mode once`

avec une relance périodique toutes les quelques minutes.

### Désinstallation

Ajout du script complémentaire :

- `scripts/windows/uninstall_protection_watcher_task.ps1`

## 2.3 Packaging NSSM / service Windows

### `scripts/windows/install_protection_watcher_service_nssm.ps1`

Ajout d’un installateur NSSM pour déployer le watcher en vrai service Windows supervisé.

### Comportement

Le script :

1. exige un `nssm.exe` externe via `-NssmExePath` ;
2. supprime proprement le service existant s’il est déjà présent ;
3. enregistre `powershell.exe` comme process du service ;
4. lui passe le launcher PowerShell en `--mode service` ;
5. configure le répertoire de travail ;
6. configure `AppStdout` / `AppStderr` ;
7. active la rotation de logs NSSM ;
8. met le service en `SERVICE_AUTO_START`.

### Paramètres principaux

- `-NssmExePath`
- `-ServiceName`
- `-DisplayName`
- `-Description`
- `-WorkspacePath`
- `-PythonExePath`
- `-Account`
- `-ExecRunId`
- `-Limit`
- `-ServiceIntervalSeconds`
- `-IdleIntervalSeconds`
- `-HeartbeatIntervalSeconds`
- `-MaxIterations`
- `-StopWhenIdle`
- `-StartAfterInstall`

### Désinstallation

Ajout du script complémentaire :

- `scripts/windows/uninstall_protection_watcher_service_nssm.ps1`

## 2.5 Résumé de santé du service dans `run_business_summaries`

### `execution_engine/protection_watcher.py`

Le `ProtectionWatcherService` persistait jusqu’ici surtout son résumé final via `emit_run_summary(...)`.

Cette passe ajoute une persistance dédiée sous :

- `step_key = execution_protection_watch_service`
- `run_kind = service`

### Stratégie retenue

Le service écrit / met à jour le même `summary_run_id` :

- au démarrage ;
- après les cycles ;
- au heartbeat ;
- à l’arrêt final.

### Champs de santé ajoutés

Le résumé de service contient notamment :

- `status`
- `service_scope`
- `iterations`
- `cycles_with_work`
- `idle_cycles`
- `heartbeat_count`
- `consecutive_failures`
- `max_consecutive_failures`
- `interval_seconds`
- `idle_interval_seconds`
- `heartbeat_interval_seconds`
- `stop_when_idle`
- `max_iterations`
- `watched_items`
- `transitioned_items`
- `last_heartbeat_at`
- `last_cycle_at`
- `last_cycle_had_work`
- `last_cycle_watched_items`
- `last_cycle_transitioned_items`

### Effet

On n’a pas ajouté de nouvelle table.

La santé du service est donc visible dans le même mécanisme de résumés métier persistants que le reste du système.

## 2.6 IHM : bloc de santé service watcher

### `ihm/services/run_summary.py`

Ajout d’un mapping dédié pour :

- `execution_protection_watch_service`

### `ihm/services/queries.py`

Ajout du helper :

- `get_latest_execution_protection_watch_service_summary(...)`

Ce helper :

1. tente d’abord un résumé scoped au `exec_run_id` courant ;
2. sinon fallback sur le dernier résumé `account_id`.

### `ihm/pages/execution.py`

Ajout d’un nouveau bloc :

- `🫀 Santé du service watcher`

Le bloc affiche :

- le résumé persistant du service ;
- le statut du service ;
- le `service_scope` ;
- un indicateur de fraîcheur heartbeat ;
- l’âge du heartbeat ;
- le dernier cycle ;
- le volume du dernier cycle ;
- les transitions du dernier cycle.

### Lecture métier

Cela permet de distinguer clairement :

- la santé du **service qui tourne** ;
- et la performance métier du **watcher sur les protections**.

## 4. Exemples d’exploitation

## 4.1 Installation Task Scheduler

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\windows\install_protection_watcher_task.ps1 -TaskName "AlphaTrade-ProtectionWatcher" -FrequencyMinutes 5 -Account default -Mode once
```

## 4.2 Désinstallation Task Scheduler

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\windows\uninstall_protection_watcher_task.ps1 -TaskName "AlphaTrade-ProtectionWatcher"
```

## 4.3 Installation NSSM / service Windows

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\windows\install_protection_watcher_service_nssm.ps1 -NssmExePath "C:\tools\nssm\win64\nssm.exe" -ServiceName "AlphaTradeProtectionWatcher" -Account default -StartAfterInstall
```

## 4.4 Désinstallation NSSM

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\windows\uninstall_protection_watcher_service_nssm.ps1 -NssmExePath "C:\tools\nssm\win64\nssm.exe" -ServiceName "AlphaTradeProtectionWatcher"
```

## 6. Ce que cette passe couvre réellement

### Côté Windows exploitation
- bootstrap standardisé via un launcher ;
- installation rapide en tâche planifiée ;
- installation rapide en service NSSM ;
- désinstallation propre ;
- redirection de logs prévue.

### Côté application
- persistance explicite de la santé du service ;
- visibilité dans `run_business_summaries` ;
- requête IHM dédiée ;
- bloc de santé visible côté exécution.

### Côté sécurité opérationnelle
- install scripts idempotents ;
- suppression/recréation si resynchronisation nécessaire ;
- scope explicite (`exec_run_id`, `account_id` ou global) ;
- heartbeat et dernier cycle visibles.

## 7. Limites restantes / prochaines étapes naturelles

1. **vrai script d’enregistrement Windows Service natif sans NSSM**
   - ici le choix retenu est NSSM pour sa robustesse et sa simplicité ;
   - une étape suivante pourrait fournir un wrapper service natif .NET ou `pywin32`.

2. **gestion explicite des secrets Windows**
   - les scripts supposent que les variables d’environnement DB / broker sont déjà disponibles pour le contexte d’exécution ;
   - une prochaine étape pourrait intégrer un chargement `.env` sécurisé ou un secret store Windows.

3. **vue IHM dédiée ops / supervision**
   - aujourd’hui la santé du service est affichée sur la page exécution ;
   - une future passe pourrait créer une vue supervision dédiée pour tous les services récurrents.

4. **alerting proactif sur heartbeat stale**
   - l’IHM affiche déjà la fraîcheur ;
   - une extension naturelle serait un statut rouge/orange explicite et une alerte automatique.

## 8. Verdict

Cette passe fait passer le watcher d’un composant technique prêt à tourner à un **composant réellement packagé pour l’exploitation Windows**.

On dispose désormais de :

- scripts Task Scheduler ;
- scripts NSSM / service Windows ;
- launcher commun ;
- README local d’exploitation ;
- résumé de santé persistant ;
- et lecture IHM minimale de supervision.

Le watcher peut donc maintenant être :

- planifié proprement,
- tourné en service Windows supervisé,
- et observé depuis l’IHM sans devoir inspecter uniquement les logs.
