## 1. Objectif

La passe précédente avait déjà apporté :

- le pilotage local du watcher depuis l’IHM ;
- les logs live des watchers lancés depuis l’IHM ;
- un historique dédié des runs watcher IHM ;
- un panneau d’intégration Windows explicite.

Il restait un manque important :

- l’IHM ne voyait pas encore le **vrai statut Windows** ;
- elle ne pouvait pas encore **relire directement les logs du packaging Windows** ;
- et le lien IHM ↔ PowerShell était encore seulement documentaire, pas structuré.

L’objectif de cette passe était donc de livrer une **supervision Windows réelle mais strictement en lecture seule**.

---

## 2. Design retenu

## 2.1 Principe de sécurité

Le design retenu conserve une séparation nette :

- **l’IHM peut superviser** ;
- **l’IHM ne peut toujours pas administrer** le packaging machine.

Concrètement, depuis l’IHM :

- on peut lire le statut réel Windows ;
- on peut importer les logs Windows ;
- on peut utiliser un bridge PowerShell **allowlisté** ;
- mais on ne peut pas :
  - installer la tâche ;
  - installer NSSM ;
  - démarrer / arrêter un service Windows externe ;
  - manipuler DPAPI ;
  - lancer des scripts PowerShell arbitraires.

Le bridge est donc **très encadré**.

## 2.3 Bridge PowerShell côté IHM

### Fichier : `C:\Users\MLI\PycharmProjects\alpha_trade\ihm\services\windows_watcher_bridge.py`

Ajout d’un module Python dédié au bridge IHM ↔ PowerShell.

### Rôle

Ce module ne permet que des appels **allowlistés**.

Allowlist actuelle :

- `status` → `get_protection_watcher_status.ps1`

### Fonctions exposées

- `run_allowed_bridge_script(...)`
- `get_windows_watcher_status(...)`
- `list_windows_watcher_log_sources(...)`
- `read_windows_log_source(...)`

### Garde-fous intégrés

- refus immédiat si le `script_key` n’est pas dans l’allowlist ;
- bridge limité à Windows (`os.name == "nt"`) ;
- timeout sur l’exécution PowerShell ;
- aucun `check=True` destructif ;
- aucun support d’arguments libres pour des scripts non autorisés ;
- aucun start/stop/install/remove exposé.

Autrement dit, le bridge n’est pas un shell générique.
C’est une **sonde contrôlée**.

## 4. Ce que l’IHM ne fait toujours pas

Même après cette passe, l’IHM ne fait toujours **pas** :

- `install_protection_watcher_task.ps1`
- `install_protection_watcher_service_nssm.ps1`
- `uninstall_*`
- `Start-Service`
- `Stop-Service`
- `Register-ScheduledTask`
- `Unregister-ScheduledTask`
- `protection_watcher_secrets.ps1`
- exécution PowerShell arbitraire.

C’est volontaire.

Le bridge est resté borné à :

- **status**
- **log import**

et rien d’autre.

---

## 5. Pourquoi c’est le bon compromis

Ce design apporte enfin la visibilité demandée par l’exploitation :

- savoir si la tâche existe vraiment ;
- savoir si le service Windows tourne vraiment ;
- voir les logs réellement écrits par le packaging Windows ;
- le tout depuis l’IHM.

Mais il évite toujours les risques majeurs :

- casser une installation Windows depuis Streamlit ;
- lancer un script non prévu ;
- mélanger supervision et administration système ;
- dépendre de privilèges élevés non maîtrisés.

On gagne donc :

- **lisibilité opérationnelle** ;
- **sécurité d’exploitation** ;
- **encadrement du pont IHM ↔ PowerShell**.

## 9. Conclusion

`Supervision Ops` couvre maintenant cinq niveaux :

1. **santé métier du watcher** via DB/heartbeat ;
2. **pilotage local IHM** ;
3. **logs live et historique watcher IHM** ;
4. **statut Windows réel read-only** ;
5. **bridge PowerShell très encadré**.

C’est une étape importante, car on commence à raccorder l’IHM au packaging Windows réel, tout en restant du bon côté de la sécurité opérationnelle.

La prochaine marche logique, si on veut poursuivre, serait :

- lecture read-only de l’Event Log Windows lié au watcher ;
- détection plus fine des erreurs Task Scheduler / NSSM ;
- éventuellement plus tard un start/stop assisté **mais uniquement** avec workflow d’autorisation explicite, rôle opérateur, confirmation forte et trail d’audit.
