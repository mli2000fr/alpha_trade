## 1. Objectif de cette étape

L’étape logique suivante après le Sprint 2 était double :

1. **remplacer la simple dérivation en trailing par un vrai stop initial broker-side** quand les champs risque le permettent ;
2. **rendre cette protection visible dans l’IHM exécution**, à la fois au niveau des KPI et au niveau des ordres réellement soumis.

Le but est de passer de :

- champs risque présents dans `portfolio_targets`,
- exploitation partielle par `execution_engine`,

à :

- **ordre `stop` natif broker-side** quand `stop_price_initial` ou `risk_per_share` le permettent ;
- **fallback trailing** seulement quand le stop initial n’est pas exploitable ou qu’il échoue à la soumission ;
- **visibilité IHM** sur la couverture réelle des protections.

---

## 2. Ce qui a été livré

## 2.1 Contrat exécution enrichi pour le stop initial

### `execution_engine/models.py`

Ajouts :

- nouveau rôle `IntentRole.INITIAL_STOP` ;
- ajout de `stop_price` dans `OrderIntent`.

### Effet

Le moteur n’est plus limité à :

- `limit_price` pour les take-profits ;
- `trail_percent` pour les trailing stops.

Il sait maintenant porter explicitement un **prix de stop broker-side** dans l’intent d’ordre.

---

## 2.2 Construction d’un vrai stop initial broker-side

### `execution_engine/order_intents.py`

Ajouts principaux :

- `resolve_initial_stop_price(reference_price, target)`
- `build_initial_stop_intent(...)`

Règles appliquées :

1. si `target.stop_price_initial` est présent et cohérent (`0 < stop < prix de référence`) :
   - on utilise ce prix ;
2. sinon, si `target.risk_per_share` est disponible :
   - on dérive un stop via `reference_price - risk_per_share` ;
3. sinon :
   - aucun stop initial natif n’est construit.

### `intent_to_alpaca_payload(...)`

Le payload Alpaca supporte maintenant :

- `type = "stop"`
- `stop_price = ...`

### Effet métier

Le moteur soumet désormais un **ordre de protection initial explicite** chez le broker, au lieu de convertir systématiquement le risque amont en `trailing_stop`.

---

## 2.3 Orchestration exécution : stop natif d’abord, trailing en fallback

### `execution_engine/executor.py`

La logique `_submit_children(...)` a été modifiée ainsi :

1. soumission du `take_profit` ;
2. tentative de soumission d’un **`initial_stop` broker-side** ;
3. si aucun stop initial n’est constructible :
   - fallback direct sur `trailing_stop` ;
4. si le stop initial est constructible mais **échoue à la soumission broker** :
   - tentative de fallback vers `trailing_stop`.

### Nouveaux compteurs calculés

Au préflight / runtime :

- `targets_with_broker_initial_stop`
- `targets_with_trailing_fallback`
- `child_take_profit_orders_submitted`
- `child_initial_stop_orders_submitted`
- `child_trailing_stop_orders_submitted`
- `child_order_submit_failures`

### Payload événementiel enrichi

L’événement `CHILDREN_SUBMITTED` expose maintenant notamment :

- `initial_stop_price`
- `trailing_stop_percent`
- `protection_mode`
- `child_order_roles`
- `risk_per_share`
- `stop_price_initial`
- `initial_risk_dollars`

### Effet métier

Le comportement devient :

- **stop initial natif si possible** ;
- **trailing seulement en secours**.

C’est plus cohérent avec l’intention de risque décidée amont.

### Effet métier

La page exécution ne montre plus seulement “run / fills / events” :
elle montre aussi **comment le risque amont a été matérialisé en protections broker-side**.

## 6. Prochaines étapes naturelles

1. **vrai chaînage stop initial -> trailing dynamique**
   - aujourd’hui, le trailing reste un fallback ;
   - une étape ultérieure pourrait transformer un stop initial en trailing après déclencheur de profit / temps.

2. **meilleure lecture IHM des protections**
   - ajouter badges/couleurs par type de protection ;
   - distinguer visuellement `stop natif`, `fallback trailing`, `protection failed`.

3. **OCO / lifecycle plus riche**
   - exposer plus clairement le cycle complet : entry fill -> child stop/tp -> cancel sibling.

4. **reporting plus fin sur la fraîcheur des cibles**
   - pousser davantage `stale_price_targets` dans la page exécution et potentiellement les alertes overview.

---

## 7. Verdict

Cette passe fait franchir un cap utile au pipeline d’exécution :

- le risque amont n’est plus seulement transporté ;
- il est **matérialisé en stop initial broker-side explicite** quand c’est possible ;
- et cette matérialisation devient **visible et auditable dans l’IHM exécution**.

Le pipeline `risk_management -> portfolio_targets -> execution_engine -> run_business_summaries -> IHM` gagne ainsi en cohérence opérationnelle et en observabilité.
