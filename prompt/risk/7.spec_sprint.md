## 1. Objectif de cette étape

Après l’introduction du **stop initial broker-side natif**, l’étape logique suivante consistait à faire évoluer la protection en deux temps :

1. **protéger immédiatement** la position avec un stop initial explicite côté broker ;
2. **transformer ensuite cette protection en trailing dynamique** quand un trigger métier est atteint.

L’objectif n’était donc plus seulement :

- `entry -> TP + stop initial`

mais :

- `entry -> TP + stop initial`
- puis, si le marché valide le scénario :
- `stop initial -> trailing dynamique`

sans perdre :

- la traçabilité ;
- la sécurité opérationnelle ;
- l’observabilité IHM.

---

## 2. Design retenu

## 2.1 Trigger métier configurable

Le trigger d’activation du trailing est désormais piloté par la configuration `ExecutionConfig` via :

- `enable_dynamic_trailing_transition`
- `trailing_activation_trigger`
- `trailing_activation_r_multiple`
- `trailing_activation_profit_pct`
- `protection_transition_timeout_seconds`
- `protection_transition_poll_interval_seconds`

### Modes supportés

#### `multiple_r`
Le trailing s’active lorsque le prix courant atteint :

- `fill_price + risk_per_share * trailing_activation_r_multiple`

#### `profit_pct`
Le trailing s’active lorsque le prix courant atteint :

- `fill_price * (1 + trailing_activation_profit_pct)`

### Règle de fallback

Si le mode demandé est `multiple_r` mais que `risk_per_share` n’est pas disponible, le moteur bascule automatiquement sur un calcul en `profit_pct`.

### Effet métier

Le passage en trailing devient **pilotable explicitement** au lieu d’être implicite ou purement technique.

---

## 2.2 Résolution du prix de trigger

### `execution_engine/order_intents.py`

Ajout principal :

- `resolve_trailing_activation_price(fill_price, config, target)`

Cette fonction détermine :

- le **prix de déclenchement** de la transition ;
- le **mode réellement utilisé** (`multiple_r`, `profit_pct`, `profit_pct_fallback`).

### Effet

Le moteur distingue maintenant clairement :

- le prix du stop initial ;
- le prix d’activation du trailing.

---

## 2.3 Récupération du prix de marché courant

### `execution_engine/broker_adapter.py`

Ajout :

- `get_latest_market_price(symbol)`

Stratégie utilisée :

1. essayer d’abord la position broker (`current_price`, sinon `market_value / qty`) ;
2. fallback vers les dernières quotes Alpaca via `fetch_latest_quotes(...)`.

### Effet métier

Le trigger trailing n’est plus évalué sur une donnée statique :

- il repose sur une **observation runtime du marché**.

---

## 2.4 Transition opérationnelle stop initial -> trailing

### `execution_engine/executor.py`

La logique `_submit_children(...)` a été étendue.

Le lifecycle devient :

1. soumission du `take_profit` ;
2. soumission du `stop initial` broker-side si possible ;
3. si le stop initial existe et si la transition dynamique est activée :
   - surveillance du trigger sur une fenêtre bornée ;
4. quand le trigger est atteint :
   - annulation du stop initial ;
   - confirmation de l’annulation ;
   - soumission d’un `trailing_stop` ;
5. si l’annulation échoue ou si la fenêtre expire :
   - le stop initial reste en place ;
   - l’échec est tracé en audit.

### Helpers ajoutés

- `_persist_child_order_state(...)`
- `_cancel_child_for_transition(...)`
- `_maybe_activate_dynamic_trailing(...)`

### Effet métier

On a maintenant une vraie logique de **promotion de protection** :

- protection dure immédiatement ;
- protection plus dynamique ensuite si le trade évolue favorablement.

## 5. Ce que cette passe couvre réellement

### Côté exécution
- stop initial broker-side natif posé immédiatement ;
- trigger métier configurable pour activer le trailing ;
- promotion `stop -> trailing` pendant le run ;
- annulation confirmée du stop initial avant bascule ;
- audit détaillé de la transition.

### Côté observabilité
- métriques explicites sur le trailing dynamique ;
- page exécution enrichie ;
- résumé métier plus riche.

---

## 6. Limites restantes / prochaines étapes naturelles

1. **monitoring post-run plus robuste**
   - actuellement la promotion dynamique se fait dans la fenêtre de surveillance du run ;
   - une étape suivante naturelle serait un job / watcher dédié capable de poursuivre la surveillance après la fin du run.

2. **replace broker natif au lieu de cancel+submit**
   - aujourd’hui la stratégie retenue est prudente : annuler puis soumettre ;
   - une optimisation future serait d’utiliser `replace_order` si le broker supporte proprement la mutation `stop -> trailing`.

3. **OCO lifecycle encore plus riche**
   - mieux intégrer la transition dans la logique OCO globale ;
   - tracer plus finement la relation entre `TP`, `stop initial`, `trailing dynamique`.

4. **IHM plus visuelle**
   - badges/couleurs dédiés pour distinguer :
     - stop initial actif,
     - trailing activé,
     - timeout de transition,
     - échec d’annulation.

---

## 7. Verdict

Cette passe fait évoluer le système d’une simple protection statique vers un **lifecycle de protection progressif** :

- **protéger immédiatement** avec un stop initial broker-side ;
- **laisser courir intelligemment** via trailing dynamique quand le trade valide un trigger métier.

Le pipeline devient plus proche d’une gestion de position réelle :

- défense initiale stricte ;
- puis adaptation dynamique quand la position entre dans sa zone de confort.
