## 1. Synthèse exécutive

Le module `risk_management` est **bien structuré pour une V1/V2 opérationnelle** :

- séparation claire entre config, repository, sizing, contraintes, corrélation et persistance ;
- pipeline simple à lire et à maintenir ;
- bonne intention métier pour un portefeuille cible long-only ;
- audit minimal déjà exploitable via `risk_decisions`, `portfolio_targets` et `run_business_summaries`.

En revanche, pour un usage **professionnel en swing trading daily cash**, avec **jusqu’à 10 ans d’historique par symbole**, il reste plusieurs faiblesses importantes.

### Verdict expert

Le module est aujourd’hui **fonctionnel mais pas encore totalement “point-in-time safe” ni pleinement “production-grade”**.

Les problèmes les plus importants sont :

1. **le `trade_date` n’est pas respecté sur la majorité des entrées**, ce qui crée du leakage et rend les reruns historiques non fiables ;
2. **le circuit breaker est quasi inactif dans le run standard** ;
3. **l’equity effective est enrichie par les dividendes de façon globalement incorrecte** ;
4. **le sizing ATR / Kelly n’est pas suffisamment tracé pour porter une vraie logique de risque jusqu’à l’exécution** ;
5. **les tests sont encore trop superficiels pour sécuriser un moteur de risque**.

### Recommandation stratégique claire

Pour ton contexte, je recommande la cible suivante :

- **moteur long-only cash** ;
- **ATR sizing comme moteur par défaut** ;
- **Kelly désactivé par défaut en production** tant que les métriques ML ne sont pas strictement PIT et calibrées par date ;
- **toutes les lectures faites “as-of trade_date”** ;
- **schéma SQL simplifié et canonique** après reset, sans fallback V1/V2/V3.

## 2. Ce que le module fait bien aujourd’hui

### Points positifs

1. **Orchestration claire**
   - `risk_management/cli.py` charge les entrées, construit les positions, persiste les résultats, puis émet un résumé run-level.

2. **Découpage propre des responsabilités**
   - `position_sizer.py` : sizing par ATR ;
   - `kelly.py` : surcouche optionnelle ;
   - `constraints.py` : contraintes portefeuille ;
   - `risk_checker.py` : intégration contraintes + circuit breaker ;
   - `portfolio_builder.py` : assemblage final.

3. **Audit fonctionnel déjà utile**
   - `risk_decisions` et `portfolio_targets` conservent déjà plus que le strict minimum ;
   - l’IHM peut afficher les décisions et le portefeuille cible ;
   - `run_business_summaries` donne un premier niveau d’observabilité.

4. **Design cohérent avec un workflow swing daily**
   - filtrage par corrélation ;
   - contraintes par position / secteur / exposition ;
   - sizing basé sur volatilité ;
   - préparation explicite d’un portefeuille cible pour l’exécution.

## 3. Constats critiques et recommandations

## P0 — à traiter avant de considérer le module comme fiable en production

### P0.1 — Le module n’est pas réellement “point-in-time” malgré `--trade-date`

**Constat**

`risk_management/cli.py` accepte `--trade-date`, mais dans `risk_management/db_io.py` seule la méthode `load_predictions()` respecte réellement cette date.

En revanche :

- `load_candidates()` lit `stock_scores` courant ;
- `load_prices()` lit le dernier prix disponible, pas le prix `<= trade_date` ;
- `load_return_matrix()` lit les derniers prix disponibles sans borne `trade_date` ;
- `load_win_rates()` prend le dernier training “completed”, pas nécessairement valable à la date du run.

**Problème**

Un rerun historique peut mélanger :

- un univers candidat ancien,
- des prédictions anciennes,
- des prix récents,
- des rendements récents,
- des métriques ML potentiellement postérieures.

C’est un **leakage majeur**.

**Impact métier**

- résultats non reproductibles ;
- backtests / reruns trompeurs ;
- faux sentiment de robustesse du moteur de risque ;
- difficulté à auditer une décision passée.

**Recommandation**

Après reset, imposer une règle simple : **toute entrée du moteur de risque doit être chargée en mode as-of `trade_date`**.

### Cible recommandée

- candidats : lire depuis `stock_scores_history` sur `snapshot_date = trade_date` ;
- prix / ATR : lire `stock_bars_daily` avec `date <= trade_date` ;
- matrice de rendements : construire les retours sur une fenêtre bornée par `trade_date` ;
- métriques ML : ne charger que des artefacts dont la date / fin de run est `<= trade_date` ;
- persister dans l’audit les dates source réellement utilisées (`score_snapshot_date`, `price_asof_date`, `ml_metrics_asof_date`).

---

### P0.2 — Le circuit breaker est presque inopérant dans le run standard

**Constat**

Le `PortfolioBuilder` peut consommer un `PnLSnapshot`, mais `risk_management/cli.py` instancie :

- `repo = RiskRepository()` ;
- `builder = PortfolioBuilder(config)`

sans charger d’état de PnL réel.

Donc dans le chemin normal :

- `CircuitBreaker._check_drawdown()` voit `None` ;
- `CircuitBreaker._check_daily_loss()` voit `None` ;
- le circuit breaker ne coupe rien.

**Problème**

La doc et le nom des composants laissent penser que le portefeuille peut être bloqué en cas de drawdown ou perte journalière, mais en pratique la protection est **inactive sauf injection externe**.

**Recommandation**

Créer une vraie source de vérité de risque compte :

- snapshot broker / ledger en base ;
- `current_equity` ;
- `high_watermark` ;
- `daily_realized_pnl` ;
- `daily_unrealized_pnl` si souhaité ;
- `buying_power` / `cash_available`.

Puis faire charger ce snapshot par le CLI avant la construction du portefeuille.

**Décision produit**

Si cette donnée n’existe pas encore, mieux vaut :

- soit **désactiver explicitement** le circuit breaker dans la doc ;
- soit **implémenter réellement** la dépendance account risk avant d’affirmer qu’il protège la stratégie.

---

### P0.3 — L’equity est enrichie par les dividendes de manière incorrecte

**Constat**

Dans `risk_management/cli.py`, l’equity de départ est augmentée par `CorporateActionRepository.get_total_dividends()`.

Or dans `corporate_actions/db_io.py`, cette méthode :

- n’est pas filtrée par `account_id` ;
- n’est pas filtrée par `trade_date` ;
- retourne le cumul global des dividendes crédités.

**Problème**

Le moteur peut surévaluer le capital disponible en incorporant :

- des dividendes d’un autre compte ;
- des dividendes futurs par rapport au `trade_date` ;
- des flux de caisse qui ne sont peut-être plus disponibles.

**Impact métier**

Très important : surallocation potentielle, sizing artificiellement trop grand, incohérence entre risque théorique et cash réel.

**Recommandation**

Après reset, l’equity de risque doit venir d’une source compte canonique :

- soit directement du broker ;
- soit d’une table `account_risk_snapshots` ou `account_equity_snapshots` ;
- avec au minimum `account_id`, `trade_date`, `cash`, `equity`, `buying_power`, `high_watermark`.

Et si les dividendes sont réintégrés :

- les filtrer par `account_id` ;
- les filtrer à `effective_date <= trade_date` ;
- idéalement ne plus les recalculer dans le CLI, mais dans une table consolidée de compte.

---

### P0.4 — Le moteur de risque ne persiste pas les vraies variables de risque utiles à l’exécution

**Constat**

Le sizing ATR calcule implicitement un risque par action via :

- `atr_20`
- `atr_stop_multiple`

Mais `portfolio_targets` ne persiste pas de champs tels que :

- `stop_price` ;
- `risk_per_share` ;
- `initial_risk_dollars` ;
- `risk_budget_pct` / `risk_budget_dollars` ;
- `expected_loss_at_stop`.

L’`execution_engine` lit surtout :

- `shares` ;
- `entry_price` ;
- `target_weight`.

**Problème**

Le moteur dit “risk management”, mais l’aval exécution ne reçoit pas toute la sémantique de risque utilisée pour décider la taille.

**Recommandation**

Faire de `portfolio_targets` une vraie table canonique de portefeuille cible avec, pour chaque ligne :

- `side` (`long`) ;
- `target_shares` ;
- `entry_reference_price` ;
- `stop_price_initial` ;
- `atr_20` ;
- `atr_stop_multiple` ;
- `risk_per_share` ;
- `risk_budget_dollars` ;
- `target_notional` ;
- `target_weight` ;
- `decision_rank`.

Pour un système swing propre, c’est beaucoup plus professionnel et cela permet ensuite :

- audit ;
- contrôle ex post ;
- OCO plus cohérent ;
- vérification de dérive entre décision et exécution.

## P1 — fortement recommandé pour professionnaliser le module

### P1.1 — `load_prices()` et l’ATR méritent une correction formelle

**Constat**

Dans `risk_management/db_io.py`, le calcul ATR :

- prend une moyenne simple des true ranges ;
- semble utiliser `rn <= :n + 1` alors que l’intention métier pour un ATR 20 est de prendre 20 observations de true range ;
- n’écrit pas la date effective du prix utilisé.

**Risque**

- ATR potentiellement légèrement biaisé ;
- difficulté d’audit ;
- sizing non parfaitement explicable.

**Recommandation**

- corriger la fenêtre ATR pour qu’elle soit exactement cohérente avec `atr_window` ;
- persister `price_asof_date` et `atr_asof_date` ;
- documenter clairement si l’ATR retenu est une SMA du TR ou un Wilder ATR ;
- si l’ATR est absent ou trop court, préférer un **rejet contrôlé** ou un fallback de volatilité mieux défini plutôt qu’un equal-weight implicite.

### Recommandation financière

Pour du swing cash, je préfère en production :

- **ATR disponible = sizing normal** ;
- **ATR indisponible = rejet**, sauf cas très particulier.

Le fallback equal-weight est pratique pour une démo, moins pour un moteur de risque strict.

---

### P1.2 — Le filtre de corrélation est utile, mais encore trop “pré-sizer” et trop simple

**Constat**

`risk_management/correlation_filter.py` applique un filtre greedy :

- avant contraintes finales ;
- avant connaissance des poids réellement approuvés ;
- sur corrélation de rendements journaliers ;
- avec seulement un seuil pairwise positif.

**Limite**

Deux titres fortement corrélés mais avec tailles finales très différentes ne devraient pas être traités exactement comme deux positions de même poids.

**Recommandation**

Garder une approche simple, mais plus professionnelle :

1. conserver le filtre pairwise comme pré-filtre ;
2. ajouter ensuite un contrôle de concentration après sizing approuvé, par cluster / secteur ;
3. calculer au minimum des métriques run-level :
   - corrélation moyenne pondérée ;
   - plus forte paire corrélée retenue ;
   - poids cumulé du plus gros cluster.

### Paramétrage recommandé pour ton cas d’usage

Pour du swing daily, je recommanderais plutôt un réglage cible du type :

- lookback corrélation : **63 à 126 séances** ;
- min overlap : **au moins 60 séances** ;
- seuil pairwise : **0.75–0.85** selon l’univers.

Le `60/40/0.80` actuel est acceptable comme point de départ, mais encore un peu court et bruité.

---

### P1.3 — Kelly est intéressant, mais trop fragile sans vraie discipline PIT

**Constat**

`risk_management/kelly.py` combine :

- `predicted_proba` ;
- `historical_win_rate` ;
- `default_win_rate=0.55` si absent.

Mais `load_win_rates()` ne garantit pas un snapshot strictement as-of `trade_date`, ni une cohérence forte entre :

- horizon de prédiction ;
- run ML ;
- métrique de calibration ;
- marché courant.

**Risque**

Le Kelly a tendance à **sur-réagir à des probabilités mal calibrées**. C’est particulièrement dangereux si les inputs ne sont pas strictement PIT.

**Recommandation claire**

- **ATR-only par défaut** en production ;
- activer Kelly seulement quand tu peux prouver :
  - calibration propre ;
  - snapshot par date ;
  - métriques par horizon cohérentes ;
  - tests de stabilité hors échantillon.

Si Kelly est conservé, le positionner comme :

- **surcouche conservative** ;
- avec cap dur bas ;
- et persistance obligatoire de la provenance (`ml_run_id`, `metrics_run_id`, `calibration_method`, `effective_probability`).

---

### P1.4 — Le schéma SQL doit être simplifié après reset

**Constat**

`RiskRepository.write_risk_decisions()` et `write_portfolio_targets()` tentent des insertions V4, puis V3, puis V2, puis fallback V1.

**Problème**

Comme tu repars d’une base saine, cette logique de compatibilité n’apporte pas de valeur et alourdit le module.

**Recommandation**

Après reset :

- définir un **schéma unique** ;
- supprimer les insertions fallback ;
- rendre les colonnes importantes non ambiguës et obligatoires ;
- ajouter les contraintes et index utiles.

### DDL cible minimale recommandée

#### `risk_decisions`
- clé métier unique : `(run_id, symbol, account_id)` ;
- index : `(account_id, trade_date, created_at)` ;
- colonnes techniques :
  - `candidate_rank`
  - `decision_rank`
  - `score_snapshot_date`
  - `price_asof_date`
  - `corr_lookback_days`
  - `atr_window`
  - `risk_budget_dollars`
  - `target_notional`

#### `portfolio_targets`
- clé métier unique : `(run_id, symbol, account_id)` ;
- colonnes de risque complètes ;
- distinction nette entre prix de décision, stop initial et poids cible ;
- optionnellement un champ `rebalance_action` (`new`, `increase`, `hold`, `exit`, `trim`).

---

### P1.5 — La batterie de tests est largement insuffisante pour un moteur de risque

**Constat**

Une grande partie des tests spécifiques `risk_management` sont encore des tests d’import.

**Problème**

Un moteur de risque doit être protégé par des tests métier, pas seulement par des smoke tests.

**Tests à ajouter en priorité**

1. **as-of safety**
   - un `trade_date` historique ne doit jamais lire de prix ou de métriques futures ;

2. **ATR exact**
   - vérifier la fenêtre et la valeur attendue sur dataset contrôlé ;

3. **circuit breaker live**
   - cas drawdown, cas daily loss, cas absence de snapshot ;

4. **dividendes / equity**
   - aucun dividende futur ou d’un autre compte ne doit augmenter l’equity ;

5. **sector cap + max gross exposure**
   - vérifier le comportement de réduction vs rejet ;

6. **corrélation**
   - cas de rejet pairwise ;
   - cas d’overlap insuffisant ;
   - cas de run déterministe ;

7. **Kelly**
   - fallback propre ;
   - cap max ;
   - absence de win rate ;

8. **idempotence d’écriture**
   - re-run d’un même `run_id` interdit ou explicitement contrôlé.

---

### P1.6 — Le résumé business est utile mais encore incomplet pour piloter un vrai moteur de risque

**Aujourd’hui**

Le résumé persiste déjà :

- nombre de symboles acceptés / réduits / rejetés ;
- notional total ;
- equity effective.

**Il manque encore**

- gross exposure finale ;
- plus gros poids ;
- plus gros poids secteur ;
- nombre de rejets par raison ;
- couverture ML (% de symboles avec `predicted_proba`) ;
- couverture ATR ;
- corrélation max retenue ;
- budget de risque total consommé.

**Recommandation**

Faire du résumé run-level un vrai tableau de bord d’exploitation.

## P2 — améliorations utiles mais non bloquantes

### P2.1 — `load_return_matrix()` doit devenir plus propre et plus déterministe

Le SQL actuel limite globalement à `lookback_days * len(symbols)`, ce qui est pragmatique mais pas idéal.

Je recommande une lecture **top N par symbole** via `ROW_NUMBER() OVER (PARTITION BY symbol ORDER BY date DESC)` pour éviter les biais de couverture.

---

### P2.2 — Les types SQL monétaires peuvent être plus stricts

Les tables `risk_decisions` et `portfolio_targets` utilisent beaucoup de `DOUBLE`.

Pour un moteur financier, il est souvent préférable d’utiliser :

- `DECIMAL` pour les prix / montants ;
- éventuellement `DOUBLE` seulement pour des ratios analytiques.

Ce n’est pas critique à court terme, mais c’est une amélioration saine après reset.

---

### P2.3 — Le modèle de conviction peut être davantage gouverné

`compute_conviction()` mélange linéairement score quant et `predicted_proba`.

C’est acceptable si `score_used` est bien calibré sur `[0,1]`, mais idéalement il faudrait aussi tracer :

- la version de calibration ;
- la distribution du score ;
- un éventuel “confidence gate” pour neutraliser un ML trop ancien ou absent.

## 4. Architecture cible recommandée après reset

## Principe directeur

**Un moteur de risque doit être intégralement explicable, as-of correct, et transmissible jusqu’à l’exécution.**

### Flux cible

1. charger les candidats du jour depuis un snapshot historique (`stock_scores_history`) ;
2. charger prix, ATR et rendements au plus tard à `trade_date` ;
3. charger les probabilités ML et métriques correspondantes au même horizon temporel ;
4. charger le snapshot de compte (`cash`, `equity`, `buying_power`, `high_watermark`) ;
5. construire les positions cibles ;
6. persister :
   - décisions détaillées ;
   - portefeuille cible complet ;
   - résumé run-level.

### Tables cibles à privilégier

#### `account_risk_snapshots`
- `account_id`
- `trade_date`
- `cash`
- `equity`
- `buying_power`
- `high_watermark`
- `daily_realized_pnl`
- `daily_unrealized_pnl`
- `created_at`

#### `risk_decisions`
- journal détaillé de toutes les évaluations ;
- une ligne par symbole candidat.

#### `portfolio_targets`
- canonique pour l’exécution ;
- seulement les positions effectivement retenues ;
- avec stop initial et budget de risque.

## 5. Paramétrage cible recommandé pour ton usage swing cash

Ce ne sont pas des obligations, mais des bornes raisonnables à tester :

- `risk_per_trade_pct` : **0.5% à 1.0%** ;
- `max_position_weight` : **8% à 10%** ;
- `max_sector_weight` : **20% à 25%** si univers assez concentré ;
- `max_positions` : **8 à 12** pour un portefeuille swing cash concentré mais pilotable ;
- `max_gross_exposure` : **1.0** tant que tu restes cash long-only ;
- `atr_stop_multiple` : **2.0 à 3.0** selon la nervosité des titres ;
- Kelly : **désactivé par défaut** tant que la calibration ML n’est pas industrialisée.

## 7. Verdict final

Le module `risk_management` est une **bonne base de travail**, avec une architecture déjà lisible et cohérente. Mais pour passer au niveau professionnel, il faut maintenant faire le saut suivant :

### Les 5 décisions les plus importantes

1. **Tout lire en as-of `trade_date`**
2. **Ne plus dériver l’equity depuis un cumul global de dividendes**
3. **Activer un vrai circuit breaker alimenté par un snapshot compte**
4. **Persister les variables de risque complètes dans `portfolio_targets`**
5. **Supprimer la compatibilité historique et figer un schéma canonique propre**

### Mon avis expert

- **niveau actuel** : bon prototype avancé / base sérieuse ;
- **niveau visé** : moteur de risque pleinement traçable, PIT-safe et exploitable en live ;
- **choix opérationnel recommandé maintenant** : **ATR sizing par défaut, Kelly en option expérimentale seulement**.
