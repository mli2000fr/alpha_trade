# Screener — Évolution phase 6 orientée robustesse par régime de marché

## Objectif

La phase 5 savait déjà :

- classer automatiquement les scénarios du `summary_metrics.csv` ;
- recommander un meilleur compromis global entre robustesse, survie et qualité forward.

Mais elle restait encore **agrégée sur toute la période**.

Or un réglage de screener peut être :

- excellent en marché haussier ;
- fragile en marché baissier ;
- ou très bon seulement dans des contextes de volatilité élevée.

L’objectif de cette phase 6 est donc d’ajouter une lecture **par régime de marché** :

- `bull`
- `bear`
- `range`
- `vol`

et de conserver la même logique que la phase 5 :

1. **artefacts exportés** ;
2. **recommandation automatique** ;
3. **classement explicable** ;
4. **lecture opérationnelle**.

En plus du meilleur compromis global, le système sait maintenant identifier :

- le meilleur compromis **dans chaque régime** ;
- et le meilleur compromis **cross-régimes**.

---

## Ce que j’ai ajouté

## 1. Une classification explicite des régimes de marché
Fichier : `backtesting/screener_diagnostics.py`

J’ai ajouté une fonction dédiée :

- `classify_market_regimes(...)`

Elle classe le benchmark (par défaut `SPY`) séance par séance en :

- `vol`
- `bull`
- `bear`
- `range`

### Logique utilisée
La logique reste volontairement simple et robuste :

### A. `vol`
Le jour est classé `vol` si la volatilité réalisée récente est nettement au-dessus de sa médiane historique récente.

Concrètement, j’utilise :

- une vol réalisée sur `20` jours ;
- comparée à une médiane glissante sur `252` jours ;
- avec un multiplicateur `1.35`.

### B. `bull`
Si le jour n’est pas `vol`, il devient `bull` si :

- le benchmark est au-dessus de sa moyenne longue (`SMA 200`) ;
- et que le rendement sur `60` jours est clairement positif (`> +3%`).

### C. `bear`
Si le jour n’est pas `vol`, il devient `bear` si :

- le benchmark est sous sa `SMA 200` ;
- et que le rendement sur `60` jours est clairement négatif (`< -3%`).

### D. `range`
Sinon, le jour est classé `range`.

### Pourquoi cette hiérarchie
La priorité donnée à `vol` permet d’isoler les contextes où le marché devient anormalement instable, même si la tendance de fond reste haussière ou baissière.

C’est utile pour détecter des scénarios qui semblent robustes en moyenne, mais deviennent moins exploitables quand le régime de volatilité se dégrade.

## 2. Enrichissement de `daily_metrics.csv` avec le contexte de marché
Fichier : `backtesting/screener_diagnostics.py`

Le service `ScreenerDiagnosticsService.analyze_period(...)` :

- précharge maintenant un historique benchmark borné mais avec warmup ;
- calcule les régimes pour les dates évaluées ;
- fusionne ces informations dans `daily_metrics`.

### Nouvelles colonnes injectées au niveau journalier
On retrouve notamment :

- `market_regime`
- `benchmark_symbol`
- `benchmark_close`
- `benchmark_return_60d`
- `benchmark_sma_200`
- `benchmark_sma_200_gap`
- `benchmark_vol_20d`
- `benchmark_vol_20d_median_252d`

### Pourquoi c’est important
À partir de là, chaque ligne `scenario x date` n’est plus seulement évaluée sur ses métriques screener / selector / portefeuille,
mais aussi replacée dans le **contexte de marché** qui prévalait ce jour-là.

## 3. Une synthèse dédiée par régime
Fichier : `backtesting/screener_diagnostics.py`

J’ai ajouté :

- `summarize_screener_diagnostics_by_regime(...)`

Cette fonction prend `daily_metrics` enrichi et reconstruit une synthèse par :

- `market_regime`
- `scenario_name`

Elle produit un nouveau tableau :

- `summary_metrics_by_regime.csv`

### Ce que contient cette synthèse
On y retrouve la même logique que `summary_metrics.csv`, mais segmentée par régime.

Exemple de lecture :
- comment un scénario se comporte-t-il en `bull` ?
- le même scénario reste-t-il bon en `bear` ?
- survit-il encore correctement en `vol` ?

## 4. Une recommandation automatique dans chaque régime
Fichier : `backtesting/screener_diagnostics.py`

J’ai ajouté :

- `recommend_screener_scenarios_by_regime(...)`

Cette fonction réutilise le moteur de phase 5 régime par régime.

### Ce qu’elle fait
Pour chaque régime disponible :

- isole le `summary_metrics_by_regime` correspondant ;
- relance la recommandation multi-critères ;
- produit un classement local ;
- construit un résumé JSON par régime.

### Résultat
On obtient :

- `scenario_recommendations_by_regime.csv`
- `recommendation_summary_by_regime.json`

### Ce que ça permet
On peut désormais distinguer :

- le meilleur compromis en `bull` ;
- le meilleur compromis en `bear` ;
- le meilleur compromis en `range` ;
- le meilleur compromis en `vol`.

Autrement dit, la recommandation n’est plus seulement globale :
elle devient aussi **contextuelle**.

## 5. Un score de robustesse cross-régimes
Fichier : `backtesting/screener_diagnostics.py`

La vraie valeur ajoutée de la phase 6 est là :

j’ai ajouté une couche de synthèse transverse pour trouver le **meilleur scénario robuste entre régimes**, pas seulement le meilleur dans un régime isolé.

### Nouvelles fonctions
- `build_cross_regime_recommendations(...)`
- intégrée via `recommend_screener_scenarios_by_regime(...)`

### Ce que mesure le score cross-régimes
Pour chaque scénario, j’agrège notamment :

- `mean_regime_overall_score`
- `worst_regime_overall_score`
- `regime_coverage_ratio`
- `regime_overall_score_std`
- `mean_regime_confidence_score`

### Intuition de scoring
Un bon scénario cross-régimes n’est pas seulement :

- celui qui a la meilleure moyenne ;
- mais aussi celui qui garde un **pire cas acceptable** ;
- reste présent sur plusieurs régimes ;
- et varie moins fortement d’un régime à l’autre.

### Pourquoi le `worst_regime_overall_score` est important
C’est le garde-fou principal contre les scénarios “trop opportunistes”.

Exemple :
- un scénario peut être excellent en `bull` ;
- mais s’effondrer en `bear` ;
- dans ce cas, il ne doit pas être recommandé comme scénario robuste global.

### Artefacts produits
- `cross_regime_recommendations.csv`
- `cross_regime_recommendation_summary.json`

### Ce que sort la recommandation
La phase 6 propose désormais explicitement un :

- `best_cross_regime_compromise`

qui représente le meilleur arbitrage pour un calibrage plus robuste aux changements de contexte de marché.

## 8. Réanalyse d’un run existant avec phase 6 automatique
Fichier : `backtesting/cli.py`

La commande existante :

```powershell
python -m backtesting recommend-screener
```

reste valable, mais elle sait maintenant faire plus.

### Nouveau comportement
Si le `daily_metrics.csv` fourni contient `market_regime`, alors la commande :

- recalcule la recommandation globale phase 5 ;
- reconstruit `summary_metrics_by_regime` ;
- produit aussi les artefacts phase 6 ;
- affiche le meilleur compromis cross-régimes.

### Pourquoi c’est utile
On peut donc :

- relire un run archivé ;
- comparer plusieurs diagnostics déjà stockés ;
- refaire l’analyse de robustesse sans relancer tout le replay PIT.

## 9. Ce que change réellement cette phase 6

Avant :
- on savait quel scénario semblait le meilleur **en moyenne sur toute la période** ;
- mais on savait moins s’il tenait bien dans différents contextes de marché.

Après :
- on sait quel scénario est le meilleur en `bull` ;
- lequel résiste le mieux en `bear` ;
- lequel reste exploitable en `vol` ;
- et surtout lequel offre le meilleur compromis **cross-régimes**.

En pratique, cela évite de sur-optimiser un paramétrage juste parce qu’il performe très bien sur un seul climat de marché dominant.

---

## 10. Ce que j’ai volontairement gardé simple

### 1. Taxonomie unique de régime
J’ai retenu un seul label final par jour :

- `bull`
- `bear`
- `range`
- `vol`

et non un système plus complexe du type :

- tendance × volatilité,
- ou un clustering de régimes plus opaque.

### Pourquoi
Cela garde :

- une lecture simple ;
- des CSV directement exploitables ;
- une logique facile à auditer ;
- une compatibilité naturelle avec la phase 5.

### 2. Heuristique explicable plutôt que modèle opaque
La classification régime n’utilise pas de modèle ML dédié.

Elle repose sur :

- tendance (`SMA 200`) ;
- momentum (`retour 60j`) ;
- volatilité réalisée relative.

C’est un bon compromis entre :

- lisibilité ;
- stabilité ;
- et coût de calcul.

## Impact attendu

Cette phase 6 permet enfin de répondre à des questions du type :

- un scénario “meilleur globalement” tient-il encore en marché baissier ?
- un scénario très agressif en `bull` est-il trop fragile en `vol` ?
- quel réglage conserve la meilleure conversion jusqu’au portefeuille cible quand le climat de marché change ?
- quel scénario faut-il privilégier si l’on veut éviter un calibrage trop dépendant d’un seul régime ?

Autrement dit, la logique de calibration du screener devient moins :

- moyenne globale,
- intuitionnelle,
- ou dépendante d’une seule sous-période,

et davantage :

- **contextuelle**,
- **robuste**,
- et **auditée par régime de marché**.

---

## Suite logique

La suite naturelle serait une phase 7 orientée :

1. comparaison **multi-périodes + multi-régimes** ;
2. lecture par **régime de volatilité séparé de la tendance** ;
3. recommandation par objectif opérationnel :
   - scénario le plus robuste,
   - scénario le plus offensif,
   - scénario défensif / bear-friendly,
   - scénario équilibré ;
4. reporting plus visuel type notebook / dashboard.

Mais la base essentielle est désormais en place :

**le pipeline sait maintenant mesurer et recommander non seulement le meilleur compromis global, mais aussi la robustesse des scénarios selon les régimes de marché et leur comportement cross-régimes.**
