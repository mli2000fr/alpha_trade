# Screener — Évolution phase 2
## Objectif
Mettre en place la refonte la plus rentable sur le module `screener` :
- chargement en **2 passes** ;
- réduction du **coût historique** ;
- ajout de **métriques de run détaillées**.
## Ce que j’ai modifié
### 1. Architecture de run détaillée
Fichier : `screener/models.py`
Ajout de structures dédiées :
- `ScreenerChunkMetrics`
- `ScreenerRunReport`
Et extension de `ScreenerConfig` avec :
- `enable_two_pass_loading=True`
- `first_pass_window_days=400`
Effet :
- le run est maintenant instrumenté proprement ;
- les métriques sont transportées explicitement entre les chunks et l’orchestrateur ;
- le comportement 2 passes est configurable.
### 2. Séparation du calcul en passe récente + passe historique
Fichier : `screener/pipeline.py`
Nouvelles briques :
- `screen_recent_prices(...)`
- `compute_historical_range_stats_from_prices(...)`
- `finalize_scores_with_historical_range(...)`
Nouvelle logique :
- **passe 1** : historique minimal, prix minimal, liquidité, force relative ;
- **passe 2** : calcul du `historical_range_score` à partir d’un jeu d’agrégats historiques.
Effet :
- le calcul devient découplé ;
- on peut réutiliser la logique de scoring sans toujours relire l’historique complet ;
- `compute_scores_from_prices(...)` reste compatible pour les tests et usages existants.
### 3. Loaders DB optimisés
Fichier : `screener/db_io.py`
Ajout de deux loaders ciblés :
- `load_recent_prices_for_chunk(...)`
- `load_historical_range_stats_for_symbols(...)`
Et conservation de `load_prices_for_chunk(...)` comme loader historique complet de compatibilité.
#### Passe 1
Charge uniquement la fenêtre récente nécessaire via `first_pass_window_days`.
#### Passe 2
Ne recharge plus 10 ans de barres pour chaque survivant ; lit seulement :
- `MIN(low)`
- `MAX(high)`
par symbole.
Effet :
- réduction massive du coût I/O ;
- baisse du volume mémoire et CPU Python ;
- meilleur scaling quand l’univers grandit.
### 4. Orchestrateur `stock_screener` refondu
Fichier : `screener/stock_screener.py`
Ajouts principaux :
- `_process_chunk_two_passes(...)`
- `_merge_run_metrics(...)`
- `run_screener_with_report(...)`
- `_emit_run_summary(...)`
`run_screener(...)` reste la façade compatible et retourne toujours un `DataFrame`.
`main()` émet désormais un résumé structuré exploitable avec le préfixe standard :
- `::alpha_trade_run_summary::`
Effet :
- meilleure observabilité ;
- meilleure auditabilité ;
- possibilité d’exploiter les métriques côté IHM / supervision / logs.

## Gain métier / technique attendu
### Sur le coût historique
Avant :
- un chunk pouvait relire un historique long pour tous les symboles du chunk.
Maintenant :
- la majorité des symboles meurent en passe 1 ;
- seuls les survivants déclenchent la passe 2 ;
- la passe 2 charge des **agrégats** historiques, pas des séries complètes.
### Sur un univers swing cash daily
Cette approche est bien adaptée à :
- beaucoup de symboles ;
- historique profond ;
- besoin de préfiltrage rapide avant `selector`.

## Pourquoi c’est la refonte la plus rentable
Parce qu’elle améliore en même temps :
1. **la perf** — moins de données lues ;
2. **la scalabilité** — moins de pression mémoire / CPU ;
3. **l’observabilité** — métriques de run détaillées ;
4. **la maintenabilité** — séparation claire entre screening récent et enrichissement historique.
