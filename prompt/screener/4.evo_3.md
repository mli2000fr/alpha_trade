# Screener — Évolution phase 4 objectivée par backtest

## Objectif

Cette phase 4 ne se contente plus d’“améliorer” le `screener` en théorie.

Elle ajoute un **diagnostic PIT (point-in-time)** pour mesurer, sur une plage de dates de marché, l’impact réel de :

- `min_relative_strength_index`
- `historical_range_lookback_days`
- `min_historical_range_score`
- `liquidity_threshold_usd`

sur :

1. la **qualité finale des candidats** ;
2. leur **survie jusqu’au portefeuille cible**.

L’idée est de pouvoir comparer objectivement plusieurs réglages de phase 3, sans se limiter à des intuitions trading.

---

## Ce que j’ai ajouté

### 1. Un module de diagnostic PIT dédié
Fichier : `backtesting/screener_diagnostics.py`

J’ai ajouté un service de diagnostic qui rejoue en mémoire :

- `screener`
- `selector`
- enrichissement score final via sentiment
- construction du **portefeuille cible** côté `risk_management`

pour chaque date de marché testée, et pour chaque scénario de paramètres.

### Ce que calcule ce module
Pour chaque **scénario x date**, il produit notamment :

- `screener_count`
- `selector_filtered_count`
- `selector_candidate_count`
- `portfolio_target_count`
- `portfolio_accepted_count`
- `portfolio_reduced_count`
- `portfolio_rejected_count`

et les ratios de survie :

- `selector_survival_ratio`
- `portfolio_survival_ratio`
- `selector_to_portfolio_survival_ratio`
- `selector_selection_ratio`

Il calcule aussi des métriques de “qualité” :

- moyenne `total_score` au niveau screener ;
- moyenne `relative_strength_index` au niveau screener ;
- moyenne `historical_range_score` au niveau screener ;
- moyenne `final_score` / `final_score_sentiment` au niveau selector ;
- moyenne du score utilisé dans le portefeuille cible.

---

### 2. Mesure de performance forward pour objectiver la qualité
Toujours dans `backtesting/screener_diagnostics.py`

J’ai ajouté des mesures de rendement forward PIT sur horizons :

- `5d`
- `10d`
- `20d`

pour :

- l’ensemble des **candidats selector retenus** ;
- l’ensemble des **titres survivant jusqu’au portefeuille cible**.

Le diagnostic calcule :

- `selector_forward_return_5d / 10d / 20d`
- `portfolio_forward_return_5d / 10d / 20d`
- `benchmark_forward_return_5d / 10d / 20d`
- `selector_excess_return_*`
- `portfolio_excess_return_*`
- `selector_positive_share_*`
- `portfolio_positive_share_*`
- couverture disponible par horizon

### Pourquoi
Cela permet de ne pas juger un réglage uniquement sur :

- le nombre de survivants,
- ou la sélectivité,

mais aussi sur une mesure plus objectivée de la **qualité ex post** des candidats issus du flux.

---

### 3. Génération de scénarios OAT ou grille
Toujours dans `backtesting/screener_diagnostics.py`

J’ai ajouté deux modes de construction de scénarios :

#### Mode OAT (`one-at-a-time`)
Baseline phase 3 + une variation à la fois sur :

- RS min
- lookback de range
- score minimal dans le range
- seuil de liquidité

#### Mode grille (`grid`)
Produit combinatoire des valeurs fournies, avec garde-fou via `max_scenarios`.

### Pourquoi
- `oat` permet une lecture rapide et propre de l’impact isolé de chaque paramètre ;
- `grid` permet ensuite de chercher des zones de paramètres plus efficaces quand on veut aller plus loin.

---

### 4. Une nouvelle commande CLI de diagnostic
Fichier : `backtesting/cli.py`

J’ai ajouté la commande :

```powershell
python -m backtesting diagnose-screener
```

### Options disponibles
- `--start`
- `--end`
- `--limit-days`
- `--mode oat|grid`
- `--chunk-size`
- `--selection-size`
- `--max-positions`
- `--screener-workers`
- `--max-scenarios`
- `--rs-values`
- `--range-lookback-values`
- `--historical-range-score-values`
- `--liquidity-threshold-values`
- `--output-dir`

### Exemple recommandé pour démarrer
```powershell
python -m backtesting diagnose-screener \
  --start 2024-01-01 \
  --end 2024-12-31 \
  --mode oat \
  --limit-days 60 \
  --rs-values 100,102,105 \
  --range-lookback-values 252,504,756 \
  --historical-range-score-values 65,70,75 \
  --liquidity-threshold-values 5000000,10000000,20000000
```

### Artefacts générés
Dans `--output-dir` :

- `daily_metrics.csv`
- `summary_metrics.csv`
- `scenarios.csv`
- `metadata.json`

## Comment la survie est mesurée

La chaîne analysée est maintenant explicitement :

### Étape 1 — Screener
Nombre de symboles survivant au préfiltrage screener.

### Étape 2 — Selector
Nombre de symboles :
- après filtres selector ;
- puis marqués `is_candidate = 1` après ranking final.

### Étape 3 — Portefeuille cible
Nombre de symboles encore vivants après :
- sizing,
- contraintes de portefeuille,
- filtre de corrélation,
- réduction/rejet de risque.

### Ratios principaux
- `selector_survival_ratio = selector_candidate_count / screener_count`
- `portfolio_survival_ratio = portfolio_target_count / screener_count`
- `selector_to_portfolio_survival_ratio = portfolio_target_count / selector_candidate_count`

### Pourquoi c’est utile
On peut enfin distinguer un réglage qui :

- génère beaucoup de survivants mais peu exploitables ensuite ;
- contre un réglage plus sélectif mais plus “convertible” jusqu’au portefeuille cible.

---

## Ce que j’ai volontairement gardé simple

### 1. Diagnostic centré sur le screener
Pour objectiver l’effet des paramètres demandés, le portefeuille cible est construit à partir du score final disponible, sans complexifier inutilement l’analyse avec un couplage ML supplémentaire dans cette phase.

### 2. Point-in-time conservé
Le service charge les prix et rendements nécessaires **bornés à la date testée**, afin de rester cohérent avec une logique backtest / walk-forward.

### 3. Sorties lisibles et exploitables
Le résultat final est exporté dans des CSV simples à relire ou à analyser ensuite dans :

- pandas,
- notebook,
- Excel,
- ou un futur reporting plus avancé.

## Correctif de compatibilité inclus
Fichier : `screener/stock_screener.py`

En validant la phase 4, j’ai détecté un problème réel :

- `backtesting/backfill_scores_history.py` importait `_process_chunk`
- alors que `screener/stock_screener.py` n’exposait plus que `_process_chunk_two_passes`

J’ai donc réintroduit un wrapper privé de compatibilité :

- `_process_chunk(...)`

qui délègue vers l’implémentation actuelle et retourne seulement le `DataFrame` attendu par le backfill PIT.

### Pourquoi c’était nécessaire
Sans ce correctif, les modules de backfill PIT et donc la phase 4 ne pouvaient pas être importés proprement.

## Impact attendu

Cette phase 4 permet maintenant de répondre objectivement à des questions du type :

- est-ce qu’un `RS min = 105` améliore vraiment la qualité finale, ou réduit seulement trop l’univers ?
- est-ce qu’un `range lookback = 252` donne des candidats plus forts que `504` ou `756` ?
- est-ce qu’un `min_historical_range_score = 75` améliore le portefeuille cible, ou devient trop restrictif ?
- est-ce qu’un seuil de liquidité à `20M` améliore réellement la conversion jusqu’au portefeuille cible ?

Autrement dit, on peut maintenant arbitrer les paramètres non plus seulement sur une logique conceptuelle, mais sur :

- **qualité forward**,
- **survie de pipeline**,
- **convertibilité jusqu’au portefeuille cible**.

## Lecture pratique du `summary_metrics.csv`

Les colonnes importantes à comparer sont en priorité :

- `selector_candidate_count_mean`
- `portfolio_target_count_mean`
- `portfolio_survival_ratio_mean`
- `selector_forward_return_20d_mean`
- `portfolio_forward_return_20d_mean`
- `delta_portfolio_survival_ratio_mean`
- `delta_portfolio_forward_return_20d_mean`

### Interprétation rapide
Un bon réglage n’est pas forcément celui qui produit :

- le plus gros univers,
- ni le plus petit.

Le plus intéressant est souvent celui qui combine :

- une bonne **survie jusqu’au portefeuille cible** ;
- une bonne **qualité forward** ;
- une sélectivité qui reste exploitable opérationnellement.

## Ce que cette phase 4 change vraiment

Avant :
- on pouvait améliorer le `screener` ;
- mais on objectivait encore peu l’effet concret des paramètres sur la chaîne complète.

Après :
- on peut comparer plusieurs calibrages de phase 3 ;
- mesurer leur effet sur la survie `screener -> selector -> portefeuille cible` ;
- objectiver la qualité forward moyenne des candidats finaux ;
- sortir des décisions de calibration moins “intuition-driven”.

---

## Recommandation logique pour la suite

La phase 5 naturelle serait d’ajouter :

1. une **comparaison multi-périodes** (bull / bear / range) ;
2. une lecture par **régime de volatilité** ;
3. un reporting synthétique du style :
   - meilleur compromis survie / rendement,
   - scénario le plus robuste,
   - scénario le plus sélectif mais encore exploitable ;
4. éventuellement un export prêt pour notebook / dashboard.

Mais la base essentielle est désormais en place :

**la phase 4 permet enfin de mesurer objectivement l’impact réel des paramètres du screener sur la qualité finale des candidats et leur survie jusqu’au portefeuille cible.**
