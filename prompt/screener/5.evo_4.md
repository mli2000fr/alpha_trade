# Screener — Évolution phase 5 orientée analyse automatique des résultats

## Objectif

La phase 4 produisait déjà des artefacts utiles :

- `daily_metrics.csv`
- `summary_metrics.csv`
- `scenarios.csv`
- `metadata.json`

Mais il manquait encore une brique importante :

**transformer automatiquement ces résultats en recommandation exploitable**.

L’objectif de cette phase 5 est donc de lire les métriques issues du diagnostic PIT et de proposer automatiquement le **meilleur compromis** entre :

1. **robustesse** ;
2. **survie jusqu’au portefeuille cible** ;
3. **qualité forward**.

Autrement dit, au lieu de lire `summary_metrics.csv` “à la main”, la phase 5 ajoute un classement explicable des scénarios et un choix automatique du réglage le plus équilibré.

Fichier : `backtesting/screener_diagnostics.py`

   - les sources de métriques utilisées ;
   - les métriques manquantes éventuelles.

## 2. Un scoring multi-critères robuste / survie / qualité forward
Toujours dans `backtesting/screener_diagnostics.py`

La recommandation n’est pas basée sur une seule colonne.

Elle repose sur **3 piliers**.

### A. Robustesse
Le pilier `robustness_score` utilise principalement :

- `success_rate` dérivé de `days_failed / days_evaluated` ;
- la couverture forward disponible (`portfolio_coverage_*` ou fallback `selector_coverage_*`) ;
- une notion de stabilité quand `daily_metrics.csv` est disponible.

Quand `daily_metrics` est fourni, j’enrichis le résumé avec :

- `portfolio_survival_ratio_std`
- `forward_return_consistency_std`
- `forward_return_positive_day_share`

Cela permet d’éviter de recommander un scénario seulement parce qu’il a une bonne moyenne, alors que son comportement journalier est trop instable.

### B. Survie
Le pilier `survival_score` combine :

- `portfolio_survival_ratio_mean`
- `selector_to_portfolio_survival_ratio_mean`
- `portfolio_target_count_mean`
  avec fallback sur `selector_candidate_count_mean` si besoin.

L’idée est de favoriser les scénarios qui :

- ne s’effondrent pas entre screener et portefeuille cible ;
- gardent un univers encore exploitable ;
- convertissent mieux en candidats réellement utilisables.

### C. Qualité forward
Le pilier `forward_quality_score` donne la priorité à :

- `portfolio_excess_return_20d_mean`
- sinon `portfolio_forward_return_20d_mean`
- avec backups côté selector (`selector_excess_return_*`, `selector_forward_return_*`)
- plus `portfolio_positive_share_20d_mean` ou fallback selector.

J’ajoute aussi un petit signal relatif à la baseline si les colonnes delta existent, par exemple :

- `delta_portfolio_excess_return_20d_mean`
- ou fallback `delta_portfolio_forward_return_20d_mean`

## 3. Normalisation explicable et tolérante aux cas limites
Toujours dans `backtesting/screener_diagnostics.py`

Pour éviter qu’une métrique brute domine les autres, j’ai ajouté une normalisation inter-scénarios.

### Ce que fait l’analyse
- winsorisation légère des extrêmes ;
- normalisation min-max entre scénarios ;
- inversion automatique pour les métriques “coût” (ex : instabilité, échec) ;
- agrégation pondérée par pilier ;
- score final via **moyenne géométrique pondérée**.

### Pourquoi la moyenne géométrique
Elle pénalise naturellement les scénarios trop déséquilibrés.

Exemple :
- un scénario très bon en forward mais faible en robustesse ne doit pas sortir automatiquement premier ;
- un scénario très robuste mais trop pauvre en survie / qualité forward non plus.

La moyenne géométrique est plus adaptée qu’une simple moyenne arithmétique pour chercher un **compromis**.

---

## 4. Gestion explicite des données incomplètes
Toujours dans `backtesting/screener_diagnostics.py`

J’ai ajouté plusieurs garde-fous pour que l’analyse reste exploitable même si certaines colonnes manquent.

### Cas gérés
- `summary_metrics` vide → retour propre avec statut `empty` ;
- colonne absente → fallback sur une autre métrique compatible ;
- métrique entièrement absente → neutralisation du score à `0.5` + baisse de confiance ;
- métrique constante entre scénarios → score neutre `0.5` ;
- scénario unique → classement toujours possible, sans explosion de calcul ;
- baseline absente → l’analyse continue, mais sans dépendre des deltas.

### Effet concret
J’ai séparé :
- le **score de scénario** ;
- le **confidence_score**.

Ainsi, un scénario peut rester bon mais être signalé comme partiellement incomplet si trop de métriques sont indisponibles.

## 6. Intégration automatique à la commande de diagnostic
Fichier : `backtesting/cli.py`

La commande existante :

```powershell
python -m backtesting diagnose-screener
```

ne s’arrête plus au diagnostic phase 4.

Elle lance maintenant automatiquement la phase 5 derrière.

### Ce qu’elle fait désormais en sortie
Après calcul PIT :
1. export des artefacts de phase 4 ;
2. analyse automatique des scénarios ;
3. export des artefacts de phase 5 ;
4. affichage console de :
   - la meilleure recommandation ;
   - ses scores `overall / robustesse / survie / forward` ;
   - un aperçu du classement final.

### Nouveaux artefacts automatiquement générés
Dans `--output-dir` :

- `daily_metrics.csv`
- `summary_metrics.csv`
- `scenarios.csv`
- `metadata.json`
- `scenario_recommendations.csv`
- `recommendation_summary.json`

## 7. Une nouvelle commande CLI dédiée à la relecture d’un run existant
Fichier : `backtesting/cli.py`

J’ai ajouté la commande :

```powershell
python -m backtesting recommend-screener
```

### Pourquoi cette commande est utile
Elle permet d’analyser un diagnostic déjà produit, sans relancer tout le replay PIT.

C’est particulièrement utile quand on veut :

- rejouer uniquement la recommandation sur un `summary_metrics.csv` existant ;
- comparer plusieurs répertoires d’artefacts ;
- refaire l’analyse plus tard à partir d’un run archivé.

### Options disponibles
- `--input-dir`
- `--summary-csv`
- `--daily-csv`
- `--output-dir`
- `--baseline-name`
- `--target-horizon`

### Exemple simple
```powershell
python -m backtesting recommend-screener --input-dir artifacts/screener_diagnostics
```

### Exemple avec chemins explicites
```powershell
python -m backtesting recommend-screener \
  --summary-csv artifacts/screener_diagnostics/summary_metrics.csv \
  --daily-csv artifacts/screener_diagnostics/daily_metrics.csv \
  --target-horizon 20
```

## 8. Ce que recommande réellement la phase 5

La phase 5 ne cherche pas seulement :

- le scénario au meilleur rendement forward brut ;
- ni celui avec la survie maximale ;
- ni celui avec le plus gros univers.

Elle cherche le **meilleur compromis exploitable**.

### Exemple de logique assumée
Un scénario peut être écarté s’il :
- a un excellent `portfolio_excess_return_20d_mean` mais une survie trop faible ;
- ou une survie forte mais une qualité forward médiocre ;
- ou des métriques trop incomplètes pour être jugé robuste.

Cette logique est volontairement plus opérationnelle qu’un simple tri sur une seule colonne du `summary_metrics.csv`.

## Ce que cette phase 5 change vraiment

Avant :
- la phase 4 objectivait les scénarios ;
- mais l’arbitrage final restait encore largement manuel ;
- il fallait lire `summary_metrics.csv` et décider soi-même quel compromis semblait “le meilleur”.

Après :
- le système **classe automatiquement** les scénarios ;
- il **propose explicitement** un meilleur compromis ;
- il distingue :
  - le meilleur compromis global,
  - le meilleur en robustesse,
  - le meilleur en survie,
  - le meilleur en qualité forward,
  - et le scénario le plus sélectif encore viable.

En pratique, cela transforme `summary_metrics.csv` d’un simple tableau de mesures en **outil d’aide à la décision**.

## Limite volontaire de cette phase

Je suis resté volontairement focalisé sur la demande :

**analyser automatiquement les résultats du diagnostic screener pour recommander un compromis robuste**.

Je n’ai pas encore ajouté dans cette phase :

- une séparation bull / bear / range ;
- un découpage par régime de volatilité ;
- une recommandation segmentée par sous-périodes de marché.

La base posée ici permet justement de faire cette évolution ensuite, sans remettre en cause l’API ni les artefacts.

---

## Suite logique

La suite naturelle serait une phase 6 de **robustesse par régime** :

1. segmenter les périodes de marché ;
2. recalculer les recommandations par segment ;
3. mesurer la stabilité du “meilleur compromis” selon le contexte ;
4. identifier les paramètres :
   - globalement robustes,
   - opportunistes,
   - ou trop dépendants d’un seul régime.

Mais à ce stade, la phase 5 apporte déjà une vraie valeur opérationnelle :

**le pipeline sait maintenant lire automatiquement les résultats du diagnostic screener et proposer le scénario le plus équilibré entre robustesse, survie et qualité forward.**
