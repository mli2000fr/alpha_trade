## 1. Objectif

La phase 5 savait recommander un **meilleur compromis global**.
La phase 6 savait déjà nuancer cette lecture par **régime de marché** puis en **cross-régimes**.

Mais il manquait encore une couche très concrète côté usage métier :

> **“Quel scénario dois-je choisir selon l’objectif recherché ?”**

Le besoin visé ici n’est pas seulement analytique, il est opérationnel.
Selon le contexte, on peut vouloir :

- un réglage **robuste** ;
- un réglage **offensif** ;
- un réglage **défensif bear-market** ;
- ou le **meilleur compromis exécutable**.

L’objectif de cette phase 7 est donc d’ajouter une **recommandation adaptative par objectif**, sans refondre le moteur existant.

## 3. Design retenu

## 3.1 Principe général

Plutôt que d’introduire une nouvelle pipeline séparée, la phase 7 **repose sur les briques déjà validées** :

- `recommend_screener_scenarios(...)` pour le scoring phase 5 ;
- `recommend_screener_scenarios_by_regime(...)` pour l’analyse phase 6 ;
- `build_cross_regime_recommendations(...)` pour la robustesse transverse.

L’idée est simple :

- conserver la mécanique d’analyse existante ;
- ajouter une couche d’orchestration qui appelle ce moteur avec des priorités différentes ;
- produire un **résumé par objectif** et des **artefacts dédiés**.

Cela limite le risque, réutilise le code éprouvé et garde la cohérence avec les phases précédentes.

---

## 3.2 Profils d’objectif introduits

Le moteur phase 7 expose 4 profils :

### `robust`
Label affiché : `robuste`

Ce profil privilégie :

- la tenue cross-régimes ;
- le pire cas acceptable ;
- la stabilité globale.

Quand l’analyse phase 6 est disponible, ce profil s’appuie explicitement sur les métriques :

- `cross_regime_overall_score`
- `worst_regime_overall_score`

Sinon, il retombe sur une lecture globale plus robuste via des pondérations renforçant la robustesse.

---

### `offensive`
Label affiché : `offensif`

Ce profil priorise clairement l’upside forward.

Au lieu de se contenter d’un simple `overall_score`, il reconstruit un score d’objectif centré sur :

- `metric_portfolio_forward_quality_score`
- `metric_selector_forward_quality_score`
- `metric_positive_share_score`
- `metric_delta_forward_vs_baseline_score`
- `forward_quality_score`

L’idée est d’identifier le scénario qui paraît le plus agressif / performant en projection forward, même si sa largeur d’exécution est moins favorable.

---

### `bear_defensive`
Label affiché : `défensif bear-market`

Ce profil bascule d’abord sur le sous-ensemble `bear` si ce régime existe.

Il cherche alors le meilleur scénario sur ce sous-univers avec des pondérations davantage orientées :

- survie ;
- robustesse ;
- tenue défensive.

Le classement final valorise notamment :

- `bear_overall_score`
- `bear_survival_score`
- `bear_robustness_score`

En l’absence de régime `bear`, le profil ne casse rien :
il retombe en `global_fallback`.

---

### `executable_compromise`
Label affiché : `meilleur compromis exécutable`

Ce profil vise le scénario le plus facilement transformable en portefeuille cible exploitable.

Le score d’objectif met explicitement l’accent sur :

- `metric_portfolio_survival_ratio_score`
- `metric_selector_to_portfolio_survival_ratio_score`
- `metric_portfolio_target_count_score`
- `metric_success_rate_score`
- `survival_score`

On ne cherche donc pas seulement un scénario “bon sur le papier”,
mais un scénario qui convertit mieux jusqu’au portefeuille final.

## 4. Nouveau moteur phase 7

## Fonction ajoutée
- `recommend_screener_scenarios_by_objective(...)`

### Signature
```python
recommend_screener_scenarios_by_objective(
    summary_metrics,
    *,
    daily_metrics=None,
    summary_metrics_by_regime=None,
    baseline_name=None,
    target_horizon=20,
) -> tuple[pd.DataFrame, dict[str, object]]
```

### Ce que fait cette fonction
Pour chaque objectif :

1. choisit la bonne base d’analyse :
   - globale ;
   - cross-régimes ;
   - sous-ensemble `bear` ;
   - fallback global si nécessaire ;
2. appelle le moteur de recommandation existant avec des pondérations adaptées ;
3. reconstruit si besoin un `objective_score` plus spécifique à l’objectif ;
4. classe les scénarios ;
5. construit un résumé JSON homogène.

## 6. Intégration CLI

Je n’ai pas ajouté une nouvelle commande.
Le choix retenu est volontairement sobre :

- `python -m backtesting diagnose-screener`
- `python -m backtesting recommend-screener`

produisent maintenant automatiquement aussi la phase 7.

- les chemins des nouveaux artefacts phase 7 ;
- un résumé par objectif ;
- un aperçu du classement `scenario_recommendations_by_objective.csv`.

### Pourquoi ce choix
Cela garde :

- une UX inchangée ;
- moins de surface CLI à maintenir ;
- une montée en capacité sans alourdir les usages existants.

## 7. Tests ajoutés / adaptés

Fichier : `tests/test_screener_diagnostics.py`

### Cas couverts
- adaptation par objectif sur un jeu de scénarios où les recommandations diffèrent selon le but ;
- fallback propre si aucun régime `bear` n’est disponible ;
- export correct des artefacts phase 7.

### Point important
Le test principal ne suppose pas que chaque objectif doive obligatoirement avoir un leader différent.

C’est intentionnel :
si un même scénario domine réellement plusieurs dimensions, le moteur doit pouvoir le recommander plusieurs fois.

Le contrat métier de la phase 7 est :

- **un scoring adapté à l’objectif** ;
- pas artificiellement **une diversité forcée**.

## 10. Limites assumées

### 1. Pas de paramètre CLI `--objective`
Cette phase produit toutes les recommandations d’un coup.
C’est suffisant à ce stade.

Si un besoin de sélection explicite apparaît plus tard, on pourra ajouter un filtre CLI sans refondre le moteur.

### 2. Pas de diversité forcée entre objectifs
Un même scénario peut ressortir à la fois :

- robuste ;
- et exécutable ;
- voire parfois offensif.

C’est acceptable tant que cela découle réellement des métriques.

### 3. Le bear-friendly dépend des données `bear`
Si aucune séance `bear` n’existe sur la période, le moteur retombe en fallback global.
C’est un comportement volontaire, explicable et robuste.

## 11. Conclusion

Cette phase 7 complète logiquement les phases précédentes :

- phase 5 : meilleur compromis global ;
- phase 6 : robustesse par régime et cross-régimes ;
- phase 7 : **recommandation adaptative par objectif**.

On obtient maintenant un moteur plus proche d’un vrai usage de calibration :

- il sait toujours classer les scénarios ;
- il sait toujours expliquer pourquoi ;
- mais il sait désormais aussi répondre à la bonne question :

> **“Quel scénario recommander selon ce que je veux réellement privilégier ?”**

C’est une amélioration compacte mais structurante :
**plus opérationnelle, plus lisible, et directement exploitable pour choisir un réglage de screener selon l’intention de déploiement.**
