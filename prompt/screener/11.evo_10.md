## 1. Objectif

La phase 10 avait renforcé le **rattachement run → artefacts** dans le centre de logs de `Backtesting`.

Il restait l’autre axe demandé :

> **permettre d’explorer plusieurs répertoires d’artefacts screener dans l’IHM, avec un historique global transverse et un sélecteur partagé entre vues.**

L’objectif de la phase 11 est donc de ne plus dépendre uniquement du dossier par défaut `artifacts/screener_diagnostics`, mais de permettre :

- la découverte des répertoires screener connus par l’IHM ;
- la sélection d’une source d’artefacts active ;
- la consultation d’un historique global multi-répertoires ;
- la réutilisation de cette sélection dans les pages `Screening` et `Overview`.

---

## 2. Design retenu

## 2.1 Nouveau service d’historique global

J’ai ajouté un nouveau service :

- `ihm/services/screener_artifact_history.py`

Ce service consolide plusieurs sources de répertoires screener :

- le dossier par défaut `artifacts/screener_diagnostics` ;
- les répertoires historisés dans les runs IHM `diagnose-screener` / `recommend-screener` ;
- des répertoires additionnels éventuellement fournis explicitement.

Pour chaque dossier connu, le service construit une entrée normalisée contenant notamment :

- le chemin absolu du répertoire ;
- un label relatif au projet si possible ;
- le nombre de runs IHM associés ;
- le dernier run connu ;
- les tags d’origine (`défaut`, `runs IHM`, `sélection manuelle`) ;
- le snapshot métier calculé via `build_screener_artifact_summary(...)`.

Cela évite de dupliquer la logique métier de lecture des artefacts :

- la phase 10 continue à produire le snapshot structuré par run ;
- la phase 11 ajoute une vue **globale par dossier**.

## 2.2 Enrichissement léger du service screener existant

- conserver en parallèle `updated_at_label` pour l’affichage IHM.

Le contrat existant des phases 8–10 reste intact.

---

## 2.3 Sélection partagée entre `Screening` et `Overview`

Le service d’historique global expose une clé partagée de session Streamlit :

- `ihm_selected_screener_artifacts_dir`

Cette clé permet de garder une source screener cohérente entre les deux vues.

### Concrètement
- sur `Screening`, l’utilisateur choisit un répertoire screener dans la liste détectée ;
- cette sélection est mémorisée dans la session ;
- `Overview` recharge automatiquement la même source ;
- si la sélection courante n’est plus dans l’historique détecté, elle reste tout de même sélectionnable comme entrée explicite.

## 3. Intégration IHM

## 3.1 Page `ihm/pages/screening.py`

Ajout d’un bloc :

- **🗂️ Source d’artefacts screener**

Fonctionnement :

- charge l’historique global des répertoires screener ;
- propose un `selectbox` multi-répertoires ;
- affiche la couverture et la date de mise à jour de la source active ;
- expose un expander :
  - **🗃️ Historique global des répertoires screener**

Ensuite la section :

- **🎯 Recommandations screener par objectif**

lit désormais les artefacts du **répertoire sélectionné**, et non plus uniquement le dossier par défaut implicite.

---

## 3.2 Page `ihm/pages/overview.py`

Ajout d’un bloc :

- **🗂️ Source screener active**

La vue d’ensemble :

- recharge l’historique global ;
- reprend la même sélection partagée que `Screening` ;
- affiche un aperçu de l’historique global dans un expander ;
- charge la calibration screener depuis la source choisie.

Résultat :

- la carte **🎯 Calibration screener** reflète le même dossier que la page `Screening`.

---

## 3.3 Page `ihm/pages/backtesting.py`

La phase 10 montrait déjà un **résumé structuré des artefacts screener par run**.

La phase 11 ajoute en plus un bloc transverse :

- **🗂️ Historique global des artefacts screener**

Ce bloc est distinct du détail par run :

- phase 10 = vue centrée sur le run sélectionné ;
- phase 11 = vue globale sur tous les dossiers screener connus de l’IHM.

Cela permet d’avoir dans la même page :

1. le suivi opérationnel par run ;
2. la cartographie transverse des répertoires screener déjà générés.

## 5. Comportement obtenu

## 5.1 Historique global multi-répertoires

L’IHM sait maintenant lister plusieurs sources screener au lieu d’un seul répertoire implicite.

Chaque entrée d’historique expose des informations directement utiles :

- disponibilité ;
- couverture ;
- date de mise à jour ;
- baseline ;
- nombre de recommandations par objectif ;
- nombre de scénarios ;
- nombre de fichiers ;
- nombre de régimes ;
- nombre de runs IHM associés ;
- dernier run lié ;
- origine de la découverte du dossier.

---

## 5.2 Sélecteur partagé

Le sélecteur de source screener est désormais cohérent entre pages :

- `Screening` pour l’exploration détaillée ;
- `Overview` pour la synthèse dashboard.

Cette cohérence évite le cas où :

- `Backtesting` écrit dans un dossier alternatif ;
- `Screening` reste bloqué sur le dossier par défaut ;
- `Overview` affiche encore un autre snapshot.

---

## 5.3 Compatibilité avec les phases 8–10

La phase 11 ne remplace pas l’existant :

- phase 8 : lecture des recommandations screener dans l’IHM ;
- phase 9 : lancement `diagnose-screener` / `recommend-screener` depuis l’IHM ;
- phase 10 : résumé structuré des artefacts par run dans le centre de logs ;
- phase 11 : historique global par dossier + sélection multi-répertoires partagée.

Le dossier par défaut `artifacts/screener_diagnostics` continue à être pris en charge et reste automatiquement visible dans l’historique.

## 8. Bénéfices obtenus

### 1. L’IHM n’est plus mono-répertoire
Les artefacts screener ne sont plus limités à une seule source implicite.

### 2. Navigation plus cohérente
Le choix du snapshot screener devient un vrai contexte utilisateur partagé entre `Screening` et `Overview`.

### 3. Meilleure lisibilité transverse
On distingue maintenant clairement :

- la lecture par run ;
- la lecture globale par dossier.

### 4. Base solide pour la suite
Cette phase prépare bien des évolutions ultérieures comme :

- filtre par type de run ou statut dans l’historique global ;
- navigateur plus avancé de snapshots screener ;
- sélection manuelle persistée plus explicitement entre sessions ;
- exploration détaillée de plusieurs jeux d’artefacts hors contexte run.

---

## 9. Limites assumées

### 1. La sélection est pour l’instant session-scoped
Elle est partagée entre pages Streamlit dans la session courante, mais pas encore persistée entre redémarrages de l’IHM.

### 2. L’historique global reste centré sur les répertoires connus
Il repose sur :

- le dossier par défaut ;
- les runs IHM historisés ;
- d’éventuels ajouts explicites.

Il ne scanne pas arbitrairement tout le filesystem, ce qui évite le bruit et le coût de découverte.

### 3. La vue reste synthétique
L’objectif est de choisir rapidement une source et d’en comprendre l’état global, pas encore d’explorer exhaustivement tous les CSV d’un dossier.

---

## 10. Conclusion

La phase 11 couvre bien le second axe resté en attente après la phase 10 :

- **historique global d’artefacts screener dans l’IHM** ;
- **sélecteur multi-répertoires partagé**.

On obtient maintenant une boucle utilisateur plus complète :

1. lancer un diagnostic/recommandation screener depuis `Backtesting` ;
2. voir le résumé structuré par run ;
3. retrouver tous les dossiers screener connus dans l’historique global ;
4. sélectionner le snapshot à explorer ;
5. relire la même source dans `Screening` et `Overview`.
