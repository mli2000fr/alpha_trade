## 1. Objectif

La phase 8 exposait déjà les recommandations screener dans l’IHM,
mais la vue restait **consommatrice** des artefacts seulement.

Il manquait l’étape opérationnelle suivante :

> **pouvoir relancer ou recalculer ces artefacts directement depuis Streamlit, sans repasser par le terminal.**

La phase 9 vise donc à intégrer dans l’IHM le déclenchement de :

- `python -m backtesting diagnose-screener`
- `python -m backtesting recommend-screener`

avec la même philosophie que la page backtesting existante :

- lancement en arrière-plan ;
- historique centralisé ;
- logs consultables ;
- réutilisation des composants IHM déjà éprouvés.

## 3. Design retenu

## 3.1 Réutiliser l’infrastructure backtesting existante

Au lieu de créer un runner séparé côté IHM, j’ai prolongé le socle déjà en place :

- `ihm/services/backtesting_runner.py`
- `ihm/services/backtesting_registry.py`
- `ihm/pages/backtesting.py`

C’est le choix le plus propre parce que ces commandes :

- appartiennent déjà au module `backtesting` ;
- ont déjà un registre de runs IHM ;
- ont déjà une logique de logs et d’historisation.

Ainsi, la phase 9 reste cohérente avec l’UX existante.

---

## 3.2 Nouvelles commandes supportées

Le type `BacktestingCommandKind` gère maintenant aussi :

- `diagnose-screener`
- `recommend-screener`

J’ai ajouté deux dataclasses dédiées :

- `DiagnoseScreenerOptions`
- `RecommendScreenerOptions`

### Pourquoi des dataclasses dédiées ?
Parce que ces deux commandes ont des paramètres riches et très différents :

- fenêtre temporelle ;
- mode `oat` / `grid` ;
- limites de scénarios ;
- chemins d’artefacts ;
- baseline explicite ;
- horizon cible.

Les encapsuler séparément évite les options polymorphes mal définies et garde `build_backtesting_command(...)` lisible et testable.

## 4. Intégration IHM

## 4.1 Page `ihm/pages/backtesting.py`

La page expose désormais **4 onglets** :

- `▶️ Backtest`
- `🧱 Backfill scores history`
- `🧪 Diagnose screener`
- `🎯 Recommend screener`

### Onglet `Diagnose screener`
Expose directement les paramètres principaux de la CLI :

- `start`
- `end`
- `limit_days`
- `mode`
- `chunk_size`
- `selection_size`
- `max_positions`
- `screener_workers`
- `max_scenarios`
- `rs_values`
- `range_lookback_values`
- `historical_range_score_values`
- `liquidity_threshold_values`
- `output_dir`

L’IHM affiche aussi la **commande PowerShell reconstruite** avant lancement.

---

### Onglet `Recommend screener`
Expose les paramètres de recalcul léger :

- `input_dir`
- `summary_csv`
- `daily_csv`
- `output_dir`
- `baseline_name`
- `target_horizon`

L’objectif est de pouvoir régénérer rapidement les recommandations sans rejouer le diagnostic complet.

---

## 4.2 Garde-fous opérateur

Comme pour les autres commandes backtesting, j’ai conservé le comportement suivant :

- **un seul run actif par type** ;
- si un `diagnose-screener` est déjà en cours, l’IHM bloque un second lancement ;
- idem pour `recommend-screener`.

Cela évite :

- la collision de deux recalculs concurrents ;
- l’écrasement involontaire des mêmes artefacts ;
- des logs difficiles à interpréter.

---

## 4.3 Compatibilité avec la phase 8

La phase 8 lit par défaut les artefacts sous :

- `artifacts/screener_diagnostics/`

J’ai donc gardé ce dossier comme valeur par défaut côté IHM.

### Conséquence utile
Si l’utilisateur laisse ce répertoire par défaut :

- `diagnose-screener` régénère les artefacts au bon endroit ;
- `recommend-screener` les met à jour au bon endroit ;
- la page `Screening` relit naturellement les artefacts mis à jour.

Autrement dit :

- phase 8 = lecture IHM ;
- phase 9 = relance IHM ;
- les deux s’enchaînent sans couture.

## 8. Bénéfices obtenus

### 1. Boucle complète dans l’IHM
On peut maintenant :

- voir les recommandations screener ;
- relancer leur calcul ;
- consulter les logs ;
- revenir voir le résultat.

### 2. Zéro rupture d’architecture
Aucun nouveau registre parallèle, aucun nouveau runner dédié.

### 3. UX cohérente
Le déclenchement des recalculs utilise exactement le même pattern que le backtest et le backfill.

### 4. Alignement avec la phase 8
Le recalcul peut alimenter directement les vues dashboard déjà exposées.

---

## 9. Limites assumées

### 1. Les formulaires sont sur la page `Backtesting`, pas `Screening`
C’est volontaire :
les commandes appartiennent au domaine `backtesting`, et cela évite de disperser les run controls dans l’IHM.

### 2. Pas de publication automatique multi-répertoires
Le comportement optimal reste d’utiliser `artifacts/screener_diagnostics/` si l’on veut alimenter les pages dashboard.

### 3. Pas encore de résumé artefact par run dans le centre de logs
Les logs/historiques sont bien centralisés, mais on ne présente pas encore un résumé structuré des CSV/JSON screener pour chaque run sélectionné.

---

## 10. Conclusion

La phase 9 fait passer le screener d’une logique :

- **artefacts visibles dans l’IHM** (phase 8)

à une logique complète :

- **artefacts visibles + recalculables depuis l’IHM**.

On obtient maintenant une chaîne opérateur cohérente :

1. lancer `diagnose-screener` depuis Streamlit ;
2. lancer au besoin `recommend-screener` ;
3. suivre les logs dans le centre d’exécution ;
4. relire les recommandations mises à jour dans `Screening` et `Vue d’ensemble`.

C’est une extension compacte mais très utile,
car elle supprime le besoin de repasser par le terminal pour itérer sur la calibration du screener.
