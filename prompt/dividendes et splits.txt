POINTS MÉTIER À COUVRIR
==================================================

### 1) Dividendes cash
Lorsqu’un dividende est détecté ou reçu :
- identifier les positions éligibles à la date ex-dividende / record date selon la stratégie retenue
- calculer le montant dû = quantité éligible × dividende par action
- créditer le cash dans un ledger dédié ou une structure équivalente si le projet n’a pas encore de ledger de cash interne complet
- enregistrer un événement auditable immuable
- rendre l’impact visible pour le reporting et, si pertinent, le risk / portfolio accounting
- ne jamais appliquer deux fois le même dividende

### 2) Splits et reverse splits
Lorsqu’un split est détecté ou reçu :
- ajuster la quantité de la position selon le ratio
- ajuster le prix de revient moyen / cost basis de manière cohérente
- garantir que la valeur économique totale de la position reste inchangée immédiatement après l’opération (hors arrondis explicitement gérés)
- historiser l’ajustement
- ne jamais modifier les trades historiques bruts
- appliquer l’opération de façon idempotente

### 3) Historique prix / données de marché
Le projet utilise déjà Alpaca avec `adjustment="all"`.
La solution doit impérativement traiter ce point proprement pour éviter tout double-ajustement.

Je veux une décision d’architecture explicite et justifiée entre deux stratégies possibles :
- soit conserver l’approche actuelle `adjustment="all"` et utiliser le module corporate actions principalement pour l’audit, la comptabilité portefeuille et la traçabilité
- soit faire évoluer l’ingestion pour stocker aussi une version raw / semi-ajustée, avec application contrôlée des corporate actions en aval

Dans tous les cas :
- ne pas casser les modules existants
- ne pas introduire d’incohérence entre `stock_bars`, `stock_bars_daily`, `risk_management`, `execution_engine` et le reporting
- expliciter la stratégie retenue dans le code et dans la documentation

### Idempotence
L’idempotence est non négociable.
Un même événement corporate action ne doit jamais produire un double crédit cash ni un double ajustement de position.

Prévoir :
- contrainte d’unicité DB
- clé d’idempotence déterministe (par ex. provider + symbol + type + ex_date + ratio/montant)
- logique applicative safe en cas de relance ou retry

### Transactions / robustesse
Le traitement doit être transactionnel autant que possible.
En cas d’échec partiel :
- rollback cohérent
- statut d’échec traçable
- possibilité de rejouer proprement
- aucun effet financier dupliqué

### Logs / audit
Respecter les conventions actuelles :
- `LOGGER = logging.getLogger(__name__)`
- logs structurés
- messages exploitables en production

En plus des tables dédiées, intégrer les événements importants dans `execution_events` si pertinent, ou proposer un audit trail cohérent avec l’écosystème actuel.

RÈGLES DE COHÉRENCE DES DONNÉES

Ces règles doivent être strictement respectées :

1. Ne jamais modifier les trades historiques bruts.

   - fraction de split

   - dividende reçu sur position partiellement vendue autour de l’ex-date

   - correction d’un événement déjà publié par la source
