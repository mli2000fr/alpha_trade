# Sprint 5 — implémentation réalisée

Date : 2026-04-26

Référence : `prompt/execution/6.sprint_4.md`

## 1. Objectif du Sprint 5

Faire évoluer la réconciliation post-run depuis une simple comparaison `targets vs broker_positions` vers une **réconciliation analytique, persistée et actionnable**, en cohérence avec le plan cible.

Le Sprint 5 livré a été volontairement cadré comme un incrément sûr et conservateur :

- comparaison multi-axes de l’état d’exécution ;
- persistance des résultats analytiques par symbole ;
- statuts explicites de décision :
  - `SAFE_AUTO`
  - `MANUAL_REVIEW`
  - `BLOCKED`
- auto-rebalance limité aux seuls cas non ambigus ;
- conservation de la compatibilité du helper legacy `reconcile_targets_vs_broker(...)`.

Principe retenu :

- **on analyse d’abord, on automatise ensuite** ;
- **tout état ambigu reste manuel** ;
- **un manque de protection ou de capacité d’achat bloque l’action automatique** ;
- **le run continue d’être traçable même sans auto-correction**.

## 2.2 Modèle métier : statuts explicites de réconciliation

Fichier modifié : `execution_engine/models.py`

Ajouts principaux :

- `ReconciliationStatus`
- `ExecutionReconciliationResult`

### Statuts introduits

- `SAFE_AUTO` : état clair, auto-action autorisable ;
- `MANUAL_REVIEW` : état ambigu ou nécessitant une validation opérateur ;
- `BLOCKED` : action automatique interdite pour raison de sûreté.

Effet :

- le moteur distingue explicitement les écarts actionnables des écarts à traiter manuellement ;
- la décision automatique n’est plus implicite ni dérivée d’une simple différence de quantité.

## 2.3 Réconciliation multi-axes dans `execution_engine/reconciliation.py`

Fichier modifié : `execution_engine/reconciliation.py`

### Nouvelle logique

Le module introduit `reconcile_execution_state(...)`.

Cette réconciliation compare désormais 5 axes :

1. les `targets` ;
2. les requêtes / ordres ouverts ;
3. les positions internes `execution_positions` ;
4. les positions broker ;
5. les protections ouvertes.

### Règles conservatrices implémentées

Le moteur marque notamment :

- `MANUAL_REVIEW` si un symbole présente encore des ordres en vol ;
- `MANUAL_REVIEW` si un symbole détenu n’est pas dans la cible ;
- `MANUAL_REVIEW` si la position interne diverge de la position broker ;
- `BLOCKED` si une position broker existe sans protection ouverte ;
- `BLOCKED` si un achat correctif dépasserait le buying power disponible ;
- `SAFE_AUTO` uniquement si l’écart est clair, la position cohérente, sans ambiguïté et sans blocage de sûreté.

### Compatibilité conservée

Le helper historique `reconcile_targets_vs_broker(...)` est conservé comme façade de compatibilité, mais il s’appuie désormais sur la nouvelle logique.

Effet :

- la réconciliation devient réellement exploitable côté OMS ;
- les auto-corrections ne partent plus sur des états partiels ou ambigus.

## 2.4 Repository : lecture du contexte et persistance des résultats

### `load_open_reconciliation_order_state(...)`

Agrège les requêtes / ordres encore ouverts par symbole :

- qty buy request ;
- qty sell request ;
- qty buy broker ;
- qty sell broker.

### `load_reconciliation_protection_state(...)`

Agrège les protections ouvertes par symbole à partir des enfants `initial_stop` / `trailing_stop` encore actifs.

### `replace_execution_reconciliation_results(...)`

Remplace les résultats analytiques d’un run/compte, puis insère la nouvelle analyse de réconciliation.

Effet :

- l’executor peut désormais reconstituer un vrai contexte de décision ;
- l’analyse Sprint 5 est persistée de manière simple, déterministe et relisible.

## 2.5 Executor : auto-rebalance limité aux cas `SAFE_AUTO`

Fichier modifié : `execution_engine/executor.py`

### Nouveau flux de phase 8

La phase de réconciliation du run :

1. relit les positions broker ;
2. calcule la réconciliation analytique via `reconcile_execution_state(...)` ;
3. persiste les résultats dans `execution_reconciliation_results` ;
4. alimente les métriques Sprint 5 ;
5. ne soumet des ordres de rebalance que pour les symboles `SAFE_AUTO`.

### Effet direct sur l’auto-rebalance

Avant Sprint 5 :

- tout écart `buy_more` / `sell_excess` pouvait potentiellement être candidat à une correction.

Après Sprint 5 :

- un symbole avec ordre en vol n’est **plus** auto-corrigé ;
- un symbole détenu hors cible reste **manuel** ;
- une position non protégée devient **bloquante** ;
- un achat correctif sans capacité disponible est **bloqué** ;
- seuls les écarts réellement clairs arrivent à `_submit_rebalance_orders(...)`.

C’est le cœur métier du Sprint 5.

## 5. Limites assumées du Sprint 5

Ce sprint pose la **réconciliation sûre V1**, mais ne termine pas toute la couche décisionnelle finale.

Restent notamment :

- une exploitation IHM dédiée de `execution_reconciliation_results` ;
- des règles plus fines pour les ordres broker externes / `unmatched`; 
- la gestion avancée des shorts, reverse positions et cas de lots externes ;
- une éventuelle automatisation dédiée de la remédiation de protections manquantes ;
- le retrait progressif des lectures legacy encore présentes autour de certains flux.

Autrement dit :

> Sprint 5 verrouille la **sûreté de la décision automatique**, mais pas encore toute la supervision fonctionnelle finale.
