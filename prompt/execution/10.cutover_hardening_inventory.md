## 1. Objectif de cette passe hors sprint

Cette passe ne vise pas à retirer immédiatement les derniers résidus legacy, mais à **les inventorier précisément** pour préparer un cutover opérateur propre.

Le périmètre analysé ici est volontairement restreint à :

- **repository execution** ;
- **watcher de protections** ;
- surfaces adjacentes minimales nécessaires pour qualifier le risque opérateur :
  - requêtes IHM `execution`,
  - outillage DB,
  - schéma SQL,
  - documentation.

---

## 2. Méthode de classification

Chaque résidu est classé dans une des catégories suivantes :

### A. Fallback actif
Chemin automatiquement déclenché à l’exécution si la voie canonique ne retourne rien.

### B. Dual-read / dual-write actif
Compatibilité encore réellement vivante dans le flux runtime nominal ou secondaire.

### C. Compatibilité passive
API ou fallback encore présents dans le code, mais qui ne pilotent plus l’IHM canonique ni le run nominal principal tel qu’il est aujourd’hui consommé.

### D. Dette doc / tests / outillage
Dette non critique pour le runtime immédiat, mais qui brouille le cutover, la purge DB ou la lisibilité opérateur.

Priorités utilisées :

- **P0** : à traiter avant un retrait final des tables legacy
- **P1** : à traiter pendant la préparation de cutover / reset DB
- **P2** : dette secondaire, après sécurisation du runtime
