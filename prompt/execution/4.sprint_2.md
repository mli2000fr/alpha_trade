# Sprint 2 — implémentation réalisée

Date : 2026-04-26

Référence : `prompt/execution/3.sprint_1.md`

---

## 1. Objectif du Sprint 2

Poursuivre la refonte du moteur `execution_engine` en introduisant le nouveau modèle de persistance centré sur :

- la requête d’ordre interne (`execution_order_requests`) ;
- l’observation des ordres broker (`execution_broker_orders`) ;
- les fills broker (`execution_broker_fills`) ;
- les snapshots de compte broker (`broker_account_snapshots`) ;
- une idempotence corrigée par séparation entre :
  - clé métier stable ;
  - clé de soumission broker par tentative.

Le principe retenu pour ce sprint est un **dual-write contrôlé** :

- le legacy `execution_orders` / `execution_fills` reste alimenté pour ne pas casser les chemins existants ;
- le nouveau schéma Sprint 2 est désormais alimenté en parallèle sur les flux principaux.

## 2. Changements implémentés

## 2.1 Nouveau schéma SQL Sprint 2

Nouveaux fichiers ajoutés :

- `database/sql/execution/execution_order_requests.sql`
- `database/sql/execution/execution_broker_orders.sql`
- `database/sql/execution/execution_broker_fills.sql`
- `database/sql/execution/broker_account_snapshots.sql`
- `alembic/versions/0009_add_execution_sprint2_persistence.py`

Tables introduites :

### `execution_order_requests`

Historise la décision OMS / moteur :

- `request_id`
- `exec_run_id`
- `account_id`
- `risk_run_id`
- `business_key`
- `submission_key`
- `attempt_no`
- `intent_role`
- `status`
- `failure_reason`
- métadonnées de prix / quantité / parenté

Contraintes clés :

- unicité `(account_id, business_key, attempt_no)`
- unicité `submission_key`

### `execution_broker_orders`

Historise l’ordre broker effectivement observé :

- rattachement à `request_id`
- `broker_order_id`
- `client_order_id`
- `raw_status` / `normalized_status`
- quantité, prix moyen, payload / réponse

### `execution_broker_fills`

Historise les fills broker côté Sprint 2 :

- `fill_id`
- `broker_order_id`
- `request_id`
- `exec_run_id`
- métriques de slippage / shortfall

### `broker_account_snapshots`

Pose les snapshots de capacité broker :

- `exec_run_id`
- `account_id`
- `snapshot_kind`
- `equity`
- `cash`
- `settled_cash`
- `buying_power`
- `daytrade_count`

## 2.3 Idempotence corrigée : clé métier stable vs clé de soumission

Fichier modifié : `execution_engine/order_intents.py`

Changements :

- `idempotency_key` reste la **clé métier stable** ;
- ajout d’une **clé de soumission** (`submission_key`) dérivée de `exec_run_id` ;
- `intent_to_alpaca_payload()` utilise désormais `submission_key` pour `client_order_id`.

Effet :

- deux runs différents peuvent porter la même intention métier sans collision côté broker ;
- chaque tentative broker conserve un identifiant de soumission distinct.

Effet :

## 2.6 Executor branché en dual-write sur le nouveau schéma

Fichier modifié : `execution_engine/executor.py`

Intégrations réalisées :

### Entrées / preflight

- snapshot de compte préflight via `snapshot_broker_account(...)`
- persistance des `execution_order_requests` dès la construction / simulation des intents

### Soumission des ordres d’entrée

- statut request mis à jour en `NEW`, `SIMULATED`, `SUBMITTED`, `REJECTED` ou `FAILED`
- persistance parallèle des ordres broker dans `execution_broker_orders`

### Polling / fills

- persistance des fills dans `execution_broker_fills`
- legacy `execution_fills` conservé en parallèle

### Enfants synthétiques (take-profit / stop / trailing)

- les ordres enfants alimentent aussi :
  - `execution_order_requests`
  - `execution_broker_orders`

### Rééquilibrage automatique

- extension du dual-write Sprint 2 aux ordres de rebalance

Effet :

- le nouveau schéma n’est pas seulement “posé” : il est réellement alimenté sur le chemin opérationnel principal.

## 5. Limites assumées du Sprint 2

Ce sprint ne termine pas encore toute la refonte métier du moteur. Restent notamment :

- la suppression effective du legacy `execution_orders` / `execution_fills` du chemin principal ;
- une reconstruction canonique complète des positions / lots ;
- une lecture IHM totalement migrée sur le nouveau schéma ;
- une réconciliation analytique branchée nativement sur les nouvelles tables ;
- le nettoyage final des chemins historiques.

Autrement dit :

> Sprint 2 introduit la nouvelle persistance et la vraie séparation OMS / broker, mais garde volontairement le legacy en parallèle pour sécuriser la transition.
