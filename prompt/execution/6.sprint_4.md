## 1. Objectif du Sprint 4

Poursuivre la refonte en **consolidant la vérité post-broker** autour du schéma Sprint 2, puis en ajoutant les premiers objets canoniques de détention attendus au plan :

- `execution_positions`
- `execution_position_lots`

Le Sprint 4 livré a été volontairement cadré comme un incrément opérationnel sûr :

- **relecture broker des ordres récents** pour resynchroniser les statuts ;
- **synthèse de fills manquants** à partir du cumul broker quand un ordre connu a progressé ;
- **projection de la position nette courante** par compte / symbole ;
- **reconstruction FIFO des lots** ouverts / fermés à partir des fills observés ;
- conservation de la logique Sprint 3 sans casser les fallbacks legacy déjà en place.

Le principe retenu reste pragmatique :

- **la vérité de position vient d’abord du broker** ;
- **les lots sont reconstruits depuis les fills connus** ;
- **les ordres non résolus côté OMS sont comptés mais n’interrompent pas le run** ;
- l’executor garde un comportement robuste même si la synchro broker échoue ponctuellement.

## 2.4 Nouveau service : synchronisation broker explicite

Fichier ajouté : `execution_engine/broker_state_sync.py`

Nouveau composant : `BrokerStateSynchronizer`

### Rôle

Le service orchestre maintenant un cycle de synchronisation broker explicite :

1. relit les ordres récents broker ;
2. tente de résoudre chaque ordre vers une `execution_order_request` connue ;
3. upsert `execution_broker_orders` avec l’état broker le plus récent ;
4. synthétise un **fill manquant** quand `filled_qty broker > filled_qty déjà historisé` ;
5. relit les positions broker ;
6. alimente `execution_positions` ;
7. reconstruit `execution_position_lots`.

### Synthèse de fills manquants

Le service crée un `ExecutionFill` synthétique quand un ordre connu a progressé côté broker mais qu’aucun journal correspondant n’existe encore localement.

Source de vérité utilisée :

- `filled_qty` cumulatif broker ;
- `avg_fill_price` broker ;
- `updated_at` broker comme horodatage de rattrapage.

Effet :

- les ordres restés en file d’attente puis remplis plus tard redeviennent visibles dans le schéma Sprint 2 ;
- la base locale ne dépend plus uniquement du moment exact du polling initial du run.

### Tolérance aux écarts

Les ordres broker non résolus vers une request OMS :

- sont comptés dans `unmatched_orders` ;
- n’interrompent pas la synchronisation ;
- n’empêchent ni la projection des positions ni la reconstruction des lots connus.

Effet :

- le système reste robuste pendant la transition ou en présence d’ordres externes / historiques.

## 5. Limites assumées du Sprint 4

Ce sprint ne termine pas encore toute la refonte canonique des positions.

Restent notamment :

- un vrai endpoint / journal broker de fills unitaires si l’on veut dépasser le rattrapage par delta cumulatif d’ordre ;
- la gestion avancée des cas d’ordres externes non résolus côté OMS ;
- la couverture des scénarios complexes de short / reverse / lots externes ;
- une exploitation plus large de `execution_positions` / `execution_position_lots` dans les autres vues métier et réconciliations analytiques ;
- le retrait final des mécanismes legacy restants.

Autrement dit :

> Sprint 4 pose la **vérité courante exploitable** sur positions et lots, mais pas encore la comptabilité exhaustive de tous les cas broker possibles.

---

## 6. Recommandation immédiate pour la suite

La suite logique est un **Sprint 5** orienté consolidation analytique et retrait progressif du legacy, par exemple dans cet ordre :

1. enrichir la synchro broker avec une source de fills plus granulaire si disponible ;
2. traiter explicitement les écarts `unmatched_orders` / lots externes ;
3. brancher la réconciliation métier sur `execution_positions` plutôt que sur des snapshots bruts ;
4. exploiter `execution_position_lots` pour les vues d’audit et de PnL ;
5. réduire progressivement les lectures legacy restantes (`execution_orders`, `execution_fills`).
