# Sprint 3 — implémentation réalisée

Date : 2026-04-26

Référence : `prompt/execution/4.sprint_2.md`

---

## 1. Objectif du Sprint 3

Poursuivre la refonte en **basculant progressivement les lectures métier** du legacy vers le schéma Sprint 2, sans casser les usages existants.

Le Sprint 3 livré s’est concentré sur trois axes à forte valeur :

- lecture des protections / enfants pour le watcher et l’OCO ;
- lecture IHM des ordres, fills, contraintes et targets ;
- maintien d’une **compatibilité transitoire** avec le legacy quand nécessaire.

Le principe retenu reste pragmatique :

- **lecture v2 prioritaire** ;
- **fallback legacy court terme** quand le nouveau schéma n’est pas encore alimenté ou lorsqu’un flux historique subsiste ;
- alignement du watcher pour qu’il continue lui aussi à nourrir le schéma Sprint 2.

---

## 2. Changements implémentés

## 2.1 Repository : lectures v2 ajoutées et compatibilité transitoire

Fichier modifié : `execution_engine/db_io.py`

### `load_open_child_orders(...)`

Cette méthode ne lit plus uniquement `execution_orders`.

Elle lit désormais :

- `execution_order_requests`
- `execution_broker_orders`

puis **fusionne** le résultat avec le legacy `execution_orders` pour éviter les trous pendant la transition.

Effet :

- l’OCO et le watcher voient les enfants déjà migrés ;
- les enfants encore historisés côté legacy restent visibles ;
- les runs mixtes Sprint 2 / legacy restent opérables.

### `load_pending_protection_watch_items(...)`

Cette lecture est maintenant basée en priorité sur :

- `execution_order_requests`
- `execution_broker_orders`
- `execution_broker_fills`
- `execution_targets_snapshot`
- `execution_runs`

avec fallback sur la requête legacy précédente si aucun résultat v2 n’est trouvé.

Effet :

- le watcher relit désormais le contexte de protection depuis le modèle Sprint 2 ;
- le prix de fill, la quantité, le stop initial et les paramètres de risque proviennent prioritairement des nouveaux objets ;
- le comportement reste robuste tant que certains historiques legacy existent encore.

---

## 2.2 Watcher : alignement d’écriture sur Sprint 2

Fichier modifié : `execution_engine/protection_watcher.py`

Le watcher ne persistait jusque-là que le legacy lors de ses transitions post-run.

Il alimente désormais aussi :

- `execution_order_requests`
- `execution_broker_orders`

via `upsert_execution_order_request_from_intent(...)` et `upsert_execution_broker_order(...)`.

### Correction importante

Le watcher reconstruit maintenant explicitement **le stop initial existant** avec l’`intent_id` d’origine (`initial_stop_intent_id`) avant persistance.

Effet :

- on évite de créer un faux nouvel identifiant de stop lors de la relecture/promotion ;
- les transitions watcher deviennent compatibles avec les nouvelles lectures IHM et repository ;
- les trailing stops soumis par le watcher deviennent visibles dans le schéma Sprint 2.

---

## 2.3 IHM : lectures basculées vers le nouveau schéma

Fichier modifié : `ihm/services/queries.py`

### `get_execution_orders(...)`

Lecture v2 prioritaire via :

- `execution_order_requests`
- `execution_broker_orders`
- agrégat de `execution_broker_fills`

avec colonnes projetées pour rester compatibles avec l’écran existant (`intent_id`, `parent_intent_id`, `qty`, `status`, etc.).

Fallback conservé sur `execution_orders` si la lecture v2 ne renvoie rien.

### `get_execution_fills(...)`

Lecture v2 prioritaire via `execution_broker_fills`, avec alias `request_id AS intent_id` pour préserver la compatibilité d’affichage.

Fallback conservé sur `execution_fills`.

### `get_execution_account_constraints(...)`

La fonction lit toujours l’événement `ACCOUNT_CONSTRAINT_APPLIED` en priorité.

Si cet événement n’est pas disponible, elle retombe maintenant sur `broker_account_snapshots` (`snapshot_kind='preflight'`) et reconstruit un payload exploitable.

Effet :

- l’écran reste explicatif même si seul le snapshot compte est disponible ;
- la dépendance à l’événement legacy est réduite.

### `get_execution_targets_snapshot(...)`

Nouvelle requête IHM dédiée à `execution_targets_snapshot`.

Effet :

- l’IHM peut afficher les **targets réellement consommées par le run**, et non seulement les targets source du `risk_run_id`.

### `get_execution_runs(...)`

La requête expose maintenant aussi :

- `execution_profile`
- `submission_window`
- `account_id`

pour enrichir le suivi opérateur.

---

## 2.4 Page Execution : affichage aligné sur les snapshots du run

Fichier modifié : `ihm/pages/execution.py`

Changements :

- affichage du `execution_profile`, de la `submission_window` et du `account_id` du run ;
- affichage prioritaire du **snapshot des cibles consommées** via `get_execution_targets_snapshot(...)` ;
- fallback sur `get_portfolio_targets(run_id=...)` seulement si le snapshot du run est absent.

Effet :

- la page devient plus fidèle au run réellement exécuté ;
- la traçabilité du run est meilleure en cas de rerun ou de changement des targets source après coup.

Le Sprint 3 est maintenant **implémenté dans le code** avec un résultat concret sur la migration des lectures métier :

- le watcher et l’OCO peuvent relire les enfants depuis le nouveau schéma ;

> les principaux consumers métier commencent réellement à **consommer** le modèle `request → broker order → broker fill → account snapshot → target snapshot`.

## 5. Limites assumées du Sprint 3

Ce sprint ne termine pas encore toute la refonte du moteur.

Restent notamment :

- la suppression effective du legacy `execution_orders` / `execution_fills` du chemin principal ;
- une migration plus large des autres lectures métier éventuelles vers le schéma v2 ;
- la refonte canonique des positions / lots ;
- la réconciliation analytique complète appuyée sur les nouveaux objets ;
- le retrait final des fallbacks legacy.

Autrement dit :

> Sprint 3 fait passer les **consommateurs critiques** sur le nouveau schéma, mais garde volontairement des béquilles legacy pour une transition maîtrisée.
