## 2. Résumé exécutif

Le module `execution_engine` est déjà **bien structuré pour un prototype avancé / pré-production** : séparation claire config / modèles / broker / repository / watcher, documentation abondante, logique métier explicite, tests unitaires présents, instrumentation métier correcte.

En revanche, **dans sa forme actuelle, il n’est pas encore au niveau “production professionnel” pour ton cas réel** :

- swing trading US,
- données **daily**,
- détention **cash principalement**,
- pas d’achat/vente pendant le marché ouvert,
- reset complet des tables possible,
- priorité à la **sûreté opératoire** et à la **traçabilité**, pas à la rétrocompatibilité.

### Conclusion courte

Le point le plus important est stratégique :

> Le moteur actuel est encore pensé comme un OMS semi-intraday capable de poller des fills, armer des enfants après fill et faire évoluer des protections via un watcher pendant la session.

Or ton cadre métier est plutôt :

> **OMS overnight / next-session / end-of-day**, déterministe, simple, très traçable, avec le moins possible de mutations en séance.

Je recommande donc **une refonte ciblée du modèle d’exécution**, pas un simple patch local.

## 4. Constats critiques et recommandations

## P0 — Écart stratégique avec ton style de trading

### Constat

Le moteur est calibré pour soumettre/poller/exécuter autour de l’ouverture et pendant la session :

- `run_execution.py` met `allow_outside_rth=False` par défaut en `paper` et `live`
- `ProductionExecutor.execute_run()` avorte si le marché est fermé et `allow_outside_rth=False`
- après fill, `_submit_children()` soumet les protections
- `protection_watcher.py` peut annuler un stop initial et soumettre un trailing stop **pendant la séance**

### Pourquoi c’est un vrai problème

Tu as explicitement indiqué :

- **swing trade uniquement**
- **pas d’achat/vente pendant marché ouvert**

Le watcher et une partie du moteur entrent en tension directe avec cette règle, car ils reviennent à **modifier la structure d’ordres pendant la session**.

### Recommandation

Créer un **mode d’exécution canonique overnight-only** et en faire le mode par défaut pour ton usage.

#### Cible recommandée

- soumission des ordres uniquement en fenêtre **post-close** ou **pre-open** ;
- aucune mutation d’ordres en séance sauf exécution broker-side automatique ;
- protections recalculées et replacées **au prochain run hors séance** ;
- le watcher de trailing dynamique devient :
  - soit **désactivé par défaut**,
  - soit réservé à un profil “intraday-enabled”,
  - soit supprimé du chemin critique.

### Décision d’architecture que je recommande

Pour ton use case, la version la plus robuste est :

1. **entrée** hors séance ;
2. **stop initial** et **take profit** posés broker-side si possible dans la même logique de protection ;
3. **pas de trailing dynamique intraday** ;
4. **rebasage quotidien des stops** au prochain cycle pipeline, à partir de données daily.

C’est beaucoup plus cohérent avec une stratégie swing daily que le couple `executor + watcher` actuel.

## P0 — Idempotence et relance de run dangereuses

### Constat

La logique de déduplication est incohérente entre code et schéma :

- `order_intents._idempotency_key()` produit une clé stable basée sur `risk_run_id + symbol + role + side + qty + broker_mode`
- `execution_orders.idempotency_key` est `UNIQUE`
- mais `ExecutionRepository.load_submitted_idempotency_keys()` filtre **par `exec_run_id`**
- et `executor.py` vérifie les doublons avec `load_submitted_idempotency_keys(exec_run_id)`

### Conséquence

Un rerun sur le même `risk_run_id` n’est pas géré proprement :

- le moteur ne voit pas les doublons des runs précédents ;
- le `UNIQUE` DB les voit ;
- l’`upsert` peut alors écraser / réutiliser une ligne d’un run antérieur au lieu de produire un comportement explicitement contrôlé.

C’est un **risque P0** de traçabilité et d’intégrité.

### Recommandation

Après reset de schéma, séparer clairement :

- **la décision d’ordre stable** (`order_key`, stable par cible/rôle) ;
- **la tentative de soumission** (`attempt_id`, unique par run/essai) ;
- **l’ordre broker réel** (`broker_order_id`) ;
- **le fill broker réel** (`broker_fill_id` si dispo, sinon surrogate key technique).

#### Règle cible

- un rerun doit être un **nouvel attempt**, jamais un overwrite silencieux ;
- la déduplication doit être faite sur `(account_id, risk_run_id, symbol, role)` ou équivalent métier ;
- la persistance doit garder **l’historique complet des tentatives**, pas seulement le dernier état écrasé.

## P0 — Isolation multi-comptes incomplète

### Constat

Le projet supporte le multi-comptes en surface, mais `execution_engine` n’est pas isolé de bout en bout.

Points précis :

1. `ExecutionRepository.load_portfolio_targets()` ne filtre pas `portfolio_targets.account_id`.
2. Le chargement du “dernier run” est basé sur `created_at`, sans scope par compte.
3. `load_pending_protection_watch_items()` joint `portfolio_targets` sur `(run_id, symbol)` sans `account_id`.
4. Les tables `execution_orders`, `execution_fills`, `execution_events` n’ont pas de colonne `account_id`.

### Risque

Avec plusieurs comptes :

- le mauvais portefeuille peut être exécuté ;
- des protections peuvent être rattachées à la mauvaise source ;
- les analyses IHM / audit deviennent ambiguës ;
- les futures contraintes par compte sont plus complexes que nécessaire.

### Recommandation

Sur schéma neuf, faire de `account_id` une dimension **canonique** partout :

- `execution_runs`
- `execution_orders`
- `execution_fills`
- `execution_events`
- `broker_positions_snapshots`
- futures tables positions / lots / account snapshots

#### Règle

Chaque lecture métier critique du moteur d’exécution doit être filtrée par :

- `account_id`
- `trade_date` ou `risk_run_id`
- éventuellement `exec_run_id`

Jamais par “dernier run global” non scoped.

## P0 — OCO logique conçu mais non branché au flux réel

### Constat

`execution_engine/oco_manager.py` existe, mais `check_and_cancel_sibling()` n’est pas utilisé dans `executor.py` ni dans `protection_watcher.py`.

### Conséquence

Le système affirme gérer un OCO synthétique, mais en pratique le code ne démontre pas que :

- si le TP est exécuté, le stop sibling est annulé ;
- si le stop est exécuté, le TP sibling est annulé.

C’est un **trou de sûreté majeur**.

### Recommandation

Choisir explicitement une des deux voies :

#### Option A — simplification recommandée pour ton contexte

Abandonner l’OCO synthétique complexe et utiliser un modèle de protection **plus simple, plus daily, plus robuste**.

#### Option B — si OCO synthétique conservé

Créer un vrai cycle de vie :

- scan des ordres enfants actifs ;
- détection d’un child `FILLED` ;
- annulation atomique/compensée du sibling ;
- persistance d’un état `protection_state` clair ;
- test d’intégration complet sur ce scénario.

## P1 — Le watcher dynamique est en partie du code mort et crée une ambiguïté d’architecture

### Constat

Dans `executor.py`, la méthode `_maybe_activate_dynamic_trailing()` existe, expose des métriques dédiées, mais n’est jamais appelée.

### Conséquence

Le système porte **deux visions concurrentes** :

- trailing dynamique potentiellement géré dans l’executor ;
- trailing dynamique finalement géré dans le watcher ;
- plus un `watcher.md` qui présente encore ce comportement comme important.

### Recommandation

Supprimer cette ambiguïté.

Pour ton contexte, je recommande :

- **retirer le trailing dynamique du cœur de l’OMS** ;
- faire du watcher un composant optionnel non critique ;
- ou supprimer complètement ce mécanisme si tu veux une discipline strictement hors séance.

## P1 — Le modèle de positions est insuffisant pour un moteur sérieux

### Constat

Le module s’appuie surtout sur :

- `broker_positions_snapshots`
- `portfolio_targets`
- `execution_orders`
- `execution_fills`

Il n’existe pas de **position canonique interne** ni de **lot management**.

### Pourquoi c’est insuffisant

Pour un moteur d’exécution professionnel, il faut pouvoir reconstruire proprement :

- position courante,
- taille résiduelle par lot,
- prix de revient,
- fills partiels,
- historique de réduction / sortie,
- exposition réellement protégée.

### Recommandation

Créer après reset :

- `execution_positions`
- `execution_position_lots`
- `broker_account_snapshots`
- éventuellement `execution_protection_states`

#### Minimum canonique recommandé

`execution_positions`
- `account_id`
- `symbol`
- `net_qty`
- `avg_cost`
- `opened_at`
- `updated_at`
- `source_exec_run_id`
- `status`

`execution_position_lots`
- `lot_id`
- `account_id`
- `symbol`
- `open_fill_id`
- `open_qty`
- `remaining_qty`
- `open_price`
- `opened_at`
- `closed_at`
- `status`

Cela simplifiera énormément la réconciliation, les corporate actions et l’audit.

## P1 — Gestion des fills trop pauvre pour du réel

### Constat

Le modèle courant enregistre essentiellement un fill “agrégé par ordre terminal” :

- `_poll_until_terminal()` attend un état terminal ;
- `_build_fill()` construit un `ExecutionFill` unique ;
- `execution_fills` n’est pas un vrai journal d’exécutions broker fines.

### Limites

Tu perds ou simplifies à l’excès :

- partial fills successifs,
- timestamps réels de chaque exécution,
- prix moyen évolutif,
- analytique TCA plus précise,
- reconstitution fiable de la position.

### Recommandation

Passer à un modèle à deux niveaux :

- `broker_orders` = état de l’ordre broker ;
- `broker_fills` = exécutions unitaires ou snapshots d’exécution successifs.

Même si Alpaca ne fournit pas toujours un fill granulaire parfait via ce chemin, il faut au minimum modéliser :

- `last_seen_filled_qty`
- `last_seen_avg_fill_price`
- `observed_at`
- état broker brut

## P1 — Réconciliation trop naïve

### Constat

`reconciliation.py` compare essentiellement `target_qty` vs `broker_qty`.

### Ce qui manque

La réconciliation ne tient pas compte de :

- ordres déjà soumis mais non encore exécutés,
- positions en cours d’ouverture,
- partial fills,
- protections ouvertes,
- positions hors cible mais volontairement conservées,
- cash réellement engagé.

### Risque

Le mode `auto_rebalance_on_reconcile` peut générer des corrections intempestives.

### Recommandation

Refondre en deux étages :

1. **reconciliation analytique** :
   - target
   - internal position
   - broker position
   - open orders
   - pending protections

2. **reconciliation actionnable** :
   - seulement si la situation est non ambiguë
   - sinon statut `MANUAL_REVIEW`

Pour un usage swing/cash, il vaut mieux **moins d’automatisme** mais plus de certitude.

## P1 — Séquence de soumission des protections non optimale

### Constat

Dans `_submit_children()`, le moteur soumet :

1. take profit,
2. puis protection (`initial_stop` ou fallback trailing).

### Problème

En cas d’échec de la jambe de protection, tu peux te retrouver avec :

- un TP posé,
- mais pas de stop valide.

Pour un moteur professionnel, la priorité doit être **risk-first**.

### Recommandation

Inverser la logique cible :

1. stop initial validé,
2. puis take profit.

Ou, encore mieux pour ton contexte :

- protection simple et cohérente d’abord,
- sophistication éventuelle seulement ensuite.

## P1 — Les snapshots broker ne capturent pas l’état “flat”

### Constat

`ExecutionRepository.snapshot_broker_positions()` retourne immédiatement si `positions` est vide.

### Conséquence

Quand le portefeuille est complètement soldé :

- aucun snapshot n’est écrit ;
- l’IHM peut continuer à montrer un ancien état ;
- on perd la preuve qu’on est réellement flat.

### Recommandation

Toujours écrire un snapshot de compte, même si aucune position n’existe.

Au minimum :

- une table `broker_account_snapshots`
- et/ou un enregistrement “flat portfolio” explicite.

---

## P1 — Persistance événementielle trop fragile

### Constat

La plupart des événements sont accumulés en mémoire puis persistés en fin de run via `_persist_events()`.

### Risque

En cas de crash brutal :

- une partie de l’audit peut être perdue ;
- l’analyse post-mortem devient incomplète.

### Recommandation

Persister immédiatement les événements critiques :

- `RUN_STARTED`
- `PRECHECK_FAILED`
- `ORDER_SUBMITTED`
- `ORDER_REJECTED`
- `ORDER_FILLED`
- `RUN_FAILED`
- événements de protection

Le buffering ne doit servir qu’aux événements secondaires.

---

## P1 — Absence de verrou d’exécution par compte / run

### Constat

Je n’ai pas trouvé de mécanisme fort empêchant :

- deux runs `execution` simultanés sur le même `account_id`,
- deux watchers actifs en concurrence sur les mêmes protections.

### Recommandation

Ajouter un verrou canonique :

- soit DB (`execution_locks`),
- soit verrou advisory MySQL,
- soit statut atomique “active run” par `account_id`.

Pour la prod, c’est indispensable.

---

## P2 — Le module ne capitalise pas assez sur le fait que ton univers est daily

### Constat

Tu peux avoir 10 ans de données par symbole, mais l’execution engine n’est pas un problème de volumétrie extrême ; c’est d’abord un problème de **cohérence métier**.

### Conséquence

Il ne faut pas sur-investir dans la sophistication intraday si ton edge est daily.

### Recommandation

Le moteur doit privilégier :

- déterminisme,
- auditabilité,
- simplicité de replay,
- robustesse en dehors des heures de marché,
- alignement exact avec les sorties de `risk_management`.

Bref : **moins EMS intraday, plus OMS daily propre**.

## 5.3 Règles métier cibles

### Profil recommandé par défaut : `overnight_cash_swing`

- soumission hors séance uniquement ;
- aucun ajustement d’ordre en RTH ;
- pas de watcher intraday dans le chemin nominal ;
- réconciliation au run suivant ;
- priorité à la maîtrise du cash settled ;
- ordre d’exécution déterministe par `decision_rank`.

### Politique de protection recommandée

#### Option la plus robuste

- `initial_stop` broker-side simple
- `take_profit` broker-side simple
- rebase des niveaux une fois par jour hors séance

#### Option à éviter par défaut

- trailing dynamique géré par watcher intraday

Elle est plus fragile, plus complexe, et moins alignée avec ton style.

## 9. Synthèse ultra-courte

- Le module est bien organisé, mais encore trop orienté exécution/pilotage intraday.
- Pour ton style swing daily cash, il faut un moteur **overnight-only**, simple et déterministe.
- Les principaux risques actuels sont :
  - idempotence de rerun,
  - isolation multi-comptes incomplète,
  - OCO non réellement branché,
  - modèle de positions trop faible,
  - watcher intraday en tension avec ta discipline de trading.
- Comme tu repars d’une base saine, c’est le bon moment pour faire une **refonte propre du schéma execution**.
