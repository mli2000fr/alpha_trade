## 1. Objectif

Mettre en œuvre la première passe **concrète** de cutover runtime identifiée dans l’inventaire P0 :

- retirer les fallback actifs encore branchés sur `execution_orders` / `execution_fills` ;
- retirer les dual-writes runtime encore actifs depuis l’executor et le watcher ;
- conserver le flux nominal sur le modèle canonique :
  - `execution_order_requests`
  - `execution_broker_orders`
  - `execution_broker_fills`

---

## 2. Changements appliqués

## 2.1 `execution_engine/db_io.py`

### `load_submitted_idempotency_keys(...)`

Bascule de la lecture legacy :

- avant : `execution_orders.idempotency_key`
- maintenant : `execution_order_requests.business_key`

### `load_open_child_orders(...)`

Suppression du dual-read V2 + legacy :

- avant : fusion `execution_order_requests` + `execution_orders`
- maintenant : lecture **V2-only** depuis `execution_order_requests` + `execution_broker_orders`

### `load_pending_protection_watch_items(...)`

Suppression du fallback actif :

- avant : fallback automatique vers `_load_pending_protection_watch_items_legacy(...)`
- maintenant : lecture **canonique seule**

Effet : le watcher ne rebascule plus automatiquement vers `execution_orders` / `execution_fills` / `portfolio_targets` si la voie canonique est vide.

---

## 2.2 `execution_engine/executor.py`

Suppression des dual-writes runtime legacy :

- suppression des appels à `upsert_execution_order(...)`
- suppression des appels à `insert_execution_fill(...)`
- simplification de `_persist_child_order_state(...)`
- nettoyage équivalent sur les rebalance orders

Effet :

- l’executor ne nourrit plus `execution_orders`
- l’executor ne nourrit plus `execution_fills`
- la persistance runtime passe uniquement par :
  - `execution_order_requests`
  - `execution_broker_orders`
  - `execution_broker_fills`

---

## 2.3 `execution_engine/protection_watcher.py`

Suppression de l’écriture legacy `execution_orders` dans `_persist_order_state(...)`.

Le watcher persiste désormais uniquement :

- `execution_order_requests`
- `execution_broker_orders`
- `execution_events`
- `run_business_summaries`

Effet :

- le runtime secondaire ne maintient plus la table legacy `execution_orders`
- la promotion stop initial → trailing reste opérée, mais sur la persistance canonique seule
