## Objectif
Créer une IHM interne opérateur pour `alpha_trade`, basée sur **Streamlit**, dans le dossier `ihm/`, adaptée au workflow réel du projet.

L'IHM doit être un **dashboard opérateur de supervision**, pas un simple écran marketing.

## Contraintes fonctionnelles
Le projet suit ce pipeline métier quotidien (ordre strict) :
1.  `import_alpaca_bar`        → stock_bars
1a. `corporate_actions sync`   → corporate_actions_events
2.  `data_sanitizer_daily`     → stock_bars_daily
3.  `stock_screener`           → stock_scores
4.  `alpha_scanner`            → stock_scores (update)
5.  `sentiment_pipeline`       → ticker/sector feats
6.  `signal_aggregator`        → final_score_sentiment
7.  `run_risk`                 → portfolio_targets
8.  `run_execution`            → ordres Alpaca
8a. `corporate_actions apply`  → position adjustments

⚠️ `corporate_actions sync` se fait AVANT le sanitizer (référentiel).
⚠️ `corporate_actions apply` se fait APRÈS l'exécution (ajuste les positions existantes).

L'IHM doit permettre à un opérateur de :
- voir l'état global du système
- suivre les runs de risque et d'exécution
- consulter les candidats et scores
- consulter les décisions de risque
- voir le portefeuille cible
- suivre les événements d'exécution
- suivre les positions broker
- suivre les corporate actions (sync et apply séparément)
- diagnostiquer l'environnement et les dépendances

## Choix technique imposé
Implémente une IHM **Streamlit** robuste et modulaire.

## Exigences de conception

### 1. Lecture seule par défaut
- aucune action destructive
- pas de lancement live implicite
- si des boutons d'action existent, ils doivent être clairement désactivés, protégés, ou limités à des commandes sûres

### 2. Réutilisation du code existant
- réutiliser `database.connection.get_sqlalchemy_engine()` pour la connexion DB
- créer une couche de services IHM dédiée (`ihm/services/`) pour les requêtes
- ne pas dupliquer inutilement la logique métier des modules existants

### 3. Robustesse
- si la DB est indisponible, afficher une erreur utilisateur claire sans crash
- si une table manque, afficher un warning et une page vide exploitable
- si certaines colonnes n'existent pas selon la version du schéma, gérer un fallback
- aucune page ne doit planter totalement
- wrap chaque requête DB dans try/except

### 4. Imports propres
- ajouter `ihm/__init__.py` et `ihm/pages/__init__.py`
- utiliser des imports absolus cohérents
- l'application doit être lancée avec :
  `python -m streamlit run ihm/app.py`
- ne PAS supposer que `python ihm/app.py` suffit (ScriptRunContext manquant)
- ne PAS faire `from ihm import ...` dans app.py (le package lui-même n'est pas installé)
- utiliser des imports relatifs dans les sous-modules ihm si nécessaire

### 5. Qualité UX
- sidebar avec navigation claire
- affichage des statuts via badges colorés (🟢 🟡 🔴)
- filtres utiles
- tableaux lisibles avec st.dataframe
- métriques résumées en haut de page (st.metric)
- messages d'aide métier explicites
- empty states propres ("Aucune donnée disponible")

## Pages attendues

### 1. Vue d'ensemble (overview)
Afficher :
- état des variables d'environnement critiques (`LOGIN_DB`, `PASSWORD_DB`, `ALPACA_API_KEY`, `ALPACA_SECRET_KEY`, optionnellement `FINNHUB_API_KEY`) avec masquage (4 chars + ****)
- santé DB (test connexion)
- dernière date de données / dernier run
- dernier `risk_run_id` et `exec_run_id`
- nombre de candidats actuels (`is_candidate=1`)
- top 10 symboles par `final_score_sentiment`
- alertes : pas de candidats, DB indisponible, dernière exécution en échec

### 2. Pipeline
Afficher une vue séquentielle du pipeline métier (10 étapes) :
Pour chaque étape :
- numéro et nom
- description courte
- tables impactées
- commande CLI associée
- dépendances amont

### 3. Screening
Lire `stock_scores` et afficher :
- `symbol`, `sector`, `is_candidate`, `total_score`, `final_score`, `final_score_sentiment`
- `trend_score`, `vcp_score`
- `signal_active`, `total_news`
- `anomaly_count`, `missing_days_count`
- dates de mise à jour (`last_updated_score`, `last_updated_scan`, `last_updated_sentiment`)

Filtres :
- symbole (text_input)
- secteur (selectbox)
- candidats uniquement (checkbox)
- score minimum (slider)
- sentiment actif uniquement (checkbox)

### 4. Risk
Lire `risk_decisions` et `portfolio_targets` :
- tableau des décisions avec filtre par run_id
- décisions ACCEPTED / REDUCED / REJECTED avec couleur
- `score_used`, `conviction_score`, `predicted_proba`, `historical_win_rate`
- `sizing_method`, `kelly_fraction`, `target_weight`
- raison de rejet
- synthèse par secteur (barres ou tableau)
- portefeuille cible du dernier run

### 5. Execution
Lire :
- `execution_runs` (statut, targets, submitted, filled, erreurs)

Afficher :

### 6. Corporate Actions

Afficher :

### 7. ML / Predictions
Lire si présentes :
- `model_training_run` (status, symboles, dates)
- `model_metrics` (accuracy, precision, recall, AUC)

Afficher :
- résumé des runs
- métriques par symbole

Afficher :
- variables d'environnement masquées

- dépendances critiques (streamlit, sqlalchemy, pandas, pymysql)
