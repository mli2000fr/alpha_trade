# Evolution 4 — Priorité 3 implémentée

## Objectif
Cette note archive l’implémentation de la **priorité 3** dans `modelFactory` :

1. ajout de **features cross-sectionnelles PIT-safe** ;
2. chargement d’un **panel univers minimal** depuis l’historique des barres ;
3. fusion par `(symbol, date)` dans la préparation des données ;
4. support de ces features en **training** et en **inférence** ;
5. journalisation minimale des **colonnes et diagnostics cross-sectionnels** dans les artefacts.

Le principe retenu a été volontairement pragmatique :
- pas de snapshot externe ;
- pas de dépendance à un historique de secteurs non garanti ;
- calcul uniquement depuis les **barres historiques disponibles** ;
- design **désactivé par défaut** ;
- compatibilité conservée avec le pipeline existant.

# 3. Logique PIT-safe retenue

## 3.1 Source des données
Les features cross-sectionnelles sont calculées uniquement depuis :
- les barres historiques de l’univers ;
- le benchmark historique si disponible.

Aucune donnée “snapshot courant” n’est utilisée.

## 3.2 Logique de calcul
Pour chaque symbole de l’univers, le module calcule d’abord des séries internes :
- momentum 20 jours ;
- momentum 60 jours ;
- volatilité rolling 20 jours ;
- dollar volume rolling 20 jours ;
- volume ratio 20 jours ;
- position dans le range 20 jours ;
- force relative 20/60 jours vs benchmark si disponible.

Ensuite, pour chaque date, ces valeurs sont transformées en **ranks percentiles intra-univers**.

## 3.3 Gestion du minimum d’univers
Si une date a un nombre de symboles strictement inférieur à `cross_sectional_min_universe` :
- les ranks de cette date sont mis à une valeur neutre `0.5`

### Pourquoi ce choix
C’est un compromis robuste pour une V1 :
- on évite de produire des ranks trompeurs sur un univers trop petit ;
- on ne casse pas le pipeline en introduisant des `NaN` partout ;
- on garde une sémantique neutre pour les jours peu fiables.

# 4. Chargement de l’univers historique

## 4.1 Nouveau loader `load_universe_bars()`
Dans `modelFactory/data_loader.py`, une nouvelle fonction a été ajoutée :
- `load_universe_bars(engine, symbols=None, end_date=None)`

### Comportement
Elle charge depuis `stock_bars_daily` :
- l’ensemble des colonnes nécessaires au calcul des features cross-sectionnelles ;
- filtrées éventuellement par liste de symboles ;
- filtrées éventuellement par `end_date`.

### Pourquoi c’est important
Le cross-sectionnel a besoin d’un **panel historique**, pas d’une série mono-symbole.
Cette fonction formalise cette brique.

# 5. Intégration dans le dataset

## 5.1 `get_feature_columns()` étendu
Dans `modelFactory/features.py`, `get_feature_columns()` accepte maintenant :
- `include_cross_sectional: bool = False`

Cela permet au pipeline de construire dynamiquement la bonne liste de features,
notamment pour :
- le scaler ;
- les datasets séquentiels ;
- les challengers tabulaires ;
- l’inférence.

## 5.2 `prepare_symbol_frame()` enrichi
Dans `modelFactory/dataset.py`, `prepare_symbol_frame()` accepte maintenant :
- `universe_df`

### Nouveau comportement
Quand `data_cfg.enable_cross_sectional_features` est activé :
1. `compute_features()` construit les features mono-symbole existantes ;
2. `build_cross_sectional_features()` construit le panel de ranks ;
3. `merge_cross_sectional_features()` fusionne sur `(symbol, date)` ;
4. le DataFrame final est filtré sur **toutes** les features actives, y compris cross-sectionnelles.

## 5.3 Diagnostics portés par le DataFrame
Les diagnostics cross-sectionnels sont stockés dans :
- `df.attrs["cross_sectional_diagnostics"]`

Puis récupérés par le `SymbolDataModule`.

# 7. Intégration dans l’orchestrateur

## Nouveau comportement de `_train_worker()`
Dans `modelFactory/orchestrator.py` :
- si `cfg.data.enable_cross_sectional_features` est activé,
- le worker charge un panel univers via `load_universe_bars()` ;
- puis le transmet à `train_symbol(..., universe_df=...)`.

## Compatibilité conservée
Quand le cross-sectionnel est désactivé :
- l’orchestrateur continue d’appeler `_train_worker(sym, cfg)` comme avant.

### Pourquoi cette compatibilité est importante
Elle évite de casser :
- les tests qui monkeypatchent `_train_worker` avec l’ancienne signature ;
- les flows legacy mono-symbole.

# 9. Support de l’inférence cross-sectionnelle

## `predictor.py` enrichi
L’inférence supporte maintenant aussi les modèles entraînés avec `enable_cross_sectional_features=True`.

### Nouveau comportement
Quand le cross-sectionnel est activé dans `config.json` :
1. `predict_symbol()` charge le benchmark si nécessaire ;
2. récupère la liste des candidats via `load_candidate_symbols()` ;
3. charge l’univers historique borné à `cutoff_date` via `load_universe_bars()` ;
4. construit les features cross-sectionnelles ;
5. les merge au DataFrame symbole ;
6. filtre sur les features actives attendues par le scaler.

### Pourquoi c’est essentiel
Sans cela, un modèle entraîné avec des colonnes cross-sectionnelles ne pourrait pas être servi correctement en prédiction.

# 10. Portée fonctionnelle de la V1

## Ce qui est couvert
La V1 implémente des features cross-sectionnelles **robustes et testables** :
- calculées à partir des barres historiques ;
- sans dépendre d’une taxonomie secteur non historisée ;
- sans dépendre de scores externes non PIT-safe.

## Ce qui n’est pas encore couvert
Cette priorité 3 ne couvre pas encore :
- neutralisation sectorielle ;
- features earnings-aware ;
- `beta_proxy_60` ou `corr_to_benchmark_60` ;
- global model multi-symboles.

### Pourquoi c’est acceptable
C’est une V1 ciblée sur le meilleur rapport :
- **valeur métier**
- **robustesse**
- **complexité d’intégration**

# 13. Ce que la priorité 3 change vraiment

## Avant
Le pipeline voyait surtout :
- l’historique du symbole ;
- éventuellement le benchmark ;
- mais pas la position relative du titre dans son univers.

## Maintenant
Le pipeline peut voir :
- si un titre est fort/faible relativement aux autres ;
- si son momentum est élevé en percentile ;
- s’il est dans le haut ou le bas de la distribution cross-sectionnelle de liquidité ou de volatilité ;
- si sa force relative vs benchmark se classe bien dans l’univers.

# 14. Verdict expert
Cette priorité 3 est une vraie montée de gamme pour du swing cash daily.

## Pourquoi c’est important métier
En pratique, beaucoup de signaux swing robustes viennent moins de :
- la dynamique absolue du titre,

que de :
- sa **qualité relative** au reste du marché ou de l’univers investi.

## Ce que cette V1 apporte
- un socle cross-sectionnel PIT-safe ;
- une intégration training + inférence ;
- une base saine pour la suite.

## Ce que cela prépare
La prochaine étape logique est la **priorité 4** :
- modèle global multi-symboles,

ou bien une étape intermédiaire de gouvernance plus avancée :
- sélection automatique du champion.

Dans tous les cas, le pipeline dispose maintenant du carburant cross-sectionnel nécessaire pour monter d’un cran supplémentaire.
