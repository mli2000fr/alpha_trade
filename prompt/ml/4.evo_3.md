# Evolution 3 — Phase 4 expert

## Objectif
Cette phase 4 fait passer `modelFactory` d’un pipeline mono-modèle déjà solide à un cadre **professionnel de sélection, calibration et gouvernance de signaux swing cash daily**.

L’ambition n’est plus seulement de produire une probabilité propre par symbole, mais de bâtir un système qui répond à des questions métier concrètes :

1. **quel modèle mérite d’être utilisé en production ?**
2. **quels seuils sont réellement tradeables pour du swing cash ?**
3. **quels signaux restent robustes selon les régimes de marché ?**
4. **comment comparer proprement LSTM, tabulaire et modèle global ?**
5. **comment rendre `metrics.json` utile comme manifeste de décision et d’audit ?**

La phase 4 est conçue pour un contexte :
- actions daily ;
- jusqu’à ~10 ans de données par symbole ;
- usage principal **cash long / no-trade** ;
- importance forte de la **calibration**, de la **densité de trades** et de la **robustesse hors échantillon**.

---

# 1. Vision cible de la phase 4

## 1.1 Ce que la phase 4 doit apporter
La phase 3 a correctement posé les fondations suivantes :
- features expertes de trend / relative strength / regime ;
- calibration Platt ;
- walk-forward ;
- baseline LightGBM ;
- bucket analysis ;
- optimisation de l’horizon.

La phase 4 doit désormais ajouter cinq briques stratégiques :

1. **sélection champion / challengers** ;
2. **optimisation jointe de la target et du seuil de décision** ;
3. **évaluation business orientée signaux réellement pris** ;
4. **features cross-sectionnelles PIT-safe** ;
5. **préparation au modèle global multi-symboles**.

## 1.2 Positionnement architectural
Le LSTM ne doit plus être considéré comme l’unique modèle “de référence”.

Le pipeline cible doit permettre de comparer au minimum :
- `lstm_attention_symbol`
- `lightgbm_symbol`
- `catboost_symbol`
- `global_lightgbm` ou `global_catboost`

Puis de décider :
- soit un **champion par défaut** ;
- soit une **sélection automatique du champion** selon des critères métier ;
- soit un mode hybride “champion en prod, challengers en audit”.

# 2. Principes métier directeurs

## 2.1 Le problème réel n’est pas “hausse / baisse”
Pour du swing cash, le problème utile est :
- **prendre un long seulement quand il y a une asymétrie exploitable** ;
- sinon rester en cash.

La phase 4 doit donc optimiser :
- la qualité des probabilités ;
- la qualité du ranking ;
- la **valeur conditionnelle des signaux au-dessus d’un seuil** ;
- la stabilité de ces signaux à travers les régimes.

## 2.2 Une bonne calibration n’est utile que si elle améliore la décision
La phase 4 ne doit pas traiter la calibration comme une simple décoration de métriques.

Elle doit servir à :
- choisir un `decision_threshold` plus fiable ;
- obtenir des buckets plus monotones ;
- stabiliser la densité de signaux ;
- rendre la conviction exploitable dans `risk_management`.

## 2.3 Le bon horizon n’est pas indépendant du bon seuil
Le meilleur `forecast_horizon` dépend aussi :
- du `target_up_threshold` ;
- du `target_down_threshold` ;
- du `decision_threshold` final ;
- de la densité de trades acceptable.

La phase 4 doit donc passer d’une optimisation **unidimensionnelle** à une optimisation **conjointe**.

## 2.4 Le daily swing equities bénéficie fortement du cross-sectionnel
Avec ~2500 barres par symbole sur 10 ans, la qualité d’un modèle vient souvent plus de :
- bonnes features relatives ;
- bon ranking cross-sectionnel ;
- bon contexte marché ;
que d’une architecture séquentielle plus sophistiquée.

# 4. Logique métier cible

## 4.1 Logique générale du training phase 4
Le pipeline de training doit suivre cette logique :

1. charger les données symbole et, si activé, les données univers / benchmark ;
2. construire les features symbole + cross-sectionnelles ;
3. optimiser la target et le seuil de décision sur train/val ou walk-forward ;
4. entraîner plusieurs modèles candidats ;
5. calibrer leurs probabilités ;
6. évaluer techniquement et métier ;
7. comparer et classer ;
8. sélectionner un champion si autorisé ;
9. sauvegarder les artefacts et un `metrics.json` riche.

## 4.2 Logique de sélection du champion
### Cas recommandé phase 4.1
- le champion de prod par défaut reste `lstm_attention` ;
- les autres modèles sont des challengers ;
- on compare tout dans `metrics.json`.

### Cas recommandé phase 4.2
- activer `ChampionSelectionConfig.allow_auto_selection=True` ;
- définir une métrique de sélection métier ;
- choisir automatiquement l’architecture champion.

## 4.3 Logique business de décision
La décision de trade doit être optimisée non sur la seule accuracy, mais sur un score mêlant :
- qualité du ranking ;
- précision des signaux longs ;
- rendement futur moyen des signaux pris ;
- stabilité multi-régimes ;
- densité de signaux acceptable.

### Exemple de score métier recommandé
```text
business_score =
    0.30 * precision_long_wf
  + 0.25 * normalized_avg_future_return_on_actions_wf
  + 0.20 * auc_wf
  + 0.10 * (1 - brier_score_wf)
  + 0.10 * top_bucket_hit_rate_wf
  + 0.05 * regime_stability_score
```

### Filtres durs recommandés
Rejeter un candidat si :
- `coverage_at_threshold < min_action_rate`
- `coverage_at_threshold > max_action_rate`
- `precision_long < min_precision_long`
- `top_bucket_count` trop faible
- `n_samples` insuffisant

## 5.3 Optimisation jointe horizon + target thresholds + decision threshold
```python
def optimize_target_and_thresholds(prepared_bars_df, cfg):
    candidates = []

    for horizon in cfg.target_optimization.candidate_horizons:
        for up in cfg.target_optimization.candidate_up_thresholds:
            for down in cfg.target_optimization.candidate_down_thresholds:
                if down > up:
                    continue

                tmp_data_cfg = replace(
                    cfg.data,
                    forecast_horizon=horizon,
                    target_up_threshold=up,
                    target_down_threshold=down,
                )

                tmp_df = prepare_symbol_frame_phase4(
                    prepared_bars_df,
                    tmp_data_cfg,
                    benchmark_df=..., sentiment_df=..., universe_df=...
                )

                split = chrono_split(tmp_df, tmp_data_cfg.train_ratio, tmp_data_cfg.val_ratio)
                selector_result = run_fast_selector_model(split, cfg)
                calibrated_val_proba = selector_result["val_proba"]
                future_ret_val = selector_result["future_return_val"]
                labels_val = selector_result["labels_val"]

                for decision_threshold in cfg.threshold_optimization.candidate_decision_thresholds:
                    metrics = compute_threshold_metrics(
                        probabilities=calibrated_val_proba,
                        labels=labels_val,
                        future_returns=future_ret_val,
                        decision_threshold=decision_threshold,
                    )
                    if not passes_hard_filters(metrics, cfg.threshold_optimization):
                        continue

                    score = compute_business_score(metrics)
                    candidates.append({
                        "horizon": horizon,
                        "target_up_threshold": up,
                        "target_down_threshold": down,
                        "decision_threshold": decision_threshold,
                        "score": score,
                        "metrics": metrics,
                    })

    return select_best_candidate(candidates)
```

## 5.5 Évaluation orientée signaux pris
```python
def compute_threshold_metrics(probabilities, labels, future_returns, decision_threshold):
    pred = (probabilities >= decision_threshold).astype(int)
    action_mask = pred == 1

    coverage = action_mask.mean()
    precision_long = labels[action_mask].mean() if action_mask.any() else 0.0
    avg_return = future_returns[action_mask].mean() if action_mask.any() else None
    median_return = np.median(future_returns[action_mask]) if action_mask.any() else None
    hit_rate = (future_returns[action_mask] > 0).mean() if action_mask.any() else None

    bucket = bucket_analysis(probabilities, labels, future_returns, n_buckets=5)
    regime = regime_analysis(probabilities, labels, future_returns, regimes=...)

    return {
        "decision_threshold": decision_threshold,
        "coverage_at_threshold": coverage,
        "precision_long": precision_long,
        "avg_future_return_on_actions": avg_return,
        "median_future_return_on_actions": median_return,
        "hit_rate_on_actions": hit_rate,
        "bucket_analysis": bucket,
        "regime_analysis": regime,
    }
```

## 5.6 Sélection du champion
```python
def rank_models(challenger_results, champion_cfg):
    rows = []
    for model_name, result in challenger_results.items():
        wf = result.get("walk_forward", {})
        test = result.get("test", {})
        score = compute_model_selection_score(wf=wf, test=test, cfg=champion_cfg)
        rows.append({
            "model_name": model_name,
            "selection_score": score,
            "status": result.get("status", "unknown"),
        })
    return sorted(rows, key=lambda x: x["selection_score"], reverse=True)


def choose_champion(ranking, champion_cfg):
    if not champion_cfg.enabled or not champion_cfg.allow_auto_selection:
        return champion_cfg.default_champion
    return ranking[0]["model_name"] if ranking else champion_cfg.default_champion
```

# 11. Recommandations expertes de gouvernance

## 11.1 Ne pas sur-optimiser le test final
La phase 4 doit garder une discipline stricte :
- optimisation sur train/val ou walk-forward ;
- test final réservé à la validation finale ;
- pas de boucle d’optimisation cachée sur le test.

## 11.2 Éviter de sur-vendre le LSTM
La phase 4 doit accepter explicitement qu’un modèle tabulaire puisse gagner.
C’est un signe de maturité du pipeline, pas un échec.

## 11.3 Favoriser les métriques conditionnelles de trade
Pour le swing cash, les métriques importantes sont :
- ce qui se passe **quand tu agis** ;
- pas seulement ce qui se passe sur tout l’échantillon.

## 11.4 Rester strict sur le PIT
Toute feature non traçable historiquement doit être :
- soit reconstruite depuis l’historique brut ;
- soit exclue.

# 13. Résumé exécutif

## Ce que la phase 4 change vraiment
La phase 4 transforme `modelFactory` en pipeline de décision beaucoup plus professionnel :
- **comparaison explicite de plusieurs architectures** ;
- **optimisation conjointe target + seuil** ;
- **lecture métier des signaux réellement pris** ;
- **préparation au cross-sectionnel et au modèle global** ;
- **artefacts plus auditables**.

## La séquence recommandée
1. optimisation jointe `horizon + target thresholds + decision threshold` ;
2. métriques “on actions” + bucket analysis enrichie ;
3. `CatBoost` challenger + ranking champion/challengers ;
4. features cross-sectionnelles PIT-safe ;
5. modèle global multi-symboles ;
6. éventuellement extension DB.

## Verdict expert
Pour ton use case swing cash daily, la priorité n’est pas d’ajouter un LSTM plus complexe.
La priorité est de rendre le pipeline meilleur sur :
- la **sélection des trades** ;
- la **stabilité des probabilités** ;
- la **comparaison de modèles** ;
- la **robustesse par régime**.

C’est exactement ce que cette phase 4 formalise.
