# Evolution 14 — Filtres IHM pour l’audit `model_predictions` ↔ `model_governance`

## Objectif
Cette évolution prolonge `prompt/ml/13.evo_7.md`.

Après avoir relié SQL et IHM entre :

- `model_predictions`
- `model_governance`

le besoin suivant était de rendre cette vue **réellement opérable au quotidien**.

L’objectif est donc d’ajouter dans la page `ML` des filtres IHM sur :

- `governance_link_status`
- `selection_mode`
- `served_model`
- `run_id`

afin de permettre un tri rapide des cas normaux, des écarts et des investigations ciblées.

---

## 1. Ce qui a été implémenté

### 1.1 Filtres SQL optionnels dans `ihm/services/queries.py`
Les requêtes ML ont été étendues pour accepter des filtres paramétrés.

### `get_model_governance(...)`
La fonction supporte maintenant en plus :

- `run_ids`
- `selection_modes`

### `get_predictions(...)`
La fonction supporte maintenant en plus :

- `run_ids`
- `served_models`

### `get_prediction_governance_audit(...)`
La fonction supporte maintenant en plus :

- `run_ids`
- `selection_modes`
- `served_models`
- `governance_link_statuses`

### Détail technique
Pour conserver une requête sûre et paramétrée, les listes sont converties dynamiquement en clauses `IN (...)` nommées.

Exemple logique :

- `run_id IN (:audit_run_id_0, :audit_run_id_1, ...)`
- `served_model IN (:audit_served_model_0, ...)`

Cela évite d’injecter du SQL brut tout en gardant un filtrage fin.

---

## 2. Filtrage sur alias d’audit joint
Le cas le plus délicat concernait `get_prediction_governance_audit(...)`, car certains filtres portent sur des colonnes **calculées/aliasées** :

- `served_model`
- `governance_selection_mode`
- `governance_link_status`

Pour rendre ces filtres robustes, la requête est maintenant structurée ainsi :

1. une sous-requête construit l’audit joint complet ;
2. une requête externe applique les filtres sur les alias déjà calculés.

### Intérêt
Cette structure permet de filtrer proprement sur les colonnes métiers visibles dans l’IHM sans dupliquer toute la logique de `CASE` dans les clauses `WHERE`.

---

## 3. Nouvelle zone de filtres dans `ihm/pages/ml.py`
La page `ML` expose désormais une section dédiée :

- **Filtres d’audit DB**

### Filtres proposés
- `governance_link_status`
- `selection_mode`
- `served_model`
- `run_id`

### Portée
Ces filtres s’appliquent :

- à la table `model_governance` quand c’est pertinent (`run_id`, `selection_mode`) ;
- à la vue jointe d’audit `model_predictions ↔ model_governance` ;
- à la table `model_predictions` pour les dimensions compatibles (`run_id`, `served_model`).

---

## 4. Construction des options de filtres
Les listes de choix sont calculées automatiquement à partir des données déjà disponibles côté DB via deux sources :

- `get_model_governance(limit=500, ...)`
- `get_prediction_governance_audit(limit=500, ...)`

### Logique
Un helper de page fusionne les valeurs distinctes pour proposer des options pertinentes :

- `selection_mode` peut venir soit de la gouvernance DB directe, soit de la vue jointe ;
- `run_id` est consolidé depuis les deux sources ;
- `served_model` et `governance_link_status` proviennent de la vue jointe.

### Bénéfice
L’utilisateur n’a pas besoin de connaître les valeurs exactes à la main :

- il sélectionne directement les statuts ou runs observés ;
- l’IHM reste cohérente avec le contenu réellement disponible en base.

---

## 5. Cas d’usage opérateurs désormais facilités
### 5.1 Isoler les écarts uniquement
Filtrer :

- `governance_link_status != aligned`

permets d’obtenir immédiatement la liste des cas à investiguer.

### 5.2 Auditer un run précis
Filtrer :

- `run_id = ...`

permet de revoir :

- la gouvernance du run ;
- les prédictions liées ;
- l’alignement entre les deux.

### 5.3 Contrôler un backend servi
Filtrer :

- `served_model = lightgbm`

permet de voir uniquement les prédictions réellement servies par ce backend.

### 5.4 Auditer une stratégie de sélection
Filtrer :

- `selection_mode = auto_selected_champion`
ou
- `selection_mode = fallback_default_champion`

permet de distinguer les runs auto-sélectionnés des cas de repli.

## 9. Verdict technique
Cette évolution ne change pas le contrat ML métier, mais améliore fortement l’exploitabilité opérateur.

### Gains principaux
1. Audit plus rapide des anomalies.
2. Navigation plus simple par run, mode de sélection et backend servi.
3. Cohérence accrue entre les tables `model_governance`, `model_predictions` et la vue jointe IHM.
4. Base plus exploitable sans devoir ouvrir immédiatement les artefacts.

### Limite conservée
Les artefacts restent la source la plus riche pour le manifeste complet et les détails bruts.

Mais l’IHM permet désormais de passer beaucoup plus vite :

- d’une vue globale
- à une investigation ciblée par statut, run, mode de sélection ou backend servi.
