# Evolution 4 — Priorité 4 implémentée

## Objectif
Cette note archive l’implémentation de la **priorité 4** dans `modelFactory` :

1. ajout d’un **modèle global multi-symboles** tabulaire ;
2. entraînement unique sur un panel chrono-splitté **par dates** ;
3. persistance d’artefacts dédiés sous un symbole global ;
4. injection du challenger global dans les artefacts de chaque symbole ;
5. support d’**inférence** pour le backend global tabulaire.

Le principe retenu est volontairement pragmatique et rétrocompatible :
- le **LSTM reste champion par défaut** ;
- le modèle global est d’abord un **challenger comparable** ;
- l’inférence globale est supportée si un symbole route explicitement vers ce backend ;
- aucun schéma SQL n’a été modifié à ce stade.

# 2. Ce qui a été implémenté

## 2.1 Activation du modèle global depuis la CLI
Dans `modelFactory/cli.py`, les options suivantes ont été ajoutées :
- `--enable-global-model`
- `--global-model-name catboost|lightgbm`
- `--global-artifact-symbol`

### Effet
Le modèle global est maintenant pilotable explicitement depuis la ligne de commande,
sans casser les flows existants.

---

## 2.2 Loader batch sentiment multi-symboles
Dans `modelFactory/data_loader.py`, une nouvelle fonction a été ajoutée :
- `load_symbols_sentiment(engine, symbols, end_date=None)`

### Pourquoi
Le modèle global peut, en V1, rester compatible avec un futur usage multi-symboles du sentiment,
sans devoir boucler symbole par symbole au niveau appelant.

---

## 2.3 Nouveau backend `global_model.py`
Un nouveau module `modelFactory/global_model.py` a été créé.

### Ce qu’il fait
Il entraîne un **modèle tabulaire global** en une seule passe sur plusieurs symboles.

### Pipeline retenu
1. charger le panel univers via `load_universe_bars()` ;
2. charger le benchmark si nécessaire ;
3. charger le sentiment multi-symboles si activé ;
4. préparer un DataFrame par symbole ;
5. concaténer tous les DataFrames préparés ;
6. faire un split **par dates uniques** ;
7. entraîner un backend tabulaire :
   - `lightgbm`
   - ou `catboost`
8. calibrer si activé ;
9. optimiser le `decision_threshold` global si activé ;
10. produire :
    - métriques globales `val/test`
    - métriques `by_symbol`
    - artefacts globaux.

# 3. Logique de préparation du dataset global

## 3.1 Préparation par symbole
Le modèle global ne réutilise pas naïvement les barres brutes.
Il passe par une préparation cohérente avec le reste du pipeline :
- `compute_features()` ;
- merge cross-sectionnel éventuel ;
- `future_return` ;
- `target` ;
- filtrage sur les features actives ;
- suppression explicite des lignes sans `target` ou `future_return`.

### Pourquoi c’est important
On garde une sémantique identique entre :
- les runs mono-symbole ;
- les challengers tabulaires ;
- le modèle global.

## 3.2 Split par dates uniques
Le split global est fait **par dates**, pas ligne par ligne.

### Pourquoi
C’est beaucoup plus propre pour un modèle multi-symboles :
- pas de fuite temporelle entre symboles ;
- un jour donné appartient entièrement à un split ;
- le test reste cohérent à l’échelle portefeuille.

# 4. Backends globaux supportés

## Backends V1
Le module global supporte :
- `global_lightgbm`
- `global_catboost`

Le backend effectivement utilisé est déterminé par :
- `cfg.global_model.model_name`

## Comportement si package absent
Si le backend demandé n’est pas installé :
- le modèle global retourne un statut `unavailable`
- avec une raison explicite

### Pourquoi ce choix
On garde la robustesse du pipeline même si l’environnement n’a pas toutes les libs optionnelles.

# 5. Artefacts globaux

## Emplacement
Les artefacts du modèle global sont persistés sous :
- `artifacts/models/<artifact_symbol>/`

Par défaut :
- `artifacts/models/__GLOBAL__/`

## Fichiers persistés
- `global_model.pkl`
- `config.json`
- `metrics.json`
- `calibrator.pkl` *(si calibration active et fit possible)*

## Contenu du `config.json` global
Le fichier contient notamment :
- `data`
- `global_model`
- `feature_columns`
- `cross_sectional_diagnostics`
- `artifact_symbol`
- `model_name = "global_model"`
- `backend_model_name`
- `model_path`
- `selected_decision_threshold`
- `architecture_selected = "global_model"`
- `inference_backend = "global_tabular"`

### Pourquoi c’est important
Le backend global devient un citoyen de première classe du système d’artefacts,
même s’il n’est pas encore champion par défaut.

# 6. Injection du challenger global dans les symboles

## Nouveau comportement dans `orchestrator.py`
Après le batch mono-symbole :
1. si `cfg.global_model.enabled` est activé ;
2. l’orchestrateur entraîne le modèle global **une seule fois** ;
3. puis il met à jour les artefacts de chaque symbole complété.

## Mise à jour des artefacts symbole
Pour chaque symbole complété :
- `config.json` reçoit une route :
  - `artifact_routes.models.global_model`
- `metrics.json` reçoit :
  - `global_model`
  - `challengers.global_model`
  - un `ranking` recalculé incluant le global model.

### Ce qui reste inchangé
- `architecture_selected` reste `lstm_attention`
- `selection_mode` reste `default_lstm_champion`

### Pourquoi c’est une bonne étape intermédiaire
Tu peux comparer le global model dans les artefacts,
mais tu ne bascules pas encore en prod automatique sur un nouveau backend.

---

# 7. Inference routing vers le modèle global

## `predictor.py` généralisé
`predictor.py` ne se limite plus à un simple routage LSTM.

### Nouveau mécanisme
Ajout de helpers :
- `_resolve_selected_model_route()`
- `_load_data_cfg_from_payload()`
- `_prepare_prediction_frame()`
- `_predict_with_global_model()`

## Comportement
Quand `artifact_routes.selected_model == "global_model"` et qu’une route `global_tabular` existe :
- le predictor charge le `config.json` global ;
- charge le `global_model.pkl` ;
- reconstruit les features du symbole courant ;
- applique éventuellement le merge cross-sectionnel ;
- exécute la prédiction tabulaire ;
- applique éventuellement la calibration globale ;
- renvoie une prédiction standardisée.

### Sinon
Le predictor continue de servir le backend `lstm_attention` comme avant.

---

# 8. Sortie de prédiction

## Sortie standardisée
Même avec le backend global, la sortie garde le contrat habituel :
- `symbol`
- `prediction_date`
- `predicted_proba`
- `predicted_class`
- `run_id`
- `raw_proba`
- `decision_threshold`
- `signal_label`
- `calibration_method`
- `selected_model`

### Pourquoi c’est important
Le reste du système n’a pas besoin de connaître le backend exact pour consommer le résultat.

# 9. Logique de ranking

## Position actuelle du global model
Le global model est injecté comme **challenger**.

Dans `metrics.json` symbole, il apparaît désormais :
- dans `global_model`
- dans `challengers.global_model`
- dans `challengers.ranking`

## Score utilisé
Le ranking continue d’utiliser la logique existante :
- `selection_score`
- sinon `threshold_business_score`
- sinon `auc`
- sinon un fallback plus faible.

### Pourquoi c’est cohérent
On garde une comparaison homogène entre :
- LSTM mono-symbole
- LightGBM mono-symbole
- CatBoost mono-symbole
- Global model tabulaire

# 10. Portée fonctionnelle de la V1

## Ce qui est couvert
Cette priorité 4 couvre :
- un modèle global tabulaire ;
- split temporel global par dates ;
- persistance dédiée ;
- injection dans les artefacts symbole ;
- inférence du backend global.

## Ce qui n’est pas encore couvert
Cette V1 ne couvre pas encore :
- sélection automatique du champion ;
- écriture du modèle global dans le registre DB ;
- global model séquentiel avec embeddings symbole ;
- pondérations spécifiques par symbole / par liquidité ;
- gouvernance avancée portfolio-aware du score global.

### Pourquoi c’est acceptable
C’est une V1 robuste et utile :
- comparaison réelle ;
- coût d’intégration raisonnable ;
- forte valeur informative ;
- base saine pour une future montée en sophistication.

# 13. Ce que la priorité 4 change vraiment

## Avant
Le pipeline comparait surtout :
- LSTM mono-symbole
- baselines tabulaires mono-symbole

mais ne disposait pas d’un vrai backend global exploitable.

## Maintenant
Le pipeline peut :
- entraîner un modèle tabulaire global sur plusieurs symboles ;
- mesurer son comportement global et par symbole ;
- le comparer dans le ranking ;
- le servir en inférence si une route l’indique.

---

# 14. Verdict expert
Cette priorité 4 fait franchir un vrai cap à `modelFactory`.

## Pourquoi c’est stratégiquement important
Avec des historiques daily limités par symbole,
le global model permet enfin de mutualiser :
- plus d’exemples ;
- plus de régimes ;
- plus de structure cross-sectionnelle ;
- plus de robustesse statistique.

## Ce que cette V1 apporte
- un backend global réel ;
- une comparaison tangible avec les modèles locaux ;
- un routage d’inférence déjà prêt ;
- une base saine pour la sélection automatique du champion.

## Suite logique
La prochaine étape la plus naturelle est désormais :
1. **sélection automatique du champion**
2. puis, si besoin, raffinement du global model :
   - features supplémentaires
   - backend séquentiel global
   - pondérations / governance portfolio-aware

En l’état, le pipeline a maintenant une vraie colonne vertébrale phase 4 :
- optimisation de target/seuil ;
- challengers ;
- cross-sectionnel ;
- global model.
