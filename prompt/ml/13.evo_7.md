# Evolution 13 — Liaison IHM entre `model_predictions` et `model_governance`

## Objectif
Cette évolution implémente le **point 3** identifié à la fin de `prompt/ml/12.evo_6.m` :

> relier explicitement `model_governance` et `model_predictions` pour naviguer d’une prédiction servie vers le snapshot de gouvernance qui l’a produite.

L’objectif n’est pas de remplacer les artefacts, mais de rendre **lisible directement dans l’IHM SQL** le lien entre :

- la prédiction réellement servie ;
- le modèle déclaré champion dans la gouvernance ;
- les métadonnées de sélection/serving associées au run concerné.

---

## 1. Ce qui a été ajouté

### 1.1 Nouvelle requête jointe dans `ihm/services/queries.py`
Une nouvelle fonction a été ajoutée :

- `get_prediction_governance_audit(limit=..., symbol=...)`

### Rôle
Elle construit une vue SQL jointe entre :

- `model_predictions p`
- `model_governance served`
- `model_governance champion`

### Principe de jointure
Le lien repose sur :

- `p.run_id = model_governance.run_id`
- `p.symbol = model_governance.symbol`

Puis deux usages complémentaires :

1. **ligne du modèle servi**
   - `served.model_name = p.selected_model`
2. **ligne du champion gouvernance**
   - `champion.is_selected_model = 1`

Cela permet de comparer explicitement :

- le backend réellement servi en prédiction ;
- le champion déclaré par la gouvernance du run ;
- les métadonnées de sélection et de serving côté gouvernance.

## 3. Effet fonctionnel dans l’IHM

### 3.1 Nouvelle section sur la page `ML`
La page :

- `ihm/pages/ml.py`

affiche désormais une section dédiée :

- **Audit serving ↔ gouvernance**

### Rôle de cette section
Elle permet, pour le symbole sélectionné, de voir :

- le dernier modèle effectivement servi ;
- le champion déclaré côté gouvernance ;
- le statut d’alignement entre les deux ;
- le nombre de lignes à investiguer si des écarts existent ;
- le détail tabulaire joint prédiction/gouvernance.

### Valeur métier
Cette vue répond directement à des questions opérateur comme :

- la prédiction servie correspond-elle bien au champion du run ?
- le modèle servi était-il bien éligible ?
- quel backend/calibration/seuil étaient attendus côté gouvernance ?
- y a-t-il des prédictions historiques non reliées à un snapshot de gouvernance ?

## 8. Verdict technique
Cette évolution rend la relation entre **serving réel** et **gouvernance ML persistée** beaucoup plus exploitable.

### Gains principaux
1. Audit SQL plus lisible du champion réellement servi.
2. Détection explicite des écarts entre `model_predictions` et `model_governance`.
3. IHM ML plus utile pour l’investigation quotidienne.
4. Contrat DB/IHM plus cohérent avec la réalité multi-modèles de `modelFactory`.

### Limite conservée
Les artefacts restent la source la plus détaillée pour le manifeste brut complet.

Mais l’IHM peut maintenant relier bien plus directement :

- **la prédiction exécutée**
- **au snapshot de gouvernance qui l’explique**.
