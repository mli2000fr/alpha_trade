# Evolution 11 — IHM ML, navigation Pipeline → ML et audit DB enrichi

## Objectif
Cette évolution poursuit la professionnalisation de l'IHM autour de `modelFactory`.

Deux besoins existaient encore :

1. depuis la page `Pipeline`, un opérateur devait pouvoir **ouvrir rapidement la page ML sur un symbole précis** au lieu de naviguer manuellement ;
2. la page `ML` dépendait encore trop des artefacts disque pour l'audit du serving quotidien, car la table `model_predictions` ne persistait pas tout le contexte de serving.

Cette évolution corrige les deux points.

---

# 1. Ce qui a été implémenté

## 1.1 Navigation `Pipeline` → `ML`
La page `ihm/pages/pipeline.py` propose maintenant, sur les étapes :
- `ml_train`
- `ml_predict`

un sélecteur de symbole basé sur les artefacts `modelFactory`, puis un bouton :
- **Ouvrir dans la page ML**

### Comportement
Quand l'opérateur clique :
- le symbole choisi est stocké dans `st.session_state["ihm_ml_selected_symbol"]` ;
- la page cible est stockée dans `st.session_state["ihm_navigation_target_page"]` ;
- `ihm/app.py` lit cette intention de navigation et force la sidebar sur la page `ML`.

### Résultat opérateur
Le flux devient naturel :
- lancer / superviser une étape ML dans `Pipeline` ;
- cliquer ;
- arriver directement sur la page `ML` avec le bon symbole déjà sélectionné.

---

## 1.2 Audit DB enrichi dans `model_predictions`
Le schéma SQL a été enrichi pour stocker explicitement le contexte réel de serving.

### Nouvelles colonnes ajoutées
Dans `model_predictions` :
- `selected_model`
- `decision_threshold`
- `signal_label`
- `calibration_method`

### Pourquoi c'est important
Avant, la DB contenait seulement :
- `symbol`
- `prediction_date`
- `predicted_proba`
- `predicted_class`
- `run_id`

Cela suffisait pour le `risk_management`, mais pas pour répondre facilement à des questions d'audit comme :
- quel backend a réellement servi cette prédiction ?
- quel seuil a été utilisé ?
- la calibration a-t-elle été appliquée ?
- le signal final était-il `long` ou `no_trade` ?

Maintenant, ces informations sont aussi présentes en base.

---

## 1.3 Migration Alembic ajoutée
Nouvelle migration :
- `alembic/versions/0005_add_model_predictions_audit_fields.py`

### Effet
Elle ajoute proprement les colonnes d'audit à `model_predictions` ainsi qu'un index :
- `idx_selected_model`

Cela permet d'aligner :
- le schéma SQL versionné ;
- le DDL manuel dans `database/sql/ml/model_predictions.sql` ;
- le code Python d'insertion.

---

## 1.4 `db_registry.insert_predictions()` supporte l'ancien et le nouveau schéma
Le code de persistance a été modifié dans :
- `modelFactory/db_registry.py`

### Nouveau comportement
`insert_predictions()` tente d'abord une insertion V2 avec :
- `selected_model`
- `decision_threshold`
- `signal_label`
- `calibration_method`

Si le schéma n'est pas encore migré, le code retombe sur l'insertion legacy.

### Pourquoi c'est utile
Cela réduit le risque d'introduire une régression brutale dans un environnement où :
- le code a été mis à jour ;
- mais la migration SQL n'a pas encore été appliquée.

---

## 1.5 La page `ML` exploite maintenant les nouvelles colonnes DB
Dans `ihm/services/queries.py`, les requêtes ML ont été enrichies.

### Ajouts
- `get_prediction_symbols()`
- `get_predictions(limit=..., symbol=...)`

La requête retourne maintenant aussi :
- `selected_model`
- `decision_threshold`
- `signal_label`
- `calibration_method`

### Conséquence côté IHM
La page `ihm/pages/ml.py` peut maintenant :
- pré-sélectionner un symbole ;
- filtrer les prédictions récentes pour ce symbole ;
- montrer un audit DB beaucoup plus utile, sans dépendre exclusivement des artefacts.

---

## 1.6 La page `ML` garde une double lecture : DB + artefacts
L'objectif n'était pas de supprimer les artefacts, mais de mieux répartir les rôles.

### La DB sert maintenant pour l'audit de serving quotidien
Très utile pour :
- l'opérateur ;
- les diagnostics quotidiens ;
- l'analyse rapide de ce qui a été réellement servi.

### Les artefacts restent la source riche pour
- le ranking complet challengers ;
- les routes détaillées ;
- les manifestes complets `config.json` / `metrics.json` ;
- la gouvernance fine multi-modèles.

### Résultat
La page `ML` devient plus robuste :
- sans DB → on peut toujours lire les artefacts ;
- avec DB → l'audit quotidien est plus riche ;
- avec les deux → on a une lecture complète.

# 3. Contrat DB final pour `model_predictions`

## Colonnes historiques
- `symbol`
- `prediction_date`
- `predicted_proba`
- `predicted_class`
- `run_id`
- `created_at`

## Colonnes d'audit ajoutées
- `selected_model`
- `decision_threshold`
- `signal_label`
- `calibration_method`

## Signification métier
- `selected_model` : backend réellement servi (`lstm_attention`, `lightgbm`, `catboost`, `global_model`)
- `decision_threshold` : seuil de décision appliqué au moment de l'inférence
- `signal_label` : signal final servi (`long`, `no_trade`)
- `calibration_method` : méthode de calibration réellement appliquée (`none`, `platt`, etc.)

---

# 4. Impact sur l'exploitation quotidienne

## Avant
Pour comprendre pourquoi une prédiction avait été servie, il fallait souvent :
1. ouvrir la page `ML` ;
2. aller lire les artefacts ;
3. reconstituer le backend réellement servi ;
4. déduire le seuil et la calibration.

## Maintenant
Une grande partie de l'audit utile est directement en base.

### Exemples de questions désormais simples
- quel backend a servi `AAPL` aujourd'hui ?
- le signal a-t-il été `long` ou `no_trade` ?
- le seuil utilisé était-il `0.61` ou `0.50` ?
- la probabilité était-elle calibrée via `platt` ou non ?

# 6. Verdict technique

Cette évolution améliore fortement l'exploitabilité de l'IHM ML.

## Gains principaux
1. **Navigation plus fluide** : `Pipeline` peut ouvrir `ML` sur le bon symbole.
2. **Audit DB enrichi** : la table `model_predictions` reflète mieux le serving réel.
3. **Réduction de la dépendance aux artefacts** pour les diagnostics quotidiens.
4. **Robustesse de déploiement** grâce au fallback de persistance si la migration n'est pas encore appliquée.

## Ce qui reste encore côté artefacts
Les artefacts restent indispensables pour :
- le détail complet challengers/champion ;
- les routes multi-backends complètes ;
- les manifestes complets de gouvernance.

Mais la DB est désormais suffisamment riche pour la majorité des audits opérateurs quotidiens.

---

# 7. Suite logique possible
Les prochaines améliorations cohérentes seraient :

1. ajouter une vraie **vue historique par symbole et par date** dans la page `ML` ;
2. persister aussi en DB des informations challengers/champion plus détaillées ;
3. permettre depuis `Pipeline` d'ouvrir non seulement la page `ML`, mais aussi directement un onglet / sous-section spécifique (`predictions`, `routes`, `ranking`).
