# Evolution 4 — Priorité 2 implémentée

## Objectif
Cette note archive l’implémentation de la **priorité 2** dans `modelFactory` :

1. ajout d’un challenger **CatBoost** ;
2. normalisation du **contrat de sortie challengers** ;
3. introduction d’un **ranking champion/challengers** ;
4. maintien du **LSTM comme champion par défaut** ;
5. préparation d’un **routage multi-artefacts** côté inférence, sans casser l’existant.

Le principe retenu a été volontairement pragmatique :
- garder l’inférence LSTM comme backend de production actif ;
- comparer `LightGBM` et `CatBoost` proprement dans les artefacts ;
- préparer le terrain pour une future sélection automatique du champion.

# 2. Ce qui a été implémenté

## 2.1 `CatBoost` challenger optionnel
Un nouveau module `modelFactory/catboost_baseline.py` a été ajouté.

### Comportement
- si `cfg.baseline.enable_catboost` est `False` :
  - le challenger n’est pas exécuté ;
- si `CatBoost` n’est pas installé :
  - le module retourne proprement :
    - `status = "unavailable"`
    - `reason = "catboost_not_installed"`
- si `CatBoost` est disponible :
  - il est entraîné comme challenger tabulaire,
  - avec le même contrat de sortie que `LightGBM`.

### Pourquoi ce design est bon
Il évite d’imposer `CatBoost` à tout l’environnement runtime,
mais permet de l’activer facilement dans un environnement orienté recherche / benchmark.

---

## 2.2 Contrat commun des challengers tabulaires
Un nouveau module `modelFactory/tabular_baseline.py` a été créé pour factoriser les briques communes à `LightGBM` et `CatBoost`.

### Ce module gère maintenant
- le split tabulaire chrono : `tabular_split()` ;
- le calcul AUC : `binary_auc()` ;
- le calcul ECE : `expected_calibration_error()` ;
- les métriques tabulaires homogènes : `compute_tabular_metrics()` ;
- la calibration Platt sur validation : `fit_tabular_calibrator()` ;
- l’application de la calibration : `apply_tabular_calibration()` ;
- le runner générique : `run_tabular_baseline()`.

### Bénéfice principal
`LightGBM` et `CatBoost` produisent désormais le même schéma métier :
- `status`
- `model_name`
- `feature_columns`
- `val`
- `test`
- `calibration_method`
- `threshold_optimization`
- `selection_score`

Cela prépare très proprement la logique champion/challengers.

---

## 2.3 Refactorisation de `LightGBM`
`modelFactory/lightgbm_baseline.py` a été simplifié.

### Avant
Le module contenait lui-même :
- split ;
- calibration ;
- métriques ;
- logique de décision.

### Maintenant
Il délègue tout le flux générique à `run_tabular_baseline()`.

### Conséquence
`LightGBM` adopte exactement le même contrat que `CatBoost`, avec en plus :
- sweep du `decision_threshold` si activé ;
- calibration Platt si activée ;
- score de ranking homogène.

Même si l’activation de `CatBoost` repose aujourd’hui surtout sur `enable_catboost`, cette ouverture rend la config plus propre et cohérente pour la suite.

## 2.6 Ranking champion/challengers dans `trainer.py`
Le cœur de la priorité 2 a été ajouté dans `modelFactory/trainer.py`.

### Ce qui a été fait
Après l’entraînement du LSTM et l’exécution des challengers :
- le pipeline construit un objet `challengers` avec :
  - `lstm_attention`
  - `lightgbm`
  - `catboost`
- il calcule un `selection_score` par modèle ;
- il produit une `ranking` triée par score ;
- il persiste ces informations dans `metrics.json`.

### Score de ranking
Le score utilisé privilégie en premier :
- `selection_score` déjà fourni par un challenger si présent ;
- sinon `threshold_business_score` ;
- sinon `auc` ;
- sinon `directional_accuracy`.

### Choix de gouvernance retenu
Le **LSTM reste champion par défaut**.

Donc :
- le ranking peut montrer qu’un challenger a un meilleur score ;
- mais `architecture_selected` reste `lstm_attention` ;
- le `status` du champion reflète ce choix :
  - `selected_default_champion`

### Pourquoi c’est important
On sépare enfin deux notions :
- **meilleur score observé** ;
- **modèle effectivement choisi en production**.

C’est une vraie logique de gouvernance de modèle.

Le `config.json` contient maintenant aussi :

### Pourquoi c’est utile

sans devoir encore activer l’inférence tabulaire en production.

## 2.8 `predictor.py` préparé au routage multi-artefacts
`modelFactory/predictor.py` a été enrichi avec :
- `_resolve_routed_lstm_artifacts()`

### Nouveau comportement
Le predictor :
1. charge `config.json` ;
2. regarde `artifact_routes` et `architecture_selected` ;
3. tente de résoudre les artefacts du backend LSTM ;
4. si le modèle sélectionné n’est pas `lstm_attention`, il loggue un warning clair ;
5. retombe proprement sur le backend LSTM tant que l’inférence tabulaire n’est pas activée.

### Pourquoi ce design est bon
Il prépare la suite sans casser le présent :
- le routage existe ;
- la sélection d’architecture existe ;
- l’inférence tabulaire future pourra s’y brancher ;
- aujourd’hui, le comportement de prod reste robuste et explicite.

---

# 6. Ce que la priorité 2 change vraiment

## Avant
Le pipeline savait :
- entraîner un LSTM ;
- comparer optionnellement une baseline `LightGBM` ;
- mais sans vrai contrat multi-modèles standardisé.

## Maintenant
Le pipeline sait :
- exécuter `LightGBM` et `CatBoost` avec une structure homogène ;
- construire un ranking challengers ;
- expliciter le champion de production ;
- commencer à router les artefacts par architecture.

---

# 7. Ce qui reste volontairement non activé

## Inférence tabulaire de production
Elle n’est **pas encore activée**.

Le système est prêt à la supporter plus tard via :
- `architecture_selected`
- `artifact_routes`
- la structure challengers

Mais, à ce stade :
- seul `lstm_attention` est réellement servi en inférence ;
- si un autre modèle est marqué sélectionné plus tard, le predictor logguera un fallback explicite tant que le backend tabulaire n’est pas branché.

## Sélection automatique du champion
Elle n’est pas encore activée non plus.

Le ranking existe,
mais le choix de prod reste :
- `selection_mode = "default_lstm_champion"`

C’est cohérent avec la roadmap :
- priorité 2 = comparer et structurer ;
- priorité suivante = choisir automatiquement.

# 8. Verdict expert
La priorité 2 fait passer `modelFactory` d’un système “LSTM + baseline optionnelle” à un pipeline beaucoup plus crédible en phase 4.

## Ce qui est maintenant en place
- challenger `CatBoost` optionnel ;
- contrat standard challengers ;
- ranking persistant ;
- champion explicite ;
- routage multi-artefacts préparé.

## Pourquoi c’est important métier
Tu peux désormais répondre proprement à :
- le `LightGBM` fait-il mieux que le LSTM ?
- `CatBoost` apporte-t-il un gain ?
- quel modèle est champion ?
- quel challenger surperforme mais n’est pas encore servi en prod ?

## Ce que cela prépare pour la suite
La prochaine étape naturelle devient :
1. sélection automatique du champion ;
2. éventuel backend d’inférence tabulaire ;
3. puis features cross-sectionnelles et modèle global.
