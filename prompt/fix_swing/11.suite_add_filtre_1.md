# Intégration du filtre, emplacement recommandé et verdict opérationnel final

## 1) Où est-il préférable d’ajouter ce filtre ?

### Réponse courte
Oui, **le meilleur endroit métier est `selector/alpha_scanner.py`**, plus précisément dans **`AlphaScanner.apply_filters()`**.

### Pourquoi cet endroit est le bon
Le filtre `volatility_ratio <= 0.90` dépend d’un calcul issu de l’historique des prix :

- `vol_10` = volatilité récente 10 jours
- `vol_60` = volatilité de référence 60 jours
- `volatility_ratio = vol_10 / vol_60`

Ce ratio n’existe **qu’après** l’étape `compute_factors()`.

Donc :
- **pas idéal dans la présélection SQL brute** ;
- **très bien dans `apply_filters()`**, juste après le calcul des facteurs et avant le ranking final.

### Ordre recommandé des étapes
1. présélection SQL : historique, univers actions US, prix, liquidité de base ;
2. chargement OHLCV + calcul des facteurs ;
3. **application du filtre de volatilité relative dans `apply_filters()`** ;
4. fusion / score final ;
5. neutralisation sectorielle ;
6. ranking final.

### Pourquoi ne pas le mettre seulement dans le backtest ?
Si on le laisse uniquement dans `prompt/fix_swing/run_filtered_case_real.py`, il agit seulement au moment du rerun/backtest.
On obtient alors une incohérence possible entre :

- l’univers live / scanner,
- les snapshots historiques backfillés,
- le rerun OOS filtré.

Le bon modèle est donc :
- **filtre métier central dans `AlphaScanner`** ;
- **filtre PIT conservé dans `run_filtered_case_real.py`** pour garantir le backtest sans look-ahead.

## 2) Où le filtre a été ajouté concrètement ?

### A. Dans `selector/alpha_scanner.py`
Ajouts réalisés :

1. **Nouveau paramètre de config** dans `AlphaScannerConfig` :
   - `max_volatility_ratio: float | None = None`

2. **Validation de config** :
   - rejet si la valeur est `<= 0`

3. **Application réelle du filtre** dans `AlphaScanner.apply_filters()` :
   - quand `max_volatility_ratio` est renseigné,
   - seuls les titres avec `volatility_ratio <= seuil` sont conservés

4. **CLI exposée** :
   - nouveau paramètre `--max-volatility-ratio`

### B. Dans `prompt/fix_swing/run_strict_oos_2025q1.py`
Ajouts réalisés :

1. définition explicite des seuils stricts :
   - `min_close = 10.0`
   - `min_avg_dollar_volume_20d = 30_000_000.0`
   - `max_volatility_ratio = 0.9`

2. injection de ces seuils dans `AlphaScannerConfig(...)` lors du backfill strict,
   afin que `stock_scores_history` soit reconstruit avec le même univers filtré

3. ajout des filtres au manifest du run strict pour la traçabilité

### C. Ce qui reste en place dans `prompt/fix_swing/run_filtered_case_real.py`
Le filtrage point-in-time reste conservé dans ce script, car il est nécessaire pour le backtest quotidien sans biais temporel.

## 4) Résumé du filtre ajouté et de son rôle

### Filtre 1 — `min_close >= 10`
But : éviter les titres trop bas de gamme / trop spéculatifs.

### Filtre 2 — `avg_dollar_volume_20d >= 30M`
But : garantir un minimum d’exécutabilité réelle.

### Filtre 3 — `volatility_ratio <= 0.90`
But : éviter les entrées sur titres en explosion de volatilité récente.

### Lecture métier globale
Ces trois filtres servent à :
- réduire les microcaps et pseudo-outliers ;
- rendre le portefeuille plus réaliste en exécution ;
- limiter la dépendance aux coups de chance ;
- rendre le backtest plus honnête pour un petit compte cash.

## 5) Verdict opérationnel final

# Verdict : **NO-GO pour passage live immédiat**

## Pourquoi ce n’est pas encore un GO live
Malgré un vrai OOS 2025Q1 convaincant, il reste deux signaux de prudence :

1. **holdout 2026Q1 trop faible**
   - +3.57% seulement
   - Sharpe 0.49
   - profit factor 1.08
   - win rate faible

2. **concentration encore trop forte**
   - 92.40% du PnL du vrai OOS 2025Q1 vient des top 3 symboles
   - 634.55% du PnL du holdout 2026Q1 vient des top 3 symboles

Donc la stratégie est meilleure, mais **pas encore suffisamment stable pour un déploiement live immédiat en confiance**.

## 6) Ce qu’il faut garder

### À conserver absolument
1. **Le triplet de filtres stricts**
   - `close >= 10`
   - `ADV20 >= 30M`
   - `volatility_ratio <= 0.90`

2. **Le mode petit compte cash réaliste**
   - `max_positions = 2`
   - `account_type = cash`
   - `swing_only = True`

3. **Le principe PIT dans le rerun backtest**
   - les filtres doivent rester calculés au bon moment historique

4. **La traçabilité des artefacts**
   - manifest
   - report
   - analysis_summary

5. **L’intégration du filtre dans `AlphaScanner`**
   - meilleure cohérence système
   - meilleure réutilisation
   - meilleure maintenabilité

## 7) Ce qu’il faut encore améliorer avant réel

### Priorité 1 — validation multi-régimes
Faire tourner le même setup sur plus de fenêtres indépendantes :
- 2024Q3
- 2024Q4
- 2025Q2
- 2025Q3
- 2025Q4
- 2026Q2 quand disponible

Objectif : vérifier si la stratégie reste au moins neutre/positive hors période favorable.

### Priorité 2 — réduire la concentration
Ajouter des diagnostics ou contraintes supplémentaires sur :
- exposition max par symbole sur une fenêtre glissante ;
- limitation du nombre de ré-entrées successives sur le même nom ;
- cap de contribution PnL ex post pour identifier les symboles “dominants”.

### Priorité 3 — tester la sensibilité des seuils
Comparer :
- `volatility_ratio <= 0.85`
- `volatility_ratio <= 0.90`
- `volatility_ratio <= 1.00`

et aussi :
- `ADV20 >= 20M`
- `ADV20 >= 30M`
- `ADV20 >= 50M`

Objectif : confirmer que le gain de robustesse n’est pas juste un lucky setting.

### Priorité 4 — intégrer des coûts d’exécution plus réalistes
Avant live, il faut tester avec :
- slippage conservateur,
- frais implicites,
- latence d’entrée à l’open,
- spreads plus durs sur small/mid caps.

### Priorité 5 — paper trading réel avant live
Avant réel :
- lancer plusieurs semaines de **paper trading**,
- comparer fills simulés vs marché,
- surveiller taux de rotation, slippage, concentration, drift de performance.

## 8) Recommandation finale en une phrase

### Décision
- **Live immédiat : NO-GO**
- **Paper trading / validation élargie : GO**
- **Conserver les filtres : GO**

### Formulation simple
La stratégie filtrée est **assez bonne pour continuer sérieusement**, mais **pas encore assez robuste pour passer en réel sans une phase supplémentaire de validation hors échantillon et en paper trading**.
