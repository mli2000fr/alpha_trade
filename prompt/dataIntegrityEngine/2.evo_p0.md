## P0.2 — Distinction no-data réel vs incident technique Alpaca

### Fichiers modifiés
- `service/alpaca/clientAlpaca.py`
- `dataIntegrityEngine/import_alpaca_bar.py`
- `tests/test_clientAlpaca.py`
- `tests/test_import_alpaca_bar.py`

### Ce qui a été fait
- Ajout d’une exception dédiée : `AlpacaBarsFetchError`.
- Après épuisement des retries timeout, `fetch_bars()` ne retourne plus une fausse liste vide : il lève une erreur technique explicite.
- Les erreurs HTTP non-404 et erreurs réseau sont converties en `AlpacaBarsFetchError`.
- Le `404` continue d’être traité comme un vrai cas “aucune donnée disponible”.
- `import_alpaca_bar.py` ne met plus `bars_available=False` lors d’un incident technique.
- `bars_available=False` n’est conservé que si l’absence de données est confirmée par le provider.

### Impact métier
On supprime le faux négatif le plus dangereux du pipeline :
un symbole n’est plus exclu durablement de l’univers à cause d’un timeout réseau transitoire.

## P0.3 — Incrémental sanitizeur remplacé par un recalcul glissant robuste

### Fichiers modifiés
- `dataIntegrityEngine/data_sanitizer_daily.py`
- `tests/test_data_sanitizer_daily.py`

### Ce qui a été fait
- Ajout d’une fenêtre glissante de recalcul : `REBUILD_LOOKBACK_CALENDAR_DAYS = 400`.
- Le sanitizeur ne repart plus de `last_sync + 1 jour`.
- Il recharge désormais les données brutes depuis `last_sync - 400 jours calendaires`.
- La sortie recalculée est ré-upsertée sur toute cette fenêtre.

### Pourquoi c’est important
Cela permet de couvrir correctement :
- corrections tardives provider ;
- effets de split ;
- dépendances sur `prev_close` ;
- détection d’anomalies sur fenêtre roulante.

## P0.4 — Échec sanitizeur propagé explicitement à l’aval

### Fichiers modifiés
- `dataIntegrityEngine/data_sanitizer_daily.py`
- `database/sanitizer_db_ops.py`
- `database/sql/stock/stock_scores.sql`
- `database/sql/stock/stock_scores_history.sql`
- `screener/db_io.py`
- `selector/alpha_scanner.py`
- `tests/test_data_sanitizer_daily.py`
- `tests/test_screener_db_io.py`
- `tests/test_selector_alpha_scanner.py`
- `tests/test_alpha_scanner.py`

### Ce qui a été fait
- `sync_audit_to_stock_scores()` accepte maintenant :
  - `missing_days_count`
  - `anomaly_count`
  - `sanitizer_status`
- Ajout de la colonne SQL :
  - `stock_scores.sanitizer_status VARCHAR(16) NOT NULL DEFAULT 'pending'`
  - `stock_scores_history.sanitizer_status VARCHAR(16) NOT NULL DEFAULT 'pending'`
- En cas d’échec sanitizeur, le pipeline n’envoie plus un faux `0/0` “propre”.
- Il persiste désormais :
  - `sanitizer_status='failed'`
  - compteurs `NULL`
- Le `screener` enrichit maintenant `stock_scores` avec le dernier audit `cleaning_audit_log`.
- Le `selector` lit `sanitizer_status` et exclut explicitement les symboles au statut différent de `success`.

### Impact métier
Un symbole dont le nettoyage a échoué ne peut plus se retrouver sélectionné comme s’il était sain.

## P0.5 — Plafond de forward-fill consécutif

### Fichiers modifiés
- `dataIntegrityEngine/data_sanitizer_daily.py`
- `tests/test_data_sanitizer_daily.py`

### Ce qui a été fait
- Ajout de `MAX_CONSECUTIVE_FILLED_DAYS = 3`.
- Calcul explicite des streaks de jours manquants forward-filled.
- Si la série dépasse le plafond, le sanitizeur lève une `DataQualityError`.

### Règle retenue
- jusqu’à **3** séances consécutives forward-filled : tolérées ;
- **au-delà** : série considérée comme dégradée, run symbole en échec.

### Impact métier
On évite de fabriquer des séries artificiellement stables sur des titres suspendus / délistés / trop mal couverts.

## 5. Points importants de conception retenus

### 5.1 Pourquoi `failed + NULL` plutôt que `failed + 0`
Parce que `0` signifie “mesuré et nul”, alors que `NULL` signifie “non fiable / non calculé”.
C’est plus propre pour l’audit et plus sûr pour l’aval.

### 5.2 Pourquoi garder l’audit dans `cleaning_audit_log` à ce stade
Le vrai split `latest / runs` était classé plutôt P1 dans l’audit.
Pour le P0, l’objectif prioritaire était de rendre le pipeline sûr sans élargir inutilement la refonte.

### 5.3 Pourquoi un lookback de 400 jours calendaires
C’est un compromis simple et robuste pour un pipeline daily :
- suffisamment large pour les recalculs de qualité ;
- suffisamment peu coûteux pour ton volume (10 ans daily par symbole).
