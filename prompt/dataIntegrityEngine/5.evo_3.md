1. **propager `history_status`** dans les consommateurs downstream ;

## 2. Changements réalisés

## 2.1 Propagation aval de `history_status`

### Fichiers modifiés
- `database/selector_reference.py`
- `selector/alpha_scanner.py`
- `tests/test_selector_reference.py`
- `tests/test_alpha_scanner.py`

### Ce qui a été fait

#### `database/selector_reference.py`
La fonction `list_active_tradable_symbols()` ne se contente plus de filtrer :
- `status='active'`
- `tradable=True`
- `bars_available=True`
- `asset_class='us_equity'`

Elle applique maintenant aussi, **si la colonne existe**, un filtre `history_status` autorisant uniquement :
- `ready`
- `pending`
- ou valeur absente / vide (fallback de compatibilité)

Les statuts suivants sont donc exclus de l’univers exploitable lorsqu’ils sont présents :
- `no_history`
- `provider_error`
- `suspended_or_stale`
- `excluded_by_policy`

#### `selector/alpha_scanner.py`
Le scanner a été aligné sur cette sémantique en deux niveaux :

1. **Lecture métadonnées**
   - ajout de `history_status` dans `METADATA_COLUMNS` ;
   - introspection du schéma `stock_metadata` via `inspect(self.engine)` ;
   - requête SQL adaptative qui ne sélectionne `history_status` que si la colonne existe ;
   - complétion des colonnes manquantes en `pd.NA` pour garder une API stable.

2. **Filtrage métier aval**
   - `_enrich_and_filter_equities()` exclut maintenant explicitement les symboles selon les raisons :
     - `history_no_history`
     - `history_provider_error`
     - `history_suspended_or_stale`
     - `history_excluded_by_policy`
   - les symboles `ready` et `pending` restent éligibles ;
   - `bars_available` reste conservé comme garde-fou historique ;
   - la sortie enrichie conserve `history_status` pour permettre des diagnostics aval.

3. **Préfiltrage SQL amont**
   - `_iter_eligible_symbol_chunks()` filtre aussi `history_status` côté SQL quand la colonne existe ;
   - il reste rétrocompatible si la colonne n’existe pas ;
   - il ajoute explicitement `sm.bars_available = 1` dans la présélection SQL.

### Pourquoi
Avant cette tranche, `history_status` existait en base mais n’était pas réellement utilisé par les consommateurs aval les plus critiques. On avait donc un statut plus riche côté ingestion, mais **pas encore de bénéfice opérationnel côté sélection d’univers**.

### Impact
- l’univers de symboles exploitable est plus cohérent avec les états réels d’ingestion ;
- un symbole en incident provider ou devenu stale ne pollue plus silencieusement les consommateurs aval ;
- les environnements de test SQLite sans `history_status` continuent de fonctionner.

## 2.2 Enrichissement du résumé run-level de l’import Alpaca

### Fichier modifié
- `dataIntegrityEngine/import_alpaca_bar.py`
- `tests/test_import_alpaca_bar.py`

### Ce qui a été fait
Le résumé retourné par `import_alpaca_bars()` a été enrichi avec des informations plus exploitables :

### Nouveaux champs
- `market_date`
- `existing_history_symbols`
- `first_import_symbols`
- `provider_error_symbols`
- `up_to_date_symbols`
- `max_calendar_gap_days`
- `max_trading_gap_days`
- `staleness_calendar_days_threshold`
- `staleness_trading_days_threshold`
- `history_status_counts`

### Breakdown `history_status_counts`
Le run compte explicitement les issues suivantes :
- `pending`
- `ready`
- `no_history`
- `provider_error`
- `suspended_or_stale`

### Comportement
- **succès d’import** → incrémente `ready`
- **vrai no-history provider** → incrémente `no_history`
- **incident technique provider** → incrémente `provider_error`
- **historique existant mais devenu stale** → incrémente `suspended_or_stale`
- **déjà à jour** → incrémente `up_to_date_symbols`

### Pourquoi
Le résumé précédent était utile, mais restait trop compact pour distinguer proprement :
- un premier import,
- une reprise incrémentale,
- un incident provider,
- un symbole stale,
- un symbole déjà à jour.

### Impact
On dispose maintenant d’un résumé beaucoup plus lisible pour :
- les logs,
- de futurs tableaux de bord,
- l’IHM,
- les scripts opérateur.

## 2.3 Raffinement de la logique de staleness

### Fichier modifié
- `dataIntegrityEngine/import_alpaca_bar.py`
- `tests/test_import_alpaca_bar.py`

### Ce qui a été fait
La logique précédente reposait sur un simple écart en jours calendaires.

Elle a été remplacée par une logique plus réaliste :

- ajout de `MAX_STALENESS_TRADING_DAYS = 5`
- ajout de `_coerce_to_date()`
- ajout de `_count_trading_days_between()`
- ajout de `_assess_staleness()`
- utilisation de `common.utils.is_trading_day()` pour compter les **séances ouvertes NYSE**

### Nouvelle règle
Le pipeline privilégie désormais :
- un seuil de **5 séances de marché** ;
- avec conservation d’un suivi de l’écart calendaire pour les logs et diagnostics.

### Pourquoi
Un simple delta calendaire produit des faux positifs autour :
- des week-ends,
- des jours fériés US,
- des périodes comme Thanksgiving.

### Impact
La staleness détectée est plus proche de la réalité opérationnelle d’un flux daily equities.

## 5. Décisions de conception retenues

### 5.1 `history_status` affine, `bars_available` sécurise
On conserve `bars_available` comme contrat historique de compatibilité, mais `history_status` devient maintenant réellement décisionnel là où c’est utile.

### 5.2 Compatibilité explicite avec schémas partiels
Le code ne suppose pas aveuglément que `history_status` existe. Il s’adapte au schéma détecté, ce qui évite de casser les tests SQLite ou des environnements de transition.

### 5.3 `pending` reste éligible
Le statut `pending` a été conservé comme éligible pour éviter de bloquer trop tôt certains flux aval pendant la phase de transition / backfill initial.

### 5.4 Staleness en séances de marché
Le critère en trading days est plus pertinent qu’un pur delta civil, tout en restant assez simple pour ne pas alourdir inutilement le pipeline.
