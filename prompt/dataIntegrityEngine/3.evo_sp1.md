## 1. Résumé exécutif

Le Sprint P1 a été enchaîné directement après les P0 sur les trois axes demandés :

1. **nettoyage du schéma brut `stock_bars`** ;
2. **validations OHLCV strictes dès l’ingestion Alpaca** ;
3. **refonte propre de l’audit sanitizeur en deux tables : `cleaning_audit_latest` + `cleaning_audit_runs`**.

La logique obtenue est plus sûre et plus lisible :

- la table brute ne stocke plus des types ambigus ou artificiellement forcés ;
- les barres OHLCV incohérentes sont rejetées avant insertion ;
- l’audit n’est plus un pseudo-log mutable :
  - `latest` sert de **snapshot courant par symbole** ;
  - `runs` sert de **journal append-only des exécutions**.

## 2. Changements réalisés

## P1.1 — Nettoyage du schéma `stock_bars`

### Fichiers modifiés
- `database/sql/stock/stock_bars.sql`
- `database/sql/truncate_all_tables.sql`

### Ce qui a été fait
- `symbol` passe à `VARCHAR(20)`.
- `trade_count` passe de `DECIMAL(20,8)` à `BIGINT UNSIGNED`.
- `volume` est explicitement `BIGINT UNSIGNED`.
- `vwa_price` devient **nullable**.
- ajout de `ingested_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP`.
- nettoyage des index :
  - contrainte d’unicité `(symbol, timeframe, timestamp)` ;
  - index `(symbol, timestamp)` ;
  - index `(timeframe, symbol, timestamp)`.

### Pourquoi
- `trade_count` n’est pas une mesure décimale : c’est un **compteur**.
- `vwa_price` peut être absent côté provider ; il ne faut plus l’inventer artificiellement.
- `ingested_at` redonne un minimum de traçabilité brute sans complexifier le pipeline.

### Impact métier
La table brute est maintenant plus fidèle à la réalité provider et plus exploitable pour le debug / backfill / audit.

## P1.2 — Validations OHLCV métier strictes à l’ingestion

### Fichiers modifiés
- `dataIntegrityEngine/import_alpaca_bar.py`
- `tests/test_import_alpaca_bar.py`

### Ce qui a été fait
Ajout d’une validation explicite dans `_build_bar_records()` :

- rejet si `timestamp` absent ;
- rejet si un des champs obligatoires est invalide (`open/high/low/close/volume/trade_count`) ;
- rejet si un prix OHLC est `<= 0` ;
- rejet si `high < max(open, low, close)` ;
- rejet si `low > min(open, high, close)` ;
- rejet si `volume < 0` ;
- rejet si `trade_count < 0` ;
- rejet si `vwap` est fourni mais `<= 0`.

En complément :

- ajout d’un sanitizeur entier non négatif pour `volume` / `trade_count` ;
- suppression du fallback artificiel `vwa_price = close_price` ;
- journalisation structurée des raisons de rejet via compteur `reasons={...}`.

### Pourquoi
Le schéma seul ne suffit pas à empêcher des barres **métier invalides** :

- un `high` inférieur au `close`,
- un `low` supérieur à l’`open`,
- un volume négatif,
- etc.

Il faut bloquer ces anomalies **avant** qu’elles polluent `stock_bars`, puis le sanitizeur, puis le screener.

### Impact métier
On évite de persister des barres daily techniquement insérables mais économiquement incohérentes.

## P1.3 — Refonte propre de l’audit en `latest + runs`

### Fichiers modifiés
- `database/sql/stock/cleaning_audit_latest.sql`
- `database/sql/stock/cleaning_audit_runs.sql`
- `database/sanitizer_db_ops.py`
- `dataIntegrityEngine/data_sanitizer_daily.py`
- `screener/db_io.py`
- `ihm/services/db_admin.py`
- `ihm/services/pipeline_runner.py`
- `database/sql/truncate_all_tables.sql`
- `doc/dataIntegrityEngine.md`
- `doc/database.md`
- `doc/DOC_TECHNIQUE.md`
- `doc/DOC_FONCTIONNELLE.md`
- `doc/corporate_actions.md`
- `tests/test_sanitizer_db_ops.py`
- `tests/test_data_sanitizer_daily.py`

### Nouveau modèle
#### `cleaning_audit_latest`
Un **snapshot par symbole** avec :
- `symbol` PK,
- `last_sync_date`,
- `missing_days_count`,
- `anomaly_count`,
- `status`,
- `error_message`,
- `latest_run_at`.

#### `cleaning_audit_runs`
Un **journal append-only** par exécution avec :
- `id` auto-incrémenté,
- `symbol`,
- `last_sync_date`,
- compteurs,
- `status`,
- `error_message`,
- `created_at`.

### Ce qui a été fait côté code
- `DataSanitizer` reflète désormais :
  - `cleaning_audit_latest`
  - `cleaning_audit_runs`
- `get_last_sync_date()` lit dans `latest`.
- `get_failed_audits()` lit les symboles failed depuis `latest`.
- `upsert_audit()` :
  - **insert** toujours un run dans `cleaning_audit_runs` ;
  - **insert/update** le snapshot courant dans `cleaning_audit_latest`.
- en cas d’échec sanitizeur, le message d’erreur formaté est persisté dans l’audit.
- le screener enrichit maintenant les scores depuis `cleaning_audit_latest`.
- l’IHM a été réalignée sur les nouvelles tables.

### Pourquoi c’est important
L’ancienne table mélangeait deux usages incompatibles :

- *dernier état connu* ;
- *historique des exécutions*.

Le résultat était un faux log, écrasé au fil de l’eau.

La séparation `latest + runs` corrige cela proprement :

- le pipeline lit vite le dernier état ;
- l’audit conserve enfin l’historique des runs ;
- les échecs gardent leur `error_message` pour diagnostic.

## 5. Décisions de conception retenues

### 5.1 `vwa_price` nullable
Le provider peut ne pas fournir de VWAP ; il vaut mieux stocker `NULL` que fabriquer une pseudo-VWAP égale au `close`.

### 5.2 validation stricte avant DB
Le bon endroit pour stopper une barre incohérente est **avant insertion dans `stock_bars`**, pas plus tard dans le sanitizeur.

### 5.3 `latest + runs` plutôt qu’une seule table enrichie
C’est plus simple, plus lisible et plus robuste :
- une table pour lire l’état courant ;
- une table pour historiser tous les runs.

### 5.4 stockage des `error_message`
Le statut `failed` seul n’est pas suffisant ; la persistance du message permet de rendre l’échec observable sans devoir replonger immédiatement dans les logs fichiers.
