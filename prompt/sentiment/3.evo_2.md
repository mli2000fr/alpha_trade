# Sprint 2 — Extension `event_sentiment`

_Date_: 2026-04-26

## 1. Objectif du sprint

Enchaîner après le Sprint 1 avec une proposition orientée :

1. **bootstrap 10 ans** ;
2. **features multi-horizons swing** ;
3. **calibration des poids sentiment / macro par backtest**.

Le sprint a été implémenté de manière **additive**, pour rester compatible avec l’architecture actuelle du projet, sans refactor global du screener, du selector ou du backtesting.

---

## 2. Résumé exécutif

Le Sprint 2 a été implémenté autour de trois axes complémentaires :

### A. Bootstrap historique long

Un service dédié reconstruit les features `event_sentiment` sur une longue plage historique à partir des tables déjà scorées (`news_raw`, `news_sentiment`, `macro_event_audit`) en **batchs de dates**, avec fenêtre tampon pour recalculer correctement les rollings.

### B. Features swing multi-horizons

Les tables et agrégations journalières ne se limitent plus au `1d`. Elles produisent désormais aussi des signaux sur :

- `3d`
- `5d`
- `10d`
- `20d`

ce qui est bien plus pertinent pour un style **swing trading cash**.

### C. Calibration des poids par backtest

Un calibrateur dédié explore des grilles de pondérations `quant / sentiment / macro`, calcule des métriques sur retours forward et exporte un classement des scénarios.

## 3.3 Pipeline recalculée avec fenêtre tampon

Fichier modifié :
- `event_sentiment/pipeline.py`

### Changement important

Le Sprint 1 avait aligné la pipeline sur les dates réellement scorées.

Le Sprint 2 complète cela avec une logique adaptée aux rollings :
- la pipeline recharge une **fenêtre tampon historique** (`feature_history_buffer_days`) ;
- recalcule les rollings ;
- filtre ensuite les résultats pour ne réécrire que les `impacted_trade_dates`.

### Pourquoi c’est nécessaire

Avec des colonnes `3d/5d/10d/20d`, recalculer uniquement la date brute n’est plus suffisant. Il faut aussi avoir accès aux jours précédents pour obtenir un rolling correct.

## 3.5 Service de bootstrap historique 10 ans

Nouveau fichier :
- `event_sentiment/history_backfill.py`

### Rôle

Reconstruire les features `ticker_daily_sentiment_features` et `sector_daily_sentiment_features` sur longue période à partir des données déjà scorées.

### Caractéristiques

- résolution automatique des bornes (`resolve_bounds`) ;
- fallback par défaut sur **10 ans** si `start_date` n’est pas fourni ;
- batchs de `trade_dates` ;
- relecture SQL sur une fenêtre tampon ;
- réécriture uniquement sur les dates cibles ;
- sortie structurée avec `run_summary`.

### Usage prévu

Exemple conceptuel :

```powershell
python -m event_sentiment.history_backfill --years 10 --batch-days 63
```

### Pourquoi cette approche est professionnelle

Pour un historique 10 ans :
- on évite un recalcul monolithique coûteux ;
- on obtient une exécution plus résiliente ;
- on prépare un vrai mode bootstrap exploitable en production.

## 3.6 Stabilisation avancée de `signal_aggregator`

Fichier modifié :
- `event_sentiment/signal_aggregator.py`

### Ce qui a été ajouté

#### A. Pondération multi-horizons configurable

Ajout dans `SentimentBoostConfig` :

- `ticker_horizon_weights`
- `sector_horizon_weights`

Defaults :
- ticker : `(1, 0.35), (3, 0.25), (5, 0.20), (10, 0.10), (20, 0.10)`
- secteur : `(1, 0.40), (3, 0.25), (5, 0.20), (10, 0.10), (20, 0.05)`

#### B. Validation des poids d’horizon

- pas de poids vide ;
- horizons strictement positifs ;
- triés ;
- sans doublons ;
- au moins un poids positif.

#### C. Composition multi-horizons

Nouvelles méthodes internes :
- `_latest_rows_by_key()`
- `_compose_horizon_signal()`
- `_aggregate_ticker_multi_horizon()`
- `_aggregate_sector_multi_horizon()`

### Comportement

Le `signal_aggregator` :
1. charge les colonnes multi-horizons si elles existent ;
2. compose un signal agrégé plus stable ;
3. fallback automatiquement sur l’agrégation historique fenêtrée si les colonnes multi-horizons ne sont pas disponibles.

### Bénéfice métier

Le score final devient moins sensible :
- aux spikes news d’une seule journée ;
- aux trous de couverture ;
- aux micro-variations de l’univers du jour.

C’est exactement ce qu’on veut pour un ranking swing robuste.

## 3.8 Calibration des poids sentiment/macro par backtest

Nouveau fichier :
- `backtesting/sentiment_calibration.py`

### Objectif

Évaluer une grille de scénarios de poids :
- `sentiment_weight`
- `macro_weight`
- `quant_weight`

sur des snapshots historiques stockés dans `stock_scores_history`, en les comparant aux retours futurs observés dans `stock_bars_daily`.

### Pipeline de calibration

1. charger les snapshots `stock_scores_history` ;
2. charger les prix futurs ;
3. calculer des retours forward (`5d`, `10d`, `20d`, etc.) ;
4. recomposer des scores candidats selon différents poids ;
5. mesurer pour chaque scénario :
   - rank IC ;
   - rendement moyen top-N ;
   - rendement moyen univers ;
   - spread top-vs-univers ;
   - score global agrégé ;
6. exporter un CSV de classement et un JSON du meilleur scénario.

### Résultat

Le module fournit maintenant :
- `SentimentCalibrationScenario`
- `SentimentCalibrationResult`
- `SentimentWeightCalibrator`

avec une méthode :
- `calibrate(...)`

### CLI backtesting

Fichier modifié :
- `backtesting/cli.py`

Nouvelle commande :
- `calibrate-sentiment-weights`

Exemple conceptuel :

```powershell
python -m backtesting calibrate-sentiment-weights --start 2018-01-01 --end 2025-12-31 --top-n 20 --horizons 5,10,20
```

### Pourquoi c’est utile

Cela permet de sortir du réglage “au doigt mouillé” des poids sentiment/macro et d’aller vers une calibration empirique basée sur le comportement réel du marché.

Pour votre cas d’usage :
- **swing trading** ;
- principalement **cash** ;
- historique potentiellement **10 ans** ;

### Ce qui devient meilleur

#### 1. Les signaux sont moins myopes

On ne regarde plus seulement le bruit du jour (`1d`), mais aussi la persistence du flux informationnel (`3d`, `5d`, `10d`, `20d`).

#### 2. Le bootstrap historique devient réaliste

Vous pouvez reconstruire proprement les features sans faire un run géant fragile et coûteux.

Vous pouvez comparer des scénarios :
- sentiment faible / macro faible ;
- sentiment fort / macro modéré ;
- quant dominant mais enrichi ;

et sélectionner ce qui fonctionne réellement sur vos horizons swing.

## 8. Recommandations pour Sprint 3

Voici la suite logique si vous voulez pousser le module vers un niveau encore plus institutionnel.

### 1. Historiser aussi les features sentiment elles-mêmes

Aujourd’hui la table de features est déjà par date, donc on peut reconstruire. Mais un audit encore plus fort pourrait stocker :
- `run_id`
- `rebuild_batch_id`
- `recompute_reason`

### 2. Calibration walk-forward stricte

Aujourd’hui la calibration est un bon outil de ranking de scénarios. L’étape suivante serait :
- train window / validation window / test window ;
- recalibration périodique ;
- contrôle de la stabilité des poids dans le temps.

### 3. Distinction news idiosyncratique vs macro régime

Il serait intéressant de séparer plus explicitement :
- signal société / earnings-like ;
- signal macro / sector regime ;
- signal régime de marché global.

### 4. Intégration directe au backtest portefeuille

La calibration actuelle mesure surtout la qualité du score vis-à-vis des retours forward. La suite logique :
- brancher automatiquement le meilleur scénario dans des backtests portefeuille complets ;
- mesurer Sharpe, drawdown, turnover, robustesse cash.

### 5. Gestion du coût informationnel / fraîcheur

Une amélioration très métier serait de moduler les signaux selon :
- fraîcheur de l’information ;
- nombre de sources ;
- fiabilité de la source ;
- risque événementiel proche (earnings blackout, FOMC, CPI, etc.).
