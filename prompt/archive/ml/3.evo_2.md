# Evolution 2 — Phase 3 expert

## Objectif
Cette phase 3 expert étend `modelFactory` sur quatre axes à forte valeur métier pour le swing trading cash :

1. **features trend / relative strength / regime** ;
2. **baseline LightGBM vs LSTM** ;
3. **bucket analysis sur probabilités calibrées** ;
4. **optimisation de la target par horizon swing**.

L’objectif est de faire passer `modelFactory` d’un pipeline LSTM daily propre mais encore V1 à une base beaucoup plus proche d’un workflow quant/ML pro :
- plus de contexte marché ;
- comparaison de modèles ;
- lecture business des probabilités ;
- sélection plus intelligente de l’horizon de prédiction.

## 1.2 Baseline LightGBM vs LSTM

### Fichiers
- `modelFactory/lightgbm_baseline.py`
- `modelFactory/trainer.py`
- `modelFactory/config.py`
- `modelFactory/cli.py`
- `requirements.txt`
- `pyproject.toml`

### Ce qui a été ajouté
- une baseline tabulaire `LightGBM` activable en option ;
- entraînement sur le `prepared_df` déjà construit par le pipeline ;
- calibration optionnelle Platt sur le split `val` ;
- métriques comparables à celles du LSTM ;
- bucket analysis côté baseline ;
- sauvegarde des résultats dans `metrics.json` sous :
  - `baseline_lightgbm`

### Philosophie retenue
La baseline LightGBM ne remplace pas le LSTM.
Elle sert à :
- comparer rapidement les architectures ;
- vérifier si le LSTM apporte réellement quelque chose ;
- détecter les cas où une approche tabulaire fait aussi bien, voire mieux.

### Pourquoi c’est clé
Sur des données actions daily avec peu d’observations par symbole, une baseline tabulaire bien conçue est souvent extrêmement compétitive.

## 1.3 Bucket analysis sur probabilités calibrées

### Fichiers
- `modelFactory/evaluation.py`
- `modelFactory/trainer.py`
- `modelFactory/lightgbm_baseline.py`
- `tests/test_model_factory_evaluation.py`

### Ce qui a été ajouté
- fonction `bucket_analysis()` ;
- analyse par buckets de conviction ;
- calcul par bucket de :
  - `count`
  - `proba_min`
  - `proba_max`
  - `proba_mean`
  - `hit_rate`
  - `avg_future_return`
  - `median_future_return`
- indicateur `monotonic_hit_rate`

### Où c’est utilisé
- dans les métriques finales LSTM (`val` et `test`) ;
- dans la baseline LightGBM.

### Pourquoi c’est business-critical
Ce n’est pas suffisant de savoir qu’un modèle a un bon AUC.
En portefeuille, tu veux savoir si :
- les hauts scores sont vraiment meilleurs ;
- les buckets de conviction sont monotones ;
- les meilleurs buckets génèrent un meilleur futur rendement moyen.

C’est ce qui transforme une probabilité ML en outil de sélection/sizing.

## 1.4 Optimisation de la target par horizon swing

### Fichiers
- `modelFactory/target_optimization.py`
- `modelFactory/trainer.py`
- `modelFactory/config.py`
- `modelFactory/cli.py`

### Ce qui a été ajouté
- une config `TargetOptimizationConfig` ;
- un scoring d’horizons candidats ;
- une sélection automatique du meilleur horizon swing avant entraînement ;
- persistance du résultat dans `metrics.json` sous :
  - `target_optimization`
- sauvegarde de l’horizon retenu dans `config.json` sous :
  - `selected_forecast_horizon`

### Logique actuelle du scoring
Pour chaque horizon candidat :
- on calcule la target correspondante ;
- on mesure :
  - `trade_rate`
  - `class_balance`
  - séparation moyenne entre rendements positifs et négatifs ;
- on construit un score simple favorisant :
  - suffisamment de trades ;
  - un dataset pas trop déséquilibré ;
  - une vraie séparation de rendement.

### Pourquoi c’est utile
Le meilleur horizon n’est pas toujours `5 jours`.
Selon le ticker, le régime et les seuils de target, le signal peut être plus propre sur :
- 3 jours,
- 5 jours,
- 10 jours,
- 15 jours.

Cette étape évite de figer un horizon arbitraire partout.

# 5. Commandes utiles

## 5.1 Entraînement expert avec features enrichies
```powershell
python -m modelFactory --mode train --feature-set expert --benchmark-symbol SPY
```

## 5.2 Entraînement expert + calibration + walk-forward
```powershell
python -m modelFactory --mode train --feature-set expert --benchmark-symbol SPY --calibration-method platt --walkforward --wf-min-train-size 756 --wf-val-size 126 --wf-test-size 126 --wf-step-size 126 --wf-max-splits 3
```

## 5.3 Comparaison LightGBM vs LSTM
```powershell
python -m modelFactory --mode train --feature-set expert --compare-lightgbm --lgbm-max-depth 4 --lgbm-n-estimators 200 --lgbm-learning-rate 0.05
```

# 6. Impact métier

## 6.1 Pour la sélection des trades
Le modèle a maintenant plus de contexte pour distinguer :
- un titre fort dans un marché fort ;
- un titre fort contre marché ;
- un faux signal dans un régime risk-off.

## 6.2 Pour l’interprétation des probabilités
La bucket analysis permet enfin de répondre à des questions métier utiles :
- les proba hautes correspondent-elles vraiment à de meilleurs trades ?
- le top bucket surperforme-t-il les buckets faibles ?
- la calibration aide-t-elle à trier les bons signaux ?

## 6.3 Pour la gouvernance du modèle
La baseline LightGBM réduit le risque de “sur-vendre” le LSTM.
Tu peux désormais vérifier si la complexité séquentielle est justifiée.

## 6.4 Pour l’horizon swing
L’optimisation de target évite de figer un horizon unique arbitraire sur tous les symboles.

# 7. Compatibilité et limites

## Compatibilité préservée
- CLI `train|predict` conservé ;
- pipeline LSTM toujours cœur de production ;
- persistance SQL inchangée pour `model_predictions` ;
- intégration `risk_management` inchangée.

## Limites actuelles
- la baseline LightGBM est aujourd’hui utilisée comme **comparaison**, pas comme artefact de prédiction principal ;
- l’optimisation d’horizon reste volontairement simple et heuristique ;
- pas encore de comparaison multi-architecture persistée en base avec séparation explicite des architectures ;
- pas encore de benchmark multi-symboles global.
