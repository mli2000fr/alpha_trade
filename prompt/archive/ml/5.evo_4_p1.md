# Evolution 4 — Priorité 1 implémentée

## Objectif
Cette note archive ce qui a été effectivement implémenté pour la **priorité 1** de la phase 4 dans `modelFactory` :

1. optimisation jointe de la target sur la grille **horizon + seuil haut + seuil bas** ;
2. optimisation du **decision_threshold** sur validation ;
3. enrichissement des métriques business orientées **trades réellement pris** ;
4. persistance claire des paramètres sélectionnés dans les artefacts.

Le contexte métier visé reste :
- actions daily ;
- swing trading cash ;
- usage principal **long / no-trade** ;
- importance forte de la calibration et de la densité de signaux.

# 2. Ce qui a été implémenté

## 2.1 Nouvelle configuration dédiée au sweep du seuil de décision
Dans `modelFactory/config.py`, une nouvelle dataclass `ThresholdOptimizationConfig` a été ajoutée.

### Champs ajoutés
- `enabled`
- `candidate_decision_thresholds`
- `min_action_rate`
- `max_action_rate`
- `min_precision_long`

### Pourquoi c’est utile
Le modèle ne doit plus seulement apprendre une target correcte ; il doit aussi choisir **à partir de quel niveau de probabilité un signal devient exploitable**.

### Validation ajoutée
Le code vérifie désormais :
- que la liste des seuils candidats n’est pas vide ;
- que tous les seuils sont dans `]0, 1[` ;
- que `min_action_rate <= max_action_rate` ;
- que les bornes sont dans `[0, 1]`.

---

## 2.2 Assouplissement contrôlé de la grille target
Dans `TargetOptimizationConfig`, la validation des couples `candidate_up_thresholds` / `candidate_down_thresholds` a été rendue plus réaliste.

### Avant
La validation imposait implicitement que **toutes** les combinaisons `down <= up` soient valides, ce qui est trop restrictif pour une vraie grille.

### Maintenant
La config accepte une grille **partiellement valide**, tant qu’il existe **au moins une** combinaison exploitable avec `down <= up`.

### Pourquoi c’est important
Pour une optimisation réelle, il est normal d’avoir une grille où certaines combinaisons sont ignorées et d’autres retenues.

## 2.7 Intégration dans `trainer.py`
Le flux d’entraînement mono-symbole a été enrichi en deux temps.

### A. Avant préparation finale des données
Si `cfg.target_optimization.enabled` :
- le pipeline choisit le meilleur triplet :
  - `forecast_horizon`
  - `target_up_threshold`
  - `target_down_threshold`
- puis reconstruit `effective_cfg.data` avec ces paramètres.

### B. Après entraînement du meilleur checkpoint
Sur le split de validation :
- les probabilités sont récupérées ;
- si possible, elles sont calibrées ;
- un sweep des `candidate_decision_thresholds` est exécuté ;
- le meilleur seuil est choisi selon les contraintes métier et un score business ;
- les métriques finales `val` et `test` sont recalculées avec le seuil retenu.

# 3. Logique exacte du sweep de `decision_threshold`

## Entrées
- probabilités de validation (calibrées si possible) ;
- labels de validation ;
- `future_return` de validation ;
- seuils candidats ;
- contraintes métier.

## Contraintes appliquées
Un seuil candidat est rejeté si :
- `coverage_at_threshold < min_action_rate`
- `coverage_at_threshold > max_action_rate`
- `precision_long < min_precision_long`

## Sélection
Parmi les candidats valides, le meilleur est choisi selon un score business simple.

### Score utilisé
Le score métier actuel favorise :
- la précision des signaux ;
- une couverture non nulle ;
- un bonus si les rendements conditionnels sont positifs ;
- un bonus léger si le `hit_rate_on_actions` est favorable.

### Fallback
Si aucun seuil candidat ne passe les contraintes :
- on retombe proprement sur `cfg.data.decision_threshold`.

# 5. Compatibilité et choix de design

## Compatibilité préservée
- `optimize_target_horizon()` est toujours disponible ;
- le LSTM reste le cœur du pipeline ;
- `predictor.py` continue d’utiliser `decision_threshold` depuis `config.json` ;
- les anciens appels CLI restent fonctionnels.

## Choix volontairement prudent
L’optimisation est maintenant **jointe au sens fonctionnel**, mais reste **séquentielle dans le pipeline** :
1. sélection de la target `(horizon, up, down)` ;
2. entraînement du modèle ;
3. sélection du `decision_threshold` sur validation calibrée.

C’est un compromis robuste pour une phase 4.1 :
- plus puissant que l’existant ;
- plus simple à maintenir ;
- moins coûteux qu’une recherche totalement imbriquée sur toutes les dimensions.
