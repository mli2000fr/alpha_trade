# Evolution 4 — Suite priorité 4 : sélection automatique du champion

## Objectif
Cette note archive l’implémentation de la **sélection automatique du champion** dans `modelFactory`.

L’objectif était de transformer la logique actuelle :
- ranking des challengers ;
- LSTM champion par défaut ;
- routage multi-artefacts déjà préparé ;

vers une vraie gouvernance capable de :
1. décider automatiquement quel modèle doit être servi ;
2. ne sélectionner que les modèles **réellement inférables** ;
3. persister ce choix dans les artefacts symbole ;
4. faire suivre ce choix au `predictor.py`.

Le principe retenu a été volontairement professionnel et pragmatique :
- sélection auto activable par config/CLI ;
- éligibilité stricte selon le backend d’inférence réellement disponible ;
- `lightgbm` / `catboost` locaux restent classés mais **non sélectionnables** tant que leur inférence locale dédiée n’est pas implémentée ;
- `lstm_attention` et `global_model` sont aujourd’hui les vrais candidats à l’auto-sélection.

# 2. Ce qui a été implémenté

## 2.1 Nouvelle config `ChampionSelectionConfig`
Dans `modelFactory/config.py`, une nouvelle dataclass a été ajoutée :
- `ChampionSelectionConfig`

### Champs ajoutés
- `enabled`
- `allow_auto_selection`
- `default_champion`
- `selection_metric`

### Valeurs supportées
`default_champion` accepte :
- `lstm_attention`
- `lightgbm`
- `catboost`
- `global_model`

`selection_metric` accepte :
- `selection_score`
- `business_score`
- `auc`

### Pourquoi c’est important
La gouvernance du champion devient maintenant une notion explicite,
au lieu d’être codée implicitement dans `trainer.py`.

### Effet

# 3. Politique d’éligibilité retenue

## 3.1 Principe
Un modèle n’est **pas sélectionnable automatiquement** juste parce qu’il a un bon score.
Il doit aussi être **réellement serviable en inférence**.

## 3.2 Modèles éligibles aujourd’hui
### `lstm_attention`
Éligible si :
- le statut est `completed` ;
- la route d’artefacts contient :
  - `checkpoint_path`
  - `scaler_path`
  - backend `lstm_attention`

### `global_model`
Éligible si :
- le statut est `completed` ;
- la route contient :
  - `config_path`
  - `model_path`
  - backend `global_tabular`

## 3.3 Modèles non éligibles aujourd’hui
### `lightgbm`
### `catboost`
Ils restent :
- évalués ;
- classés ;
- visibles dans les artefacts ;

mais ne sont pas encore sélectionnables automatiquement,
car l’inférence locale dédiée n’est pas encore implémentée.

### Pourquoi ce choix est bon
Cela évite une erreur de gouvernance classique :
- élire un modèle “meilleur en score”,
- mais impossible à servir proprement en production.

# 4. Logique de sélection automatique

## 4.1 Si l’auto-sélection est désactivée
Le système garde :
- `default_champion`
- `selection_mode = "default_champion"`

## 4.2 Si l’auto-sélection est activée
Le système :
1. annote chaque challenger avec :
   - `selection_eligible`
   - `eligibility_reason`
2. filtre les modèles éligibles ;
3. score les candidats selon `selection_metric` ;
4. choisit le meilleur ;
5. en cas d’égalité, favorise le `default_champion`.

## 4.3 Si aucun challenger n’est éligible
Le système retombe proprement sur :
- `default_champion`
- `selection_mode = "fallback_default_champion"`

---

# 5. Métriques de sélection supportées

## `selection_score`
C’est la valeur prioritaire si elle existe déjà sur le challenger.
Sinon le système retombe sur :
- `threshold_business_score`
- puis `auc`

## `business_score`
Favorise explicitement :
- `selection_score`
- sinon `threshold_business_score`
- sinon `auc`

## `auc`
Force la sélection principalement sur l’AUC de test/validation.

### Pourquoi cette flexibilité est utile
Tu peux maintenant choisir si tu veux :
- un champion orienté score métier ;
- ou un champion orienté qualité technique pure.

# 6. Intégration dans `trainer.py`

## Nouveau comportement
Le `train_symbol()` n’impose plus mécaniquement :
- `architecture_selected = "lstm_attention"`

À la place :
1. il construit `artifact_routes.models` ;
2. il construit le dict `challengers` ;
3. il appelle `select_champion()` ;
4. il récupère :
   - `selected_model`
   - `selection_mode`
   - challengers annotés
5. il persiste ces données dans `config.json` et `metrics.json`.

## Effet concret
Même avant injection du global model :
- la sélection auto existe déjà ;
- mais comme `lightgbm` et `catboost` sont inéligibles,
- `lstm_attention` reste naturellement champion.

---

# 7. Intégration dans `orchestrator.py`

## Nouveau comportement après injection du `global_model`
Quand le challenger global est injecté dans les artefacts symbole,
l’orchestrateur ne se contente plus de recalculer le ranking.

Il :
1. reconstruit le map `challengers` ;
2. met à jour `artifact_routes.models.global_model` ;
3. appelle `select_champion()` ;
4. recalcule :
   - `architecture_selected`
   - `artifact_routes.selected_model`
   - `selection_mode`
   - `metrics["champion"]`
   - `challengers.ranking`

### Conséquence
Si `global_model` est :
- complété ;
- routable ;
- meilleur selon la métrique choisie ;

alors il peut devenir automatiquement le champion servi.

# 8. Intégration dans `predictor.py`

## Comportement induit
`predictor.py` suivait déjà `artifact_routes.selected_model`.
Avec cette évolution, il suit maintenant naturellement le champion auto-sélectionné,
à condition qu’il soit éligible et routable.

### Cas couverts aujourd’hui
- `lstm_attention`
- `global_model`

### Cas encore non couverts
- `lightgbm` local
- `catboost` local

Ces deux modèles restent donc volontairement non éligibles à la sélection auto.

# 12. Ce que cette suite change vraiment

## Avant
Le pipeline savait :
- comparer ;
- classer ;
- préparer le routage ;

mais le champion restait essentiellement déterminé par convention.

## Maintenant
Le pipeline sait :
- appliquer une politique de sélection ;
- vérifier l’éligibilité réelle à l’inférence ;
- choisir automatiquement le meilleur modèle servi ;
- persister ce choix proprement dans les artefacts.

---

# 13. Verdict expert
Cette évolution est la vraie couche de **gouvernance de production** qui manquait.

## Pourquoi c’est important
Un bon pipeline ML de trading ne doit pas seulement :
- entraîner des modèles ;
- produire des scores ;

il doit aussi savoir :
- **quel modèle servir réellement** ;
- **pourquoi** ;
- **avec quelle traçabilité**.

## Ce que cette version apporte
- une sélection automatique sérieuse ;
- une notion d’éligibilité technique ;
- une cohérence parfaite avec le predictor ;
- une base saine pour les prochaines étapes.

## Prochaine suite logique
La prochaine étape naturelle devient :
1. rendre `lightgbm` / `catboost` locaux inférables eux aussi ;
2. puis permettre une auto-sélection complète sur tous les challengers ;
3. éventuellement enrichir le score de champion avec plus de dimensions régime / stabilité / densité de trades.
