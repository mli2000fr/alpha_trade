# Evolution 1 — Calibration + target swing cash + walk-forward

## Objectif
Cette évolution implémente le trio prioritaire pour `modelFactory` :

1. **calibration des probabilités** ;
2. **target swing cash avec seuil / no-trade** ;
3. **validation walk-forward**.

L’objectif est d’améliorer la qualité des probabilités consommées par `risk_management`, d’aligner la target sur un usage **cash long / no-trade**, et d’obtenir une validation plus robuste sur séries temporelles financières.

## 1.2 Target swing cash avec seuil / no-trade

### Fichiers
- `modelFactory/config.py`
- `modelFactory/features.py`
- `modelFactory/dataset.py`
- `modelFactory/cli.py`
- `modelFactory/predictor.py`

### Nouveau principe
Le mode `swing_cash` permet de construire une target orientée **long / no-trade**, sans forcer le modèle à apprendre sur des mouvements trop faibles.

### Nouveau comportement de la target
Dans `build_target()` :

- mode `binary` :
  - `1` si `future_return > positive_threshold`
  - `0` sinon

- mode `swing_cash` :
  - `1` si `future_return >= target_up_threshold`
  - `0` si `future_return <= target_down_threshold`
  - `NaN` entre les deux → **zone neutre / no-trade**, ignorée à l’entraînement

### Pourquoi c’est mieux pour ton cas
Pour du swing cash, beaucoup de mouvements à horizon 5 jours sont trop faibles pour justifier une entrée.
Le mode `swing_cash` évite de polluer l’apprentissage avec du bruit non exploitable.

### Décision en inférence
En inférence :
- `predicted_proba` devient la probabilité **calibrée** si un calibrateur est disponible ;
- `predicted_class = 1` si `predicted_proba >= decision_threshold` ;
- sinon `predicted_class = 0`.

### Interprétation recommandée
Dans ce mode, `predicted_class = 0` doit être lu comme :
- **pas de signal long / no-trade**, et non pas forcément “short”.

### Colonnes de sortie enrichies en mémoire
Le `DataFrame` retourné par `predict_symbol()` inclut maintenant aussi :
- `raw_proba`
- `decision_threshold`
- `signal_label` (`long` / `no_trade`)
- `calibration_method`

La persistance SQL reste compatible car `insert_predictions()` continue d’écrire seulement :
- `symbol`
- `prediction_date`
- `predicted_proba`
- `predicted_class`
- `run_id`

## 1.3 Validation walk-forward

### Fichiers
- `modelFactory/config.py`
- `modelFactory/dataset.py`
- `modelFactory/trainer.py`
- `modelFactory/cli.py`

### Ce qui a été ajouté
- une config dédiée `WalkForwardConfig` ;
- un générateur de splits chronologiques `generate_walk_forward_splits()` ;
- une évaluation walk-forward avant l’entraînement final du modèle de production ;
- agrégation des métriques par split :
  - moyenne
  - écart-type
  - détail par split

### Principe retenu
Le walk-forward est utilisé comme **outil d’évaluation**, pas comme source d’artefact de production.

Le flux est donc :
1. préparer `features + target` ;
2. si activé, lancer plusieurs folds walk-forward ;
3. agréger les métriques ;
4. entraîner ensuite le modèle final standard sur le split principal ;
5. sauvegarder les artefacts finaux de prod.

### Pourquoi ce choix est bon
- tu gardes un seul artefact de prod clair par symbole ;
- tu obtiens une vision de robustesse multi-régimes ;
- tu ne casses pas le contrat actuel `load_training_run()` / `predict_symbol()`.

# 3. Nouveau comportement du training

## 3.1 Évaluation finale
Après `trainer.fit()` :
- le meilleur checkpoint est rechargé ;
- les sorties `val` sont collectées ;
- le calibrateur est appris sur `val` ;
- les métriques `val` et `test` sont recalculées sur le **best checkpoint** ;
- les métriques enrichies sont sauvegardées dans `metrics.json`.

## 3.2 Persistance
Le `config.json` sauvegarde désormais aussi :
- la config `calibration`
- la config `walk_forward`
- `calibrator_path`

Le `metrics.json` contient désormais :
- `val`
- `test`
- `walk_forward`

## 3.3 Base SQL
La persistance SQL reste compatible :
- `model_metrics` continue d’enregistrer les métriques usuelles (`loss`, `directional_accuracy`, `precision`, `recall`, `auc`) ;
- le résumé walk-forward est sauvegardé côté DB avec `split_name = "wf"` si disponible ;
- les métriques avancées (`brier_score`, `ece`, `action_rate`, etc.) restent dans `metrics.json`.

# 5. Impact métier

## 5.1 Pour `risk_management`
`predicted_proba` devient plus exploitable si la calibration est activée.
C’est particulièrement utile si tu l’utilises comme proxy de conviction.

## 5.2 Pour le swing cash
Le pipeline est désormais plus aligné avec une logique :
- **entrer seulement quand le move anticipé est suffisamment fort** ;
- sinon rester en cash.

## 5.3 Pour le backtesting
La validation walk-forward permet une lecture plus honnête de la stabilité du modèle à travers différents régimes de marché.

# 6. Compatibilité et limites

## Compatibilité préservée
- CLI `train|predict` conservé ;
- schéma SQL `model_predictions` inchangé ;
- schéma SQL `model_metrics` inchangé ;
- anciens artefacts encore tolérés côté `predictor` si aucun calibrateur n’existe.

## Limites actuelles
- `predicted_class = 0` reste un entier binaire en DB, donc on encode la logique cash sous la forme **not-long / no-trade** ;
- la calibration actuelle implémente **Platt scaling** mais pas isotonic ;
- le walk-forward entraîne plusieurs modèles temporaires et peut coûter du temps CPU/GPU si activé sur un grand univers.
