# Evolution 5 — Inférence locale LightGBM / CatBoost et gouvernance multi-modèles complète

## Objectif
Cette évolution finalise la gouvernance multi-modèles de `modelFactory` en ajoutant l’**inférence locale réelle** pour :
- `lightgbm`
- `catboost`

Jusqu’ici, ces challengers étaient :
- entraînés ;
- scorés ;
- visibles dans les artefacts ;
- classés dans le ranking ;

mais **non sélectionnables automatiquement** car l’inférence locale dédiée n’existait pas encore.

Avec cette suite :
1. les modèles tabulaires locaux sont persistés proprement ;
2. `predictor.py` sait les charger et les exécuter ;
3. `champion_selection.py` les considère désormais comme **éligibles** ;
4. la gouvernance auto peut enfin arbitrer entre :
   - `lstm_attention`
   - `lightgbm`
   - `catboost`
   - `global_model`

# 2. Ce qui a été implémenté

## 2.1 Persistance des artefacts tabulaires locaux
Dans `modelFactory/tabular_baseline.py`, la baseline tabulaire supporte maintenant un `artifact_dir` optionnel.

Quand il est fourni, la baseline :
- sérialise le modèle entraîné dans :
  - `lightgbm_model.pkl`
  - `catboost_model.pkl`
- sérialise le calibrateur si présent dans :
  - `lightgbm_calibrator.pkl`
  - `catboost_calibrator.pkl`
- retourne des métadonnées d’inférence :
  - `artifact_paths`
  - `selected_decision_threshold`
  - `feature_columns`
  - `inference_backend`

### Pourquoi c’est important
Le pipeline n’a plus seulement des métriques de comparaison ; il possède maintenant les **artefacts réellement servis** pour les challengers locaux.

---

## 2.2 Wrappers LightGBM / CatBoost enrichis
Dans :
- `modelFactory/lightgbm_baseline.py`
- `modelFactory/catboost_baseline.py`

les wrappers propagent désormais `artifact_dir` au helper commun.

### Effet
Le `trainer` peut demander explicitement :
- l’entraînement de la baseline ;
- la persistance disque ;
- le retour d’un contrat d’inférence prêt à router.

---

## 2.3 Publication des routes d’inférence locales dans `trainer.py`
Dans `modelFactory/trainer.py`, le `train_symbol()` :
- persiste désormais les artefacts tabulaires dans le dossier symbole ;
- renseigne `artifact_routes.models.lightgbm` avec :
  - `model_path`
  - `calibrator_path`
  - `config_path`
  - `feature_columns`
  - `selected_decision_threshold`
  - `inference_backend = "lightgbm_tabular"`
- renseigne `artifact_routes.models.catboost` avec le même schéma et :
  - `inference_backend = "catboost_tabular"`

### Effet
Le `config.json` symbole contient maintenant des routes complètes pour les trois familles locales :
- `lstm_attention`
- `lightgbm`
- `catboost`

---

## 2.4 Éligibilité champion étendue dans `champion_selection.py`
Dans `modelFactory/champion_selection.py`, la politique d’éligibilité a été complétée.

### `lightgbm`
Éligible si :
- statut `completed` ;
- backend `lightgbm_tabular` ;
- `model_path` présent ;
- `config_path` présent.

### `catboost`
Éligible si :
- statut `completed` ;
- backend `catboost_tabular` ;
- `model_path` présent ;
- `config_path` présent.

### Conséquence
La sélection automatique n’est plus limitée à :
- `lstm_attention`
- `global_model`

Elle couvre maintenant aussi les challengers locaux tabulaires quand les artefacts nécessaires existent réellement.

---

## 2.5 Inférence locale ajoutée dans `predictor.py`
`modelFactory/predictor.py` a été étendu pour :
- résoudre les routes `lightgbm` et `catboost` dans `_resolve_selected_model_route()` ;
- charger un modèle picklé local ;
- reconstruire le calibrateur tabulaire si présent ;
- appliquer le `selected_decision_threshold` propre au challenger ;
- produire le même format de sortie que les autres backends.

### Nouveau helper tabulaire
La logique d’inférence tabulaire a été factorisée dans un helper commun interne qui gère :
- chargement modèle ;
- chargement calibrateur ;
- préparation des features ;
- contrôle des colonnes nécessaires ;
- application du seuil de décision ;
- persistance optionnelle des prédictions.

### Cas désormais supportés dans `predictor.py`
- `lstm_attention`
- `lightgbm`
- `catboost`
- `global_model`

# 4. Ce que cela change dans la gouvernance

## Avant
Le système savait :
- entraîner des challengers tabulaires locaux ;
- les évaluer ;
- les classer ;

mais il ne pouvait pas les **servir**.
Donc la gouvernance les laissait volontairement hors sélection automatique.

## Maintenant
Le système sait :
- entraîner ;
- persister ;
- router ;
- charger ;
- calibrer ;
- prédire ;
- sélectionner automatiquement ;

pour l’ensemble des familles de modèles aujourd’hui disponibles.

### En pratique
Si `lightgbm` ou `catboost` :
- finissent en `completed` ;
- disposent de leur route locale complète ;
- ont le meilleur score selon la métrique choisie ;

alors ils peuvent devenir le **champion servi en production**.

# 7. Verdict technique

Cette évolution clôt la boucle de gouvernance multi-modèles côté local.

## Ce qui est maintenant vrai
Le pipeline sait non seulement comparer les modèles, mais aussi décider **lequel est réellement servi**, parmi :
- `lstm_attention`
- `lightgbm`
- `catboost`
- `global_model`

avec :
- traçabilité dans les artefacts ;
- cohérence entre `trainer.py`, `champion_selection.py` et `predictor.py` ;
- sélection basée sur un modèle réellement inférable.

## Gain principal
La gouvernance n’est plus bridée par une asymétrie entre :
- modèles évalués ;
- modèles servables.

Autrement dit :
- **ce qui gagne peut maintenant être servi**.
