## 1. Synthèse exécutive

Le module `dataIntegrityEngine` est déjà **cohérent dans son intention** :

1. peupler `stock_metadata` ;
2. ingérer les barres Alpaca dans `stock_bars` ;
3. produire une table daily nettoyée `stock_bars_daily` ;
4. alimenter ensuite `stock_scores`, `selector`, `modelFactory` et le reste du pipeline.

Pour un usage **swing trading cash** sur actions US, avec **jusqu’à 10 ans de daily par symbole**, le design actuel est globalement exploitable, mais il présente plusieurs risques importants :

- confusion entre **absence réelle de données** et **incident réseau/provider** ;
- incrémental du sanitizeur **trop court**, qui ne recalcule pas une fenêtre suffisante pour garantir des features cohérentes ;
- propagation aval d’un **faux état “propre”** quand le sanitizeur échoue ;
- usage de `adjustment="all"` qui n’est **pas le meilleur choix métier** pour ton cas ;
- schéma et audit encore un peu “prototype” sur certains points.

### Décision recommandée sur les prix

### ✅ Recommandation finale : utiliser **`adjustment="split"`** comme **série canonique unique**

Je recommande **de ne conserver qu’une seule série daily split-adjusted** dans le projet.

**Pourquoi `split` et pas `all` ?**

Pour du **swing trading cash** orienté :
- tendance,
- supports/résistances,
- MA50 / MA200,
- ATR,
- proximité du plus haut 52 semaines,
- exécution réelle sur actions US,

il faut **corriger les splits** mais **préserver les effets économiques réels des dividendes** dans la série de prix observée.

`adjustment="all"` est utile pour une logique de **total return** ou d’analyse académique de performance. En revanche, pour un moteur orienté **stock picking / chart structure / exécution réelle**, il introduit une distorsion légère mais inutile :

- les historiques deviennent artificiellement “lissés” autour des dividendes ;
- certaines métriques de momentum / trend / gaps / range ne reflètent plus exactement le comportement de prix vu par le marché ;
- on éloigne la donnée de la lecture chartiste et de l’exécution effective.

### Règle cible

- `stock_bars` : **daily Alpaca split-adjusted uniquement** ;
- `stock_bars_daily` : **même convention `split`**, nettoyée et auditée ;
- pas de variante parallèle `raw` / `all` / `dividend` ;
- `adj_close = close` si on reste sur une seule série canonique simple.

## 3. Cartographie rapide du flux actuel

### Flux observé

1. `import_alpaca_assets.py`
   - charge l’univers Alpaca vers `stock_metadata`

2. `import_alpaca_bar.py`
   - sélectionne les symboles `active + tradable + bars_available + us_equity`
   - récupère l’historique Alpaca
   - upsert dans `stock_bars`
   - met `bars_available=False` si aucun historique n’est récupéré

3. `data_sanitizer_daily.py`
   - charge les 1D depuis `stock_bars`
   - bâtit un calendrier depuis `SPY`
   - forward-fill les jours manquants
   - calcule `daily_return`
   - détecte des anomalies
   - upsert dans `stock_bars_daily`
   - met à jour `cleaning_audit_log`
   - recopie les compteurs vers `stock_scores`

4. aval
   - `selector/alpha_scanner.py` lit `stock_bars_daily` + `stock_scores`
   - `modelFactory/data_loader.py` lit `stock_bars_daily`

## 4. Constats critiques et recommandations

## P0 — à traiter avant de reconstruire la base propre

### P0.1 — Le choix `adjustment="all"` n’est pas le plus adapté au projet

**Constat**
- `service/alpaca/clientAlpaca.py` appelle Alpaca avec `adjustment="all"`.
- Cette hypothèse est propagée dans :
  - `dataIntegrityEngine/data_sanitizer_daily.py`
  - `database/sanitizer_db_ops.py`
  - `doc/dataIntegrityEngine.md`
  - `doc/DOC_FONCTIONNELLE.md`
  - `doc/DOC_TECHNIQUE.md`
  - `doc/corporate_actions.md`

**Impact métier**
Pour une stratégie swing cash centrée sur la structure du prix, les dividendes ne doivent pas “réécrire” artificiellement le passé. Les splits doivent être neutralisés, les dividendes non.

**Recommandation**
Passer partout à **`adjustment="split"`** et considérer cette série comme la vérité unique du projet.

---

### P0.2 — Un timeout Alpaca peut être interprété comme “aucune donnée disponible”

**Constat**
Dans `service/alpaca/clientAlpaca.py`, après trop de timeouts, `fetch_bars()` retourne `all_bars`, potentiellement vide.
Ensuite, dans `dataIntegrityEngine/import_alpaca_bar.py`, si le résultat est vide et que le symbole n’existe pas encore dans `stock_bars`, le code appelle `update_bars_available_false(symbol)`.

**Problème**
Un incident réseau transitoire peut donc :
- faire croire qu’un symbole n’a pas d’historique ;
- exclure à tort ce symbole de tout l’univers futur.

**Impact**
Très important. C’est un risque de faux négatif durable sur l’univers tradable.

**Recommandation**
Séparer explicitement :
- `no_data` réel provider ;
- `transport_error` / `timeout_exhausted` ;
- `partial_success`.

Et surtout :
- **ne jamais muter `bars_available=False` sur un échec technique** ;
- ne le faire que sur un statut provider explicitement fiable.

---

### P0.3 — Le sanitizeur incrémental ne recalcule pas une fenêtre suffisante

**Constat**
Dans `DataSanitizer._process_symbol()` :
- `start_date = last_sync + 1 jour`
- seules les nouvelles lignes sont relues depuis `stock_bars`
- `daily_return`, anomalies et forward-fill sont recalculés uniquement sur la nouvelle tranche

**Problème**
Cela ne suffit pas pour garantir la cohérence temporelle quand :
- une barre historique est corrigée par le provider ;
- un split est intégré plus tard ;
- une anomalie dépend d’une fenêtre glissante ;
- la dernière journée recalculée dépend du `prev_close` d’une barre précédente modifiée.

**Impact**
Risque de divergence silencieuse entre `stock_bars` et `stock_bars_daily`.

**Recommandation**
Après reset, adopter une règle simple et robuste :

- à chaque run daily, **retraiter au minimum une fenêtre glissante de 252 séances** par symbole ;
- idéalement **400 jours calendaires** pour couvrir weekends/jours fériés ;
- upsert complet de cette fenêtre dans `stock_bars_daily`.

Pour ton volume (10 ans daily), ce coût est totalement acceptable.

---

### P0.4 — En cas d’échec sanitizeur, `stock_scores` reçoit quand même `0 anomalies / 0 manquants`

**Constat**
Dans `dataIntegrityEngine/data_sanitizer_daily.py`, le bloc d’exception construit :
- `status='failed'`
- `missing_days=0`
- `anomaly_count=0`

Puis appelle quand même `sync_audit_to_stock_scores(...)`.

**Problème**
Le downstream peut voir un symbole comme “propre” alors que le sanitizeur a échoué.

**Impact**
Critique : le `selector` peut conserver un titre sur des données daily obsolètes ou incomplètes.

**Recommandation**
Ne plus propager `0/0` lors d’un échec.

Deux options propres :
1. ajouter un champ explicite `sanitizer_status` dans `stock_scores` et filtrer `status='success'` ;
2. plus simple : sur échec, **ne pas mettre à jour** `stock_scores`, ou écrire des sentinelles bloquantes (`NULL` / très grand nombre) + exclusion explicite dans le scanner.

Pour un design propre, je recommande :
- `stock_scores.sanitizer_status`
- `stock_scores.last_updated_audit`
- filtre dur côté `selector` : seuls les symboles `sanitizer_status='success'` sont éligibles.

---

### P0.5 — Le forward-fill doit être plafonné

**Constat**
Le sanitizeur forward-fill toute date du calendrier `SPY` manquante pour un symbole.

**Problème**
Pour une action suspendue, illiquide, radiée ou avec historique incomplet, on peut fabriquer trop de jours synthétiques consécutifs.

**Impact métier**
- faux ATR bas ;
- fausse stabilité ;
- faux momentum ;
- univers potentiellement pollué par des titres “morts”.

**Recommandation**
Introduire une règle simple :
- autoriser seulement **1 à 3 séances consécutives** de fill ;
- au-delà, considérer le symbole comme **non exploitable** pour le run ;
- remonter ce statut dans l’audit et l’exclure du `selector`.

Pour du swing cash US large cap / mid cap, **3 séances** est un bon plafond pragmatique.

## P1 — fortement recommandé pour une version professionnelle

### P1.1 — Le schéma `stock_bars` doit être nettoyé

**Constat**
Dans `database/sql/stock/stock_bars.sql` :
- `trade_count` est un `DECIMAL(20,8)` alors que c’est un entier logique ;
- pas de champ `ingested_at` ;
- pas de champ de statut/source ;
- index minimaliste.

**Recommandation**
Après reset :
- `trade_count BIGINT UNSIGNED NOT NULL` ;
- ajouter `ingested_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP` ;
- conserver `UNIQUE(symbol, timeframe, timestamp)` ;
- ajouter un index couvrant `(timeframe, symbol, timestamp)` si tu gardes plusieurs timeframes ;
- si ton projet reste centré daily, garder le schéma simple mais propre.

---

### P1.2 — `cleaning_audit_log` n’est pas un vrai audit log

**Constat**
`database/sanitizer_db_ops.py::upsert_audit()` met à jour la dernière ligne du symbole au lieu d’ajouter un historique immuable.

**Problème**
Le nom “audit log” laisse penser à un historique complet, mais le comportement réel est plutôt un **snapshot mutable**.

**Recommandation**
Scinder en deux tables :

1. `cleaning_audit_latest`
   - une ligne par symbole, état courant ;
2. `cleaning_audit_runs`
   - append-only, une ligne par run symbole/date avec détails d’exécution.

C’est beaucoup plus professionnel pour diagnostiquer les dérives et les incidents data.

---

### P1.3 — Il faut ajouter des contrôles OHLCV métier avant insertion

**Constat**
`import_alpaca_bar.py` vérifie surtout la finitude et la plage numérique.

**Il manque encore**
- `open/high/low/close > 0`
- `high >= max(open, close, low)`
- `low <= min(open, close, high)`
- `volume >= 0`
- `trade_count >= 0`

**Impact**
Une ligne provider corrompue peut contaminer :
- ATR,
- volatilité,
- RSI,
- beta,
- sélection finale.

**Recommandation**
Ajouter une validation métier stricte à l’ingestion, avec compteur d’exclusions et logs structurés.

---

### P1.4 — Le sanitizeur calcule des features non persistées et non réutilisées ici

**Constat**
`data_sanitizer_daily.py` calcule :
- `parkinson_vol`
- `overnight_gap`
- `rvol20`

mais ces colonnes ne sont pas upsertées dans `stock_bars_daily`.

**Problème**
Coût CPU inutile, confusion fonctionnelle.

**Recommandation**
Choisir explicitement :
- soit on les **persiste** parce qu’elles servent à l’aval ;
- soit on **cesse de les calculer** ici et on laisse `modelFactory/features.py` les recalculer à la volée.

Vu le design actuel, je recommande de **ne pas les calculer dans le sanitizeur** si elles ne sont pas stockées.

---

### P1.5 — Le module est encore partiellement dupliqué / hétérogène

**Constat**
Des fonctions proches existent à plusieurs endroits :
- `dataIntegrityEngine/import_alpaca_bar.py`
- `database/bar_metadata.py`

Il y a aussi des `sys.path.append(...)` dans :
- `dataIntegrityEngine/import_alpaca_assets.py`
- `dataIntegrityEngine/update_sector.py`

**Problème**
Le module n’est pas encore totalement uniformisé comme package Python propre.

**Recommandation**
Centraliser :
- le client provider Alpaca ;
- les helpers barres ;
- les règles d’univers ;
- les points d’entrée CLI.

Et supprimer les hacks `sys.path.append(...)` au profit d’exécutions `python -m ...` uniquement.

---

### P1.6 — Observabilité insuffisante pour un pipeline de production

**Aujourd’hui**
On a des logs, mais pas encore un vrai résumé run-level robuste.

**À ajouter**
Pour chaque run data integrity :
- `run_id`
- date/heure début-fin
- nb symboles ciblés
- nb symboles réussis / échoués / skipped
- nb barres insérées
- nb symboles avec fills > seuil
- nb symboles exclus pour données dégradées

**Bénéfice**
Pilotage beaucoup plus simple depuis l’IHM ou les scripts d’exploitation.

## P2 — améliorations utiles mais non bloquantes

### P2.1 — Le module se dit multi-timeframe mais le comportement est surtout pensé pour le daily

**Constat**
- `TimeFrame` expose plusieurs granularités ;
- mais toute la logique métier aval est centrée sur `1D`.

**Recommandation**
Assumer explicitement que `dataIntegrityEngine` est d’abord un pipeline **daily equities**.
Cela simplifiera le code, la documentation et les tests.

---

### P2.2 — L’import initial peut être borné plus intelligemment

`clientAlpaca.py` utilise `DEFAULT_START_DATE = "2010-01-01T00:00:00Z"`.

Pour ton besoin réel, une base propre peut démarrer sur :
- **10 ans glissants** ;
- ou **11 ans** si tu veux du confort pour certains indicateurs / modèles.

Cela réduit le bruit et accélère les backfills initiaux.

---

### P2.3 — Mieux distinguer les symboles “sans données” des symboles “hors univers”

Aujourd’hui, `bars_available` est un booléen pratique mais un peu trop binaire.

À terme, un statut plus précis serait meilleur :
- `ready`
- `no_history`
- `provider_error`
- `suspended_or_stale`
- `excluded_by_policy`

Ce n’est pas indispensable tout de suite, mais c’est une évolution saine.

## 5. Recommandation d’architecture cible après reset

## Principe directeur

**Une seule série de prix, simple, robuste, traçable : split-adjusted.**

### Schéma logique cible

#### `stock_metadata`
- univers instrument
- statut Alpaca
- `bars_available`
- `sector`
- `market_cap`

#### `stock_bars`
- source brute normalisée Alpaca
- **daily split-adjusted uniquement**
- une ligne par `(symbol, timestamp)`
- champs d’audit minimaux : `ingested_at`

#### `stock_bars_daily`
- série daily nettoyée utilisée par le reste du projet
- une ligne par `(symbol, date)`
- colonnes clés :
  - `open, high, low, close, volume`
  - `adj_close = close`
  - `daily_return`
  - `is_filled`
  - `data_adjustment = 'split'`
  - `ingested_at`
  - idéalement `fill_streak` ou `quality_flag`

#### audit
- `cleaning_audit_latest`
- `cleaning_audit_runs`

#### downstream
- `stock_scores` doit intégrer un statut explicite de qualité sanitizeur

## 8. Jeux de tests à renforcer

### Cas à couvrir absolument

1. **timeout provider** ne doit pas désactiver `bars_available`
2. **empty provider réel** doit désactiver `bars_available` proprement
3. **split historique** : recalcul cohérent après reingestion
4. **dividend ex-date** : la série `split` conserve la réalité de marché attendue
5. **3+ jours manquants** : le symbole devient non éligible
6. **sanitizeur failed** : le symbole est exclu aval
7. **ligne OHLC incohérente** : rejet à l’ingestion
8. **re-run idempotent** : mêmes résultats, même audit latest, historique runs enrichi

## 9. Verdict final

Le module `dataIntegrityEngine` est une **bonne base**, mais il doit encore passer d’un mode “pipeline fonctionnel” à un mode **data platform de production**.

### Mon verdict expert

- **Choix de prix recommandé** : **`split`**, pas `all`
- **Niveau actuel** : correct / intermédiaire avancé
- **Niveau visé après refonte courte** : professionnel, robuste, exploitable en production swing cash

### Les 5 décisions les plus importantes

1. **Une seule série canonique en `split`**
2. **Aucun `bars_available=False` sur incident réseau**
3. **Sanitizeur avec recalcul glissant**, pas append strict naïf
4. **Échec sanitizeur = exclusion aval explicite**
5. **Forward-fill plafonné**

Si tu appliques ces 5 points en priorité, la qualité globale du projet montera nettement, sans complexifier inutilement l’architecture.
