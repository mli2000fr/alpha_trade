## 1. Résumé exécutif

Cette tranche enchaîne directement après `prompt/dataIntegrityEngine/5.evo_3.md`.

Le chantier précédent avait déjà :
- rendu `history_status` décisionnel dans certains consommateurs aval prioritaires ;
- enrichi les résumés run-level côté import Alpaca et sanitizeur ;
- introduit une staleness fondée sur les séances de marché.

Le problème restant était surtout **structurel** : la règle d’éligibilité de l’univers était encore dupliquée dans plusieurs modules, ce qui créait un risque de dérive entre :
- l’import data-integrity,
- le sanitizeur,
- les consommateurs corporate actions,
- les helpers legacy,
- le sélecteur / scanner,
- et l’IHM qui ne savait pas encore exploiter les résumés métier émis par stdout.

Cette tranche ferme ce gap en deux volets :

1. **centralisation réelle de la règle d’univers éligible** dans `database/assets.py` ;
2. **transport + affichage IHM** des résumés run-level structurés déjà émis par les pipelines.

Le résultat est cohérent de bout en bout :
- un même helper pilote désormais l’éligibilité SQL des symboles actifs/tradables/bar-eligible ;
- `history_status` est propagé au-delà des premiers consommateurs prioritaires ;
- l’IHM capte les payloads `::alpha_trade_run_summary::...`, les persiste avec les runs et les affiche en résumé métier.

## 2. Centralisation de la règle d’univers éligible

### Fichier pivot
- `database/assets.py`

### Nouveaux éléments introduits
- `ELIGIBLE_HISTORY_STATUSES = ("pending", "ready")`
- `build_eligible_stock_metadata_filters(stock_metadata)`
- `list_eligible_stock_symbols(limit=None, *, engine=None, stock_metadata=None)`

### Règle centralisée
Le helper partagé encode désormais la règle d’éligibilité suivante, quand les colonnes existent :
- `status == 'active'`
- `tradable is True`
- `bars_available is True`
- `asset_class == 'us_equity'`
- `history_status` autorisé si :
  - `NULL`
  - chaîne vide / blanche
  - `pending`
  - `ready`

Donc, quand `history_status` est présent, les statuts bloquants sortent automatiquement de l’univers :
- `no_history`
- `provider_error`
- `suspended_or_stale`
- `excluded_by_policy`

### Décision de conception
Le helper reste **schema-adaptive** :
- si certaines colonnes n’existent pas dans un schéma de test ou legacy, elles ne sont pas exigées ;
- cela conserve la compatibilité SQLite / schémas transitoires ;
- mais dès qu’une colonne existe, elle devient réellement décisionnelle.

### Bénéfice
On supprime la duplication de conditions SQL dispersées dans plusieurs modules. La politique d’univers exploitable devient :
- plus lisible,
- plus testable,
- plus homogène,
- et plus sûre vis-à-vis des futures évolutions de `history_status`.

### Effet
Même les helpers plus anciens / transverses ne portent plus une logique d’univers en parallèle.

## 4. Propagation secondaire de `history_status`

Le chantier précédent avait couvert en priorité :
- `database/selector_reference.py`
- `selector/alpha_scanner.py`

Cette tranche étend la propagation à des consommateurs secondaires ou transverses :
- `database/sanitizer_db_ops.py`
- `database/bar_metadata.py`
- `corporate_actions/db_io.py`
- `dataIntegrityEngine/import_alpaca_bar.py` (sélection amont réalignée)
- `database/assets.py` (fonctions de sélection des symboles à enrichir)

### Résultat concret
`history_status` n’est plus seulement un garde-fou local au scanner ; il participe désormais à plusieurs flux d’univers :
- import,
- sanitation,
- corporate actions,
- enrichissement fundamentals,
- helpers selector legacy.

Cela réduit fortement le risque d’avoir :
- un univers “valide” pour un module,
- mais “bloqué” pour un autre,
uniquement à cause d’une duplication de logique SQL.

## 5. Intégration IHM des résumés run-level

## 5.1 Capture du résumé dans `ihm/services/process_registry.py`

### Ajouts structurants
- constante `RUN_SUMMARY_PREFIX = "::alpha_trade_run_summary::"`
- champ `run_summary: dict[str, object]` dans `PipelineRunRecord`
- helper `_extract_run_summary(line)`
- adaptation de `_drain_events()`

### Fonctionnement
Quand un pipeline écrit une ligne stdout préfixée par :
- `::alpha_trade_run_summary::`

le registre :
1. parse le JSON ;
2. le stocke dans `managed.record.run_summary` ;
3. évite de repropager cette ligne brute dans les logs stdout combinés.

### Bénéfice
On transforme un simple message stdout en **signal structuré persisté** dans l’historique IHM, sans créer de nouvelle table technique dédiée.

---

## 5.2 Exposition du résumé dans `ihm/pages/pipeline.py`

### Ajouts principaux
- `RUN_SUMMARY_METRICS`
- `_get_run_summary(record)`
- `_build_run_summary_caption(record)`
- `_render_run_summary(record, compact=False)`

### Ce qui est affiché
#### Dans le centre d’exécution
Pour le run sélectionné, la page affiche maintenant :
- un bloc **Résumé métier** avec métriques compactes ;
- le breakdown `history_status_counts` si présent ;
- le breakdown `status_breakdown` si présent ;
- le payload brut dans un expander de debug.

#### Dans les cartes d’étape
Le dernier run de chaque étape affiche un résumé compact, utile pour lire rapidement :
- cibles,
- succès,
- skips,
- échecs,
- no-data,
- stale,
- rows upsert,
selon la nature du pipeline.

#### Dans l’historique centralisé
Une colonne supplémentaire :
- `résumé métier`

fournit un condensé lisible du payload run-level, directement dans le tableau historique.

### Bénéfice
L’IHM ne sert plus seulement à lancer / arrêter les jobs et lire les logs techniques ; elle expose maintenant une **lecture business du run**.

## 8. Décisions de conception retenues

### 8.1 Une seule source de vérité pour l’univers SQL
Le choix retenu est de faire de `database/assets.py` la source de vérité de l’éligibilité stock-level partagée.

Cela évite les divergences silencieuses entre modules qui recopiaient historiquement :
- `status`
- `tradable`
- `bars_available`
- `asset_class`
- puis maintenant `history_status`

### 8.2 `history_status` affine, sans casser les schémas incomplets
Comme dans la tranche précédente, la colonne reste optionnelle du point de vue du code :
- si elle existe, elle filtre réellement ;
- si elle n’existe pas, le comportement reste compatible.

### 8.3 Intégration IHM légère via stdout structuré
Plutôt que d’ajouter immédiatement une persistance métier dédiée, la solution retenue exploite :
- un préfixe stable,
- un JSON sérialisé,
- une capture dans le registre IHM.

Cette approche apporte une valeur immédiate avec un coût technique faible.

### 8.4 Priorité à l’observabilité opérateur
Le résumé run-level est maintenant exploitable à trois niveaux :
- logs machine / stdout structuré,
- persistance dans l’historique des runs IHM,
- affichage synthétique dans la page pipeline.

## 9. Limites connues / suites possibles

Cette tranche finalise proprement le lot demandé, mais plusieurs prolongements restent possibles :

- exposer ces résumés run-level dans d’autres pages IHM (overview / reporting transverse) ;
- agréger plusieurs `run_summary` de sous-runs workflow dans un résumé parent plus riche ;
- persister à terme les résumés métier dans une table dédiée si l’on veut du reporting historique avancé ;
- étendre la même logique de helper partagé à d’autres univers spécialisés si certains modules ont des contraintes métier supplémentaires ;
- nettoyer les artefacts `__pycache__` générés par les validations locales si l’on veut garder un working tree plus propre.
