# Screener — Audit expert phase 1

## Ce que j’ai modifié

### 1. Garde-fous métier dans `screener`
Fichier : `screener/models.py`

Ajout de deux paramètres structurants :
- `min_history_days=252`
- `min_close_price=5.0`

Effet :
- on élimine d’emblée les IPO récentes / historiques trop courts ;
- on évite les penny stocks, peu cohérents avec un process swing cash propre.

### 2. `total_score` rendu vraiment exploitable
Fichier : `screener/pipeline.py`

Avant :
- `total_score` mélangeait directement des composantes sur des échelles différentes ;
- la force relative brute pouvait dominer artificiellement le ranking.

Maintenant :
- `liquidity_val`, `relative_strength_index` et `historical_range_score` sont transformés en percentiles cross-sectionnels ;
- `total_score` devient une moyenne pondérée normalisée, bornée de facto sur `0-100`.

Effet :
- ranking plus stable ;
- comparaison inter-symboles plus saine ;
- meilleur comportement pour un univers large et hétérogène.

### 3. Univers screener plus propre et plus scalable
Fichier : `screener/db_io.py`

Amélioration de `iter_symbol_chunks()` :
- présélection de l’univers via `stock_metadata` :
  - `status='active'`
  - `tradable=1`
  - `bars_available=1`
  - `asset_class='us_equity'`
  - `history_status in ('pending', 'ready')` ou vide
- remplacement de la pagination `OFFSET` par une pagination keyset (`last_symbol`)

Effet :
- moins de travail inutile sur des symboles non tradables / exclus ;
- meilleure montée en charge ;
- cohérence plus forte avec l’univers réellement exploitable aval.

### 4. Documentation réalignée
Fichiers :
- `doc/screener.md`
- `doc/dataIntegrityEngine.md`
- `README.md`

Documentation ajoutée / corrigée sur :
- les nouveaux filtres métier ;
- la normalisation du score ;
- l’ordre de pipeline réel autour de `screener`, `sync_latest_quotes`, `sync_earnings_calendar`, `alpha_scanner`.

## Ce que j’ai constaté à la lecture experte

### Points forts existants
- `DataSanitizer` est globalement bien conçu :
  - reconstruction glissante,
  - garde-fou sur les `fill streaks`,
  - audit exploitable.
- Le `selector` est plus avancé que le `screener` :
  - filtres riches,
  - neutralisation sectorielle,
  - intégration quotes/earnings.

### Faiblesses initiales du `screener`
1. **Univers trop large**  
   Il scorait potentiellement des symboles qui n’auraient jamais dû entrer dans le pipe.

2. **Score total mal calibré**  
   Mélange de métriques non homogènes.

3. **Pas assez de garde-fous métier**  
   Historique insuffisant et prix trop bas pas exclus assez tôt.

4. **Scalabilité perfectible**  
   Avec jusqu’à 10 ans de daily par symbole, charger de gros chunks sans filtration amont coûte vite cher.

## Recommandations expertes pour la phase suivante

### P0 — Refactor perf du `screener` en 2 passes
Refonte idéale :
- **Pass 1** : charger seulement le nécessaire pour :
  - liquidité récente,
  - force relative 6m,
  - min price,
  - min history
- **Pass 2** : charger l’historique long uniquement pour les survivants

C’est probablement le plus gros gain perf à venir.

### P0 — Rendre le lookback “range” configurable métier
Pour du swing cash, un `historical_range_score` sur 10 ans est discutable.
À tester :
- 252j
- 504j
- 756j

En pratique, pour du swing, un range 52 semaines ou 2 ans est souvent plus utile qu’un range 10 ans.

### P1 — Ajouter un vrai `run_summary` structuré au `screener`
Comme pour `data_sanitizer_daily` :
- `targeted_symbols`
- `eligible_symbols`
- `filtered_history`
- `filtered_price`
- `filtered_liquidity`
- `scored_symbols`
- `duration_seconds`

Très utile pour ops + IHM + audit.

### P1 — Ajouter des index DB orientés pipeline
À envisager après reset des tables :
- `stock_metadata(status, tradable, bars_available, asset_class, history_status, symbol)`
- revue des index de `stock_scores` selon les écrans IHM et requêtes de ranking

### P1 — Backtester les seuils du `screener`
Vu l’usage swing cash, calibrer empiriquement :
- `min_close_price`
- `liquidity_threshold_usd`
- fenêtre de force relative
- fenêtre du range
- poids des composantes

## Avis cible

Pour un contexte :
- daily only,
- swing trade,
- cash majoritairement,
- reset complet des tables,

la bonne cible n’est pas un screener “générique quant”, mais un screener :
- plus **sélectif en univers**,
- plus **simple en features**,
- plus **stable cross-sectionnellement**,
- plus **rapide** avant le `selector`.

Le `selector` doit porter la sophistication.
Le `screener`, lui, doit surtout faire un **pré-tri robuste, rapide, propre**.
