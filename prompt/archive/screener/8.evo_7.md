## 1. Objectif

La phase 7 savait calculer des recommandations adaptées selon 4 objectifs métier :

- robuste ;
- offensif ;
- défensif bear-market ;
- meilleur compromis exécutable.

Mais ces résultats restaient surtout visibles via les artefacts CSV/JSON et la CLI.

La phase 8 vise donc à répondre à la question suivante :

> **Comment rendre ces recommandations visibles directement dans l’IHM opérateur, sans obliger à relire les fichiers à la main ?**

Le but n’était pas de recréer le moteur de diagnostic dans Streamlit.
Le bon choix était au contraire de **réutiliser les artefacts existants** et d’en faire une couche de lecture/présentation robuste.

## 3. Design retenu

## 3.1 Source de vérité conservée

La phase 8 ne recalcule rien.
Elle lit simplement les artefacts déjà produits par :

- `python -m backtesting diagnose-screener`
- `python -m backtesting recommend-screener`

Répertoire cible par défaut :

- `artifacts/screener_diagnostics/`

Fichiers lus côté IHM :

- `recommendation_summary_by_objective.json`
- `scenario_recommendations_by_objective.csv`
- `metadata.json`

Cette approche garde un contrat clair :

- la CLI/backtesting produit ;
- l’IHM consomme et présente.

---

## 3.2 Pourquoi un service IHM dédié

J’ai introduit `ihm/services/screener_recommendations.py` pour éviter de mettre de la logique de parsing directement dans les pages Streamlit.

Ce service centralise :

- la résolution du répertoire d’artefacts ;
- la lecture JSON/CSV ;
- les erreurs tolérantes (fichier absent, JSON invalide, CSV absent) ;
- la construction d’un tableau de leaders par objectif ;
- le fallback sur le CSV si le JSON résumé n’est pas présent.

Avantage :
les pages restent simples, et la logique devient testable indépendamment de Streamlit.

## 4. Ce qui est affiché dans l’IHM

## 4.1 Dashboard — `ihm/pages/overview.py`

Ajout d’un bloc compact **"🎯 Calibration screener"** avec :

- les leaders recommandés pour chaque objectif ;
- le périmètre d’analyse (`global`, `cross_regime`, `bear_regime`, etc.) ;
- la période couverte via `metadata.json` ;
- l’horodatage de mise à jour des artefacts.

L’idée ici est d’avoir une vision exécutive immédiate, directement visible sur la page d’accueil.

---

## 4.2 Page Screening — `ihm/pages/screening.py`

Ajout d’un bloc détaillé **"🎯 Recommandations screener par objectif"** avec :

- des cartes métriques reprenant les leaders ;
- un tableau `Leaders phase 7 par objectif` ;
- un tableau `Classement détaillé phase 7` issu du CSV complet ;
- un détail de chargement si certains artefacts sont manquants.

Cette page devient donc le point d’entrée naturel pour :

- consulter les scores stock actuels ;
- voir le contexte pipeline ;
- lire les recommandations opératoires du screener.

## 5. Comportement de fallback

La phase 8 a été pensée pour être robuste même si les artefacts sont incomplets.

### Cas gérés
- répertoire d’artefacts absent ;
- `recommendation_summary_by_objective.json` absent ;
- `metadata.json` absent ;
- CSV présent mais JSON absent.

### Règle appliquée
Si le JSON résumé manque, l’IHM tente quand même de reconstruire les leaders à partir de :

- `scenario_recommendations_by_objective.csv`

Cela évite qu’un défaut mineur d’export rende la vue complètement vide.

## 6. API introduite côté IHM

## Fonction principale
- `load_screener_recommendation_report(...)`

### Retour structuré
Le service retourne un dictionnaire contenant notamment :

- `summary`
- `metadata`
- `recommendations_df`
- `objective_rows_df`
- `leaderboard_df`
- `coverage_label`
- `updated_at_label`
- `available`
- `errors`

Cette structure a été choisie pour être immédiatement exploitable dans plusieurs pages, sans dupliquer les transformations.

## 9. Bénéfices obtenus

### 1. Les recommandations deviennent visibles sans passer par la CLI
Le dashboard expose maintenant immédiatement les leaders utiles.

### 2. L’IHM reste découplée du moteur de calcul
Aucune logique de recommandation n’est recopiée dans Streamlit.

### 3. L’intégration reste robuste
Même avec des artefacts partiels, l’interface garde un comportement propre.

### 4. L’usage métier est plus direct
On lit enfin, dans l’interface :

- quoi choisir pour un objectif robuste ;
- quoi choisir pour un objectif offensif ;
- quoi privilégier en bear ;
- quoi déployer pour un compromis exécutable.

---

## 10. Limites assumées

### 1. Vue en lecture seule
La phase 8 ne déclenche pas encore `diagnose-screener` ou `recommend-screener` depuis l’IHM.

### 2. Répertoire d’artefacts fixe par défaut
La lecture cible `artifacts/screener_diagnostics/` par convention.

### 3. Pas encore de drill-down par régime dans l’IHM
La phase 8 expose surtout la synthèse opérationnelle par objectif.
La navigation dédiée cross-régimes pourra venir ensuite si nécessaire.

---

## 11. Conclusion

La phase 8 complète logiquement la progression précédente :

- phase 5 : recommandation globale ;
- phase 6 : robustesse par régime ;
- phase 7 : recommandation adaptative par objectif ;
- phase 8 : **mise à disposition directe dans l’IHM / dashboard**.

Le résultat est volontairement simple mais utile :

- aucune rupture de CLI ;
- aucun recalcul du moteur ;
- une lecture immédiate dans Streamlit ;
- une meilleure passerelle entre analyse research et usage opérateur.

Autrement dit, la recommandation phase 7 n’est plus seulement un artefact :
elle devient maintenant une information visible et exploitable dans le cockpit de supervision.
