## 3. Diagnostic principal

### 3.1 Incohérence backlog / scoring / agrégation

Dans `event_sentiment/pipeline.py` :

1. la fenêtre d’agrégation est dérivée de `aggregation_start`, elle-même issue des checkpoints / symbol windows ;
2. le scoring charge ensuite les articles pending via `load_pending_articles(limit=sentiment_pending_limit)` ;
3. l’agrégation relit la base avec `load_feature_frames(start_date=aggregation_start.date(), end_date=end_utc.date() + 5 jours)`.

Problème : les **articles réellement scorés** dans le backlog ne sont pas forcément inclus dans cette fenêtre d’agrégation.

Cas typique :
- on relance un run récent avec `aggregation_start` proche d’aujourd’hui ;
- mais il reste des pending rows plus anciennes dans `news_raw` ;
- elles sont scorées ;
- puis l’agrégation relit seulement la fenêtre récente ;
- résultat : `news_sentiment` est alimentée, mais **pas les features journalières correspondantes**.

Impact métier :
- dérive entre tables canoniques (`news_sentiment`, `macro_event_audit`) et tables dérivées (`ticker_daily_sentiment_features`, `sector_daily_sentiment_features`) ;
- biais dans `final_score_sentiment` pour le ranking swing ;
- comportement non déterministe quand le backlog dépasse `sentiment_pending_limit`.

### 3.2 Schéma `macro_event_audit` trop faible

Le schéma SQL actuel utilise :

```sql
PRIMARY KEY (article_id, sector)
```

Alors que le moteur macro (`event_sentiment/macro_rules.py`) supporte explicitement le **multi-match** d’un article sur plusieurs `macro_event_type`.

Conséquence :
- deux événements macro différents pour le même article et le même secteur s’écrasent à l’upsert ;
- on perd de l’information métier ;
- l’agrégation sectorielle devient incomplète.

Le modèle métier et les commentaires du code suggèrent déjà la clé canonique attendue :

- `(article_id, sector, macro_event_type)`

### 3.3 `signal_aggregator` instable sur données partielles

Constats dans `event_sentiment/signal_aggregator.py` :

- la normalisation effective utilisée dans `merge()` est une min-max cross-sectionnelle ;
- un univers avec une seule valeur non nulle ou une série constante neutralise le signal ;
- un secteur manquant ou un score neutre peut être transformé en biais positif/négatif selon la distribution du jour ;
- `symbol`, `sector`, `final_score` et plusieurs colonnes peuvent arriver avec `NaN`, texte, ou duplicats sans normalisation stricte.

Impact :
- signal instable d’un jour à l’autre ;
- dépendance indésirable à la composition de l’univers candidat ;
- risque d’amplification / pénalisation artificielle sur des valeurs manquantes.

## 4. Décisions de Sprint 1

### A. Rendre l’agrégation cohérente avec les dates réellement scorées

Décision :
- l’agrégation doit se baser sur les **`effective_trade_date` des articles effectivement scorés dans le batch**, et non sur la seule fenêtre de reprise ingestion.

Conséquences techniques :
- calculer les `trade_dates` impactées après scoring ;
- relire les frames uniquement pour ces dates ;
- garder un batch déterministe quand le backlog est limité.

### B. Faire de `macro_event_audit` une table canonique multi-événements

Décision :
- passer la clé primaire à `(article_id, sector, macro_event_type)` ;
- conserver `trade_date` comme dimension analytique indexée, pas comme dimension d’unicité principale.

Justification :
- un article appartient à une date de trading unique ;
- le multi-match vient du type d’événement ;
- cela correspond au comportement du moteur métier.

### C. Stabiliser la fusion de `signal_aggregator`

Décision :
- utiliser une normalisation **signée, bornée et déterministe** pour les signaux déjà définis nativement sur `[-1, 1]` :
  - `sentiment_net_agg`
  - `sector_impact_agg`
- mapping cible : `[-1, 1] -> [0, 1]` avec `0.5` = neutre ;
- normaliser explicitement symboles / secteurs / scores quantitatifs ;
- neutraliser proprement les valeurs manquantes.

Pourquoi c’est plus professionnel pour votre cas d’usage :
- en swing trading, on veut un signal **interprétable**, stable, et pas dépendant du nombre de candidats du jour ;
- la valeur 0 doit rester **neutre**, pas devenir baissière ou haussière selon la distribution cross-sectionnelle.

## 5. Améliorations futures recommandées (hors Sprint 1)

1. **Bootstrap 10 ans**
   - `initial_backfill_days=365` est trop court pour un véritable historique 10 ans ;
   - prévoir un mode bootstrap dédié, batché par tranches calendaires.

2. **Backlog incrémental piloté par date**
   - idéalement, traiter le backlog par `effective_trade_date` et non seulement par volume d’articles.

3. **Agrégations rolling plus riches**
   - ajouter des features 3j / 5j / 20j côté ticker et secteur.

4. **Qualité macro**
   - enrichir `rule_hits` avec type de cue (`positive_cue`, `negative_cue`) et score brut avant clipping.

5. **Persisted lineage**
   - stocker un `run_id` / `batch_id` technique pour audit complet du pipeline.

## 6. Critères d’acceptation du Sprint 1

- chaque article scoré dans un batch alimente les features journalières de ses dates impactées ;
- `macro_event_audit` conserve plusieurs `macro_event_type` pour un même `(article_id, sector)` ;
- `signal_aggregator` reste déterministe, borné `[0,1]`, sans warnings sur données partielles ;
- les tests ciblés couvrent backlog, schéma macro et fusion sentiment.
