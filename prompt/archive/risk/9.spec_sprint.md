## 1. Objectif

La passe précédente a extrait la promotion `stop initial -> trailing` dans un watcher post-run dédié.

La limite restante était opérationnelle :

- le watcher existait bien en **one-shot** ;
- mais il fallait encore le relancer manuellement ou via une orchestration externe ad hoc ;
- il n’y avait pas de mode **service persistant** prêt à être branché sur un scheduler long-lived.

L’objectif de cette passe était donc de fournir un **scheduler/service persistant intégré** au watcher, sans casser le mode ponctuel déjà en place.

Le système permet maintenant deux usages complémentaires :

- **mode `once`** : un scan unique des stops initiaux en attente ;
- **mode `service`** : une boucle persistante qui relance périodiquement le watcher, gère les périodes idle, publie des heartbeats et s’arrête proprement en cas d’erreurs répétées ou sur demande.

## 2. Design retenu

## 2.1 Nouveau contrat de configuration du service

### `execution_engine/config.py`

Ajout d’un dataclass dédié :

- `ProtectionWatcherServiceConfig`

Paramètres introduits :

- `interval_seconds`
- `idle_interval_seconds`
- `heartbeat_interval_seconds`
- `max_iterations`
- `stop_when_idle`
- `max_consecutive_failures`

### Pourquoi un dataclass dédié

Le watcher avait déjà une configuration métier d’exécution via `ExecutionConfig`.

Le scheduler persistant porte une autre responsabilité :

- cadence de boucle ;
- backoff idle ;
- heartbeat opérationnel ;
- politique d’arrêt.

Le fait d’isoler cette configuration évite de mélanger :

- les paramètres de trading / broker,
- et les paramètres de service d’ordonnancement.

### Validations ajoutées

Le dataclass valide explicitement :

- `interval_seconds > 0`
- `idle_interval_seconds > 0`
- `heartbeat_interval_seconds > 0`
- `max_iterations >= 1` si renseigné
- `max_consecutive_failures >= 1`

---

## 2.2 Service persistant autour du watcher existant

### `execution_engine/protection_watcher.py`

Ajout d’un nouveau composant :

- `ProtectionWatcherService`

Ce service encapsule `ProtectionTransitionWatcher.run(...)` dans une boucle persistante.

### Responsabilités

À chaque itération, le service :

1. appelle le watcher existant ;
2. agrège les métriques des résumés retournés ;
3. distingue les cycles avec travail des cycles idle ;
4. publie des logs heartbeat ;
5. attend un délai différent selon qu’il y avait du travail ou non ;
6. s’arrête proprement selon la politique configurée.

### Métriques de service agrégées

Le résumé opérationnel renvoyé par le service contient notamment :

- `iterations`
- `cycles_with_work`
- `idle_cycles`
- `consecutive_failures`
- `max_consecutive_failures`
- `watched_items`
- `triggered_items`
- `transitioned_items`
- `pending_items`
- `terminal_items`
- `skipped_existing_trailing`
- `cancel_failed_items`
- `submit_failed_items`

### Statuts possibles

Le service termine avec l’un des statuts :

- `COMPLETED`
- `FAILED`
- `STOPPED`

---

## 2.3 Politique de boucle retenue

### Cadence dynamique

La boucle distingue deux cadences :

- `interval_seconds` quand le cycle a réellement traité des items ;
- `idle_interval_seconds` quand aucun item n’a été surveillé.

### Intérêt

Cela permet :

- une surveillance plus réactive quand il y a de l’activité ;
- un coût opérationnel plus faible quand le portefeuille est calme.

### Heartbeat

Le service publie un heartbeat périodique contenant :

- le nombre d’itérations ;
- le nombre de cycles actifs / idle ;
- le cumul des transitions ;
- le compteur d’échecs consécutifs ;
- les filtres `account` / `exec_run_id`.

### Arrêt piloté

Deux modes d’arrêt contrôlé ont été ajoutés :

- `--stop-when-idle` : utile pour du quasi-scheduler piloté ou des runs batch relançables ;
- `--max-iterations` : utile pour tests, dry-run d’exploitation, smoke tests et watchdogs bornés.

### Résilience

En cas d’exception dans une itération :

- le service loggue l’erreur ;
- incrémente `consecutive_failures` ;
- continue tant que le seuil `max_consecutive_failures` n’est pas atteint ;
- bascule en `FAILED` si le seuil est dépassé.

### Arrêt manuel

Un `KeyboardInterrupt` est intercepté proprement et converti en statut `STOPPED`.

- `--heartbeat-interval-seconds`
- `--max-iterations`

Le comportement par défaut reste :

Donc les usages déjà existants restent compatibles.

## 2.5 Runner conservé et désormais utilisable en mode service

### `run_execution_protection_watch.py`

Le runner existant est conservé.

Il pointe toujours vers `execution_engine.protection_watcher.main`, mais cette `main(...)` sait maintenant lancer :

- un run one-shot ;
- ou un service persistant.

### Exemples d’usage

#### Scan ponctuel

```powershell
python run_execution_protection_watch.py --exec-run-id exec_20260426_001
```

#### Service persistant borné pour exploitation

```powershell
python run_execution_protection_watch.py --mode service --account default --limit 100 --service-interval-seconds 30 --idle-interval-seconds 120 --heartbeat-interval-seconds 300
```

#### Service borné pour test local

```powershell
python run_execution_protection_watch.py --mode service --max-iterations 3 --stop-when-idle --log-level DEBUG
```

## 2.6 Observabilité conservée côté métier

Le watcher métier continue de persister, à chaque cycle utile, les résumés déjà en place :

- `step_key = execution_protection_watch`

Donc l’IHM d’exécution garde la même lecture métier :

- protections surveillées ;
- triggers atteints ;
- transitions effectuées ;
- annulations échouées ;
- pending / terminal.

Le service persistant ajoute par-dessus une **observabilité opérationnelle** via :

- logs de cycle ;
- heartbeat ;
- résumé final émis sur la sortie standard via `emit_run_summary(...)`.

## 5. Ce que cette passe couvre réellement

### Côté runtime
- le watcher peut maintenant tourner comme un **service persistant** ;
- il n’est plus limité à un simple déclenchement ponctuel ;
- il peut être branché tel quel derrière un scheduler ou supervisé comme process long-lived.

### Côté robustesse
- arrêt contrôlé sur idle ;
- arrêt contrôlé sur nombre d’itérations ;
- arrêt de sécurité après erreurs consécutives ;
- interruption manuelle propre.

### Côté exploitation
- heartbeat périodique ;
- résumé de service ;
- runner inchangé côté point d’entrée.

---

## 6. Étape naturelle d’intégration exploitation

Cette passe prépare directement deux modes de déploiement pratiques sur Windows :

1. **Task Scheduler**
   - lancer périodiquement le runner en `--mode once`
   - ou en `--mode service --max-iterations ...` selon le besoin

2. **service long-lived supervisé**
   - lancer le runner en `--mode service`
   - le faire superviser par NSSM, un service wrapper Windows, ou un orchestrateur maison

Le code ajouté couvre surtout le second cas :

- process vivant ;
- heartbeat ;
- gestion de l’idle ;
- reprise continue.

---

## 7. Limites restantes / prochaines étapes naturelles

1. **vrai wrapper service Windows / NSSM / SC**
   - la boucle persistante est prête ;
   - l’étape suivante serait de fournir un script d’installation ou une doc d’exploitation pour l’enregistrer comme service Windows.

2. **persistence opérationnelle du service lui-même**
   - aujourd’hui les résumés métier du watcher restent persistés run par run ;
   - le résumé du service est surtout émis en log / stdout ;
   - une étape suivante pourrait stocker aussi un `execution_protection_watch_service` dans `run_business_summaries`.

3. **coordination multi-instances**
   - la logique métier évite déjà les transitions dupliquées en relisant les enfants ouverts ;
   - une étape supplémentaire serait un mécanisme de lease/claim SQL si plusieurs services tournent en parallèle.

4. **rechargement externe de configuration**
   - actuellement la configuration service passe par la CLI ;
   - une prochaine étape pourrait la déplacer vers `config.yaml` ou une section dédiée par compte.

---

## 8. Verdict

Cette passe transforme le watcher post-run d’un simple outil relançable en **composant exploitable de manière persistante**.

On obtient maintenant une architecture plus mature :

- `execute_run` pose la protection initiale ;
- `ProtectionTransitionWatcher` porte la logique métier de promotion ;
- `ProtectionWatcherService` orchestre cette logique en boucle persistante, avec cadence, heartbeat et garde-fous d’exploitation.

Le watcher est donc désormais prêt à être branché soit :

- sur un scheduler,
- soit sur un vrai service supervisé.
