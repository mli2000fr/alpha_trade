# Sprint 7 — implémentation réalisée

Date : 2026-04-26

Référence : `prompt/execution/8.sprint_6.md`

---

## 1. Objectif du Sprint 7

Finaliser la bascule IHM / supervision vers le modèle canonique `execution` en retirant les mélanges implicites les plus ambigus entre :

- données scoppées **run** ;
- données scoppées **compte** ;
- fallback **legacy** (`execution_orders`, `execution_fills`, `portfolio_targets`) ;
- indicateurs secondaires du watcher intraday.

Le Sprint 7 livré a été cadré comme un incrément **sûr, concret et testable immédiatement** :

- rendre la page `execution` strictement lisible par **run** sur les blocs critiques ;
- supprimer les fallback silencieux sur les écrans critiques ;
- reléguer explicitement le contexte compte et le watcher en lecture secondaire ;
- aligner la documentation et le wording pipeline sur la chaîne canonique post-refonte.

Principe retenu :

- **le nominal opérateur doit être scoppé run** ;
- **le contexte compte reste visible, mais dans un bloc explicitement secondaire** ;
- **aucun écran critique ne doit mélanger sans le dire les tables canoniques et les tables legacy**.

## 2. Changements implémentés

## 2.1 Requêtes IHM : modes stricts pour éviter les fallback implicites

Fichier modifié : `ihm/services/queries.py`

### Changements introduits

Ajout de garde-fous explicites sur les requêtes `execution` :

- `get_execution_orders(..., allow_legacy_fallback=True)`
- `get_execution_fills(..., allow_legacy_fallback=True)`
- `get_execution_positions(..., allow_account_fallback=True)`
- `get_execution_position_lots(..., exec_run_id=None, allow_account_fallback=True)`
- `get_execution_reconciliation_results(..., allow_account_fallback=True)`

### Effet métier

La page `execution` peut désormais demander des données **strictement canoniques et strictement scoppées run**, sans :

- relecture silencieuse de `execution_orders` / `execution_fills` legacy ;
- fallback implicite vers des positions, lots ou réconciliations de tout le compte.

### Point important

Un scope run dédié a été ajouté pour les lots :

- lecture des lots touchés par un run via `open_exec_run_id = :eid OR close_exec_run_id = :eid`

Cela permet de distinguer proprement :

- ce qui a été **ouvert / fermé par le run sélectionné** ;
- le stock plus large des lots du compte.

## 2.2 Page `execution` : lecture nominale strictement scoppée run

Fichier modifié : `ihm/pages/execution.py`

### Changements principaux

La page `execution` a été recentrée sur le flux nominal **strictement lié au run sélectionné** pour les blocs critiques :

- requests / ordres broker ;
- fills ;
- positions projetées ;
- lots touchés par le run ;
- réconciliation persistée.

Les appels critiques utilisent désormais les modes stricts introduits en Sprint 7 :

- `get_execution_orders(selected, allow_legacy_fallback=False)`
- `get_execution_fills(selected, allow_legacy_fallback=False)`
- `get_execution_positions(..., exec_run_id=selected, allow_account_fallback=False)`
- `get_execution_position_lots(..., exec_run_id=selected, allow_account_fallback=False)`
- `get_execution_reconciliation_results(..., exec_run_id=selected, allow_account_fallback=False)`

### Effet

L’opérateur lit maintenant d’abord :

> `run sélectionné → état canonique du run → réconciliation du run`

et non plus un mélange implicite entre run courant et état global du compte.

## 2.3 Suppression du fallback direct vers `portfolio_targets` sur l’écran critique

Fichier modifié : `ihm/pages/execution.py`

### Nouveau comportement

Si `execution_targets_snapshot` est absent pour un run, la page n’affiche plus automatiquement `portfolio_targets` comme substitut visuel.

À la place, elle affiche un message explicite indiquant que :

- aucun snapshot figé n’a été trouvé pour ce run ;
- le fallback direct vers `portfolio_targets` n’est plus affiché ici ;
- cela évite de mélanger la source risque et le run d’exécution.

### Effet

On retire une ambiguïté importante :

- `portfolio_targets` = source amont du risk ;
- `execution_targets_snapshot` = cible réellement consommée par le run.

L’écran critique n’utilise donc plus un remplacement silencieux entre ces deux objets métier.

## 2.4 Séparation explicite entre scope run et contexte compte

Fichier modifié : `ihm/pages/execution.py`

### Nouvelle structure

La page distingue désormais :

#### Bloc nominal
- `📦 Positions et détentions du run`
- `🧮 Positions projetées — scope run`
- `🪵 Lots touchés par ce run`
- `🧭 Réconciliation actionnable`

#### Bloc secondaire
Dans un expander dédié :

- `📚 Contexte compte — hors scope strict du run`
- `📦 Positions broker — dernier snapshot compte`
- `🧮 Positions projetées — scope compte`
- `🪵 Lots reconstruits — scope compte`

### Effet

L’opérateur sait immédiatement :

- ce qui appartient au **run sélectionné** ;
- ce qui relève du **contexte plus large du compte**.

Le diagnostic reste riche, mais il n’est plus ambigu.

## 2.5 Watcher et trailing dynamique relégués encore plus explicitement en secondaire

Fichier modifié : `ihm/pages/execution.py`

### Évolution

Les métriques liées au trailing dynamique ne sont plus au cœur du bloc principal de risque.

Le bloc principal se concentre désormais sur :

- `Stops broker`
- `Stops soumis`
- `Cibles stale`
- `Échecs protections`

Les métriques plus intraday / watcher sont maintenues dans l’expander secondaire :

- `Éligibles trail dyn.`
- `Trailing activés`
- `Fallback trailing`
- `Checks trigger`
- `Trails soumis`
- `Annulations KO`

### Effet

Le watcher reste visible et utile, mais son vocabulaire ne pilote plus la lecture nominale de la page `execution`.

## 5. Limites assumées du Sprint 7

Ce Sprint 7 finalise surtout la **lisibilité canonique et la bascule IHM/documentation**, mais ne supprime pas encore tout le code legacy résiduel au niveau du moteur interne.

Restent notamment :

- certains chemins de compatibilité encore présents côté repository / watcher ;
- la présence de tables legacy encore référencées dans certains tests utilitaires et outils d’admin ;
- le fait que le watcher continue d’exister comme composant secondaire optionnel ;
- l’absence d’une campagne runtime `simulate` / `paper` réelle dans cette session, en dehors des suites de tests.

Autrement dit :

> Sprint 7 termine la bascule de lecture et de documentation vers le canonique, sans prétendre effacer en une seule passe toute la compatibilité interne restante.
