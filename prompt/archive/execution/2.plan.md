# Plan d’implémentation concret — refonte de `execution_engine`

Date : 2026-04-26

Source de référence : `prompt/execution/1.audit.md`

---

## 1. Objectif

Transformer `execution_engine` en un **OMS swing daily / overnight**, cohérent avec ton cadre réel :

- actions US,
- swing trading,
- principalement compte cash,
- **pas d’achat/vente piloté par l’application pendant le marché ouvert**,
- reset DB autorisé,
- aucune contrainte de rétrocompatibilité historique.

L’objectif n’est pas de patcher l’existant, mais de faire une **refonte propre, ordonnée et industrialisable**.

---

## 2. Principes directeurs

### 2.1 Invariants métier

1. **Toute mutation pilotée par l’application se fait hors séance**.
2. `account_id` devient **obligatoire** dans tout le flux critique.
3. Un rerun ne doit **jamais écraser silencieusement** un run précédent.
4. Le moteur privilégie la **sûreté**, le **cash disponible**, la **traçabilité** et le **déterminisme**.
5. La réconciliation est d’abord **analytique** ; l’action automatique n’est autorisée que si l’état est non ambigu.
6. Le watcher intraday n’est **plus dans le chemin nominal**.

### 2.2 Positionnement cible

Le module doit devenir :

> un **OMS swing daily overnight**, multi-comptes, traçable, fondé sur des snapshots immuables, des tentatives historisées, une synchronisation broker explicite et une réconciliation sûre.

Il ne doit plus se comporter comme un mini-EMS intraday.

## 3.2 Politique de protection cible

### V1 recommandée

Version robuste et simple :

- `initial_stop` broker-side simple,
- `take_profit` simple seulement si sa gestion est sûre,
- **pas de trailing dynamique intraday** dans le chemin nominal,
- rebasage quotidien des protections au prochain run hors séance.

### Décision recommandée

Pour la phase 1 de refonte :

- **retirer le trailing dynamique du design nominal** ;
- garder le watcher au mieux comme composant séparé, optionnel, non critique ;
- ne pas faire dépendre la sécurité du portefeuille d’un runtime intraday.

---

## 4. Stratégie globale d’implémentation

La refonte doit se faire dans cet ordre :

1. figer les invariants métier ;
2. poser le nouveau schéma ;
3. corriger les fondations repository / idempotence / lock ;
4. réécrire l’executor nominal overnight ;
5. reconstruire positions / fills / réconciliation ;
6. adapter l’IHM ;
7. supprimer le legacy intraday.

Je recommande une **bascule big-bang contrôlée**, pas une migration incrémentale complexe, puisque tu repars d’une base saine.

## Sprint 3 — réécriture du run nominal `ProductionExecutor`

### Objectif

Faire de `ProductionExecutor.execute_run()` un run **overnight déterministe**, sans dépendance au polling intraday long ni au watcher.

### Résultat attendu

Le run exécution :

- charge les targets du bon compte,
- snapshotte les cibles,
- construit les requests,
- soumet les ordres broker,
- journalise immédiatement les événements critiques,
- se termine proprement sans logique intraday centrale.

### Fichiers principalement impactés

- `execution_engine/executor.py`
- `execution_engine/broker_adapter.py`
- `execution_engine/audit.py`
- `execution_engine/config.py`
- `tests/test_execution_engine_executor.py`
- `tests/test_executor.py`

### Changements code

#### `execution_engine/executor.py`
Réécrire le flux nominal autour de :

1. acquisition du lock ;
2. préflight compte + fenêtre de soumission ;
3. lecture targets scoped ;
4. snapshot des targets ;
5. création `execution_order_requests` ;
6. soumission broker ;
7. enregistrement `execution_broker_orders` ;
8. persistance immédiate des événements critiques ;
9. release du lock ;
10. clôture de run.

### Logique à retirer du cœur nominal

- boucle de polling long comme mécanisme central ;
- dépendance au watcher pour finaliser la sécurité ;
- métriques centrées sur le fill immédiat pendant le run.

### Politique risk-first

Si une protection V1 doit être créée dans le run, l’ordre de priorité doit être :

1. protection,
2. puis sophistication éventuelle.

### Tests à écrire

- run nominal hors séance ;
- crash pendant soumission avec événement `RUN_FAILED` persisté ;
- lock correctement libéré ;
- rerun explicable ;
- impossible de lancer deux runs sur le même compte.

### Risques

- changement d’habitude côté exploitation ;
- nécessité de revoir les messages IHM/CLI sur la notion de “filled”.

### Critères d’acceptation

- le run se comporte comme un run overnight, pas intraday ;
- `RUN_STARTED`, `ORDER_SUBMITTED`, `RUN_FAILED`, `RUN_COMPLETED` sont persistés de façon fiable ;
- le watcher n’intervient plus dans le succès nominal.

## Sprint 5 — réconciliation analytique puis actionnable

### Objectif

Remplacer la réconciliation naïve par une réconciliation professionnelle, sûre et actionnable.

### Résultat attendu

Le moteur compare maintenant 5 axes :

- targets,
- requests / ordres ouverts,
- positions internes,
- positions broker,
- protections.

### Schéma / SQL

À créer :

- `execution_reconciliation_results`

### Fichiers principalement impactés

- `execution_engine/reconciliation.py`
- `execution_engine/db_io.py`
- `execution_engine/executor.py`
- tests de réconciliation

### Changements code

Introduire des statuts explicites de réconciliation :

- `SAFE_AUTO`
- `MANUAL_REVIEW`
- `BLOCKED`

Le rebalance automatique ne doit être autorisé que si :

- aucun ordre ambigu n’est en vol,
- la position est claire,
- les protections sont cohérentes,
- le cash est réellement disponible,
- l’écart est actionnable sans ambiguïté.

### Tests à écrire

- position hors cible mais ordre encore ouvert ;
- partial fill + protection manquante ;
- symbole non cible mais détenu ;
- cash insuffisant ;
- état ambigu => `MANUAL_REVIEW`.

### Risques

- tentation de trop automatiser ;
- fausses corrections si la logique n’est pas assez conservatrice.

### Critères d’acceptation

- plus aucun auto-rebalance sur état ambigu ;
- toute correction automatique est justifiable par les données.

## 9. Stratégie de bascule production

## 9.1 Type de bascule

### Recommandation

**Big-bang contrôlé**.

C’est le bon choix ici, car :

- tu acceptes le reset des tables ;
- la rétrocompatibilité n’est pas requise ;
- garder deux modèles execution en parallèle augmenterait inutilement la complexité.

## 9.2 Séquence de cutover

1. geler `execution` legacy et le watcher ;
2. sauvegarder si besoin les artefacts de diagnostic ;
3. reset des tables execution ;
4. déployer nouveau schéma ;
5. déployer repository + executor + IHM ;
6. exécuter la campagne `simulate` ;
7. exécuter la campagne `paper` ;
8. valider les données et les écrans ;
9. activer `live` sur un compte ;
10. étendre progressivement.

## 9.3 Condition de rollback

Le rollback ne doit pas être un mélange des deux modèles.

Si la bascule échoue :

- on corrige,
- on reset de nouveau le périmètre execution,
- puis on relance la campagne paper.

## 11. Résumé ultra-opérationnel

### Priorités absolues

1. **sortir l’intraday du chemin nominal** ;
2. **imposer `account_id` partout** ;
3. **corriger l’idempotence avec historique des tentatives** ;
4. **poser un vrai schéma request / broker / fill / position** ;
5. **refondre la réconciliation avant tout auto-rebalance sérieux**.

### Vision finale

À la fin de la refonte, un opérateur doit pouvoir expliquer un run avec cette chaîne simple :

> target lue → snapshot figé → request créée → tentative envoyée → ordre broker observé → fill observé → position reconstruite → réconciliation calculée → décision actionnable.

C’est cette chaîne qu’il faut viser, sprint après sprint.
