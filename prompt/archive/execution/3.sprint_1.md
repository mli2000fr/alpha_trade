# Sprint 1 — implémentation réalisée

Date : 2026-04-26

Référence : `prompt/execution/2.plan.md`

---

## 1. Objectif du Sprint 1

Poser les fondations minimales de la refonte `execution_engine` sans encore entrer dans la refonte complète request / broker / fills des sprints suivants.

Cibles du sprint :

- rendre explicite le profil métier overnight ;
- scoper le chargement des targets par `account_id` ;
- ajouter un verrou d’exécution par compte ;
- poser le snapshot SQL des targets consommées ;
- enrichir `execution_runs` avec les métadonnées de profil/fenêtre ;
- sécuriser la base de tests autour de ces changements.

---

## 2. Changements implémentés

## 2.1 Configuration métier overnight

Fichier modifié : `execution_engine/config.py`

Ajouts :

- `execution_profile` avec défaut `overnight_cash_swing`
- `submission_window` avec défaut `both`
- propriété `resolved_account_id`
- propriété `is_overnight_profile`
- validations associées

Effet :

- le profil overnight devient une primitive métier explicite du moteur ;
- la notion de fenêtre de soumission hors séance existe désormais dans la config.

---

## 2.2 Point d’entrée opérateur aligné Sprint 1

Fichier modifié : `run_execution.py`

Changements principaux :

- presets `simulate`, `paper`, `live` réorientés vers un profil nominal :
  - `account_type = cash`
  - `pdt_rule = off`
  - `swing_only = True`
  - `allow_outside_rth = True`
  - `execution_profile = overnight_cash_swing`
  - `submission_window = both`
- ajout de `--submission-window`
- defaults CLI alignés sur le profil overnight cash swing
- affichage opérateur enrichi avec :
  - profil d’exécution
  - fenêtre de soumission
  - compte résolu
- persistance des résumés avec `config.resolved_account_id`

Effet :

- le point d’entrée opérateur reflète mieux la cible métier overnight ;
- le run nominal n’est plus présenté comme un flux centré sur l’intraday.

---

## 2.3 Scope `account_id` sur les targets

Fichier modifié : `execution_engine/db_io.py`

Changements :

- `ExecutionRepository.load_portfolio_targets()` accepte désormais `account_id`
- toutes les lectures des targets sont filtrées par `account_id`
- le chargement du “dernier run” est désormais scoped par compte
- fallback explicite sur `default` si `account_id` absent

Effet :

- suppression du risque immédiat de fuite inter-comptes au moment du chargement des cibles.

---

## 2.4 Verrou d’exécution par compte

Fichier modifié : `execution_engine/db_io.py`

Ajouts :

- `acquire_execution_lock(...)`
- `release_execution_lock(...)`

Schéma support :

- nouvelle table `execution_locks`

Effet :

- un compte ne peut plus lancer proprement deux runs concurrentiels sur le même périmètre si le lock est déjà pris.

---

## 2.5 Snapshot des targets consommées

Fichier modifié : `execution_engine/db_io.py`

Ajout :

- `snapshot_execution_targets(...)`

Schéma support :

- nouvelle table `execution_targets_snapshot`

Effet :

- on garde une trace immuable des targets effectivement consommées par un `exec_run_id`.

---

## 2.6 `execution_runs` enrichi pour le profil overnight

Fichiers modifiés :

- `database/sql/execution/execution_runs.sql`
- `execution_engine/db_io.py`

Ajouts dans `execution_runs` :

- `execution_profile`
- `submission_window`
- `account_id` rendu non nul dans le DDL cible
- index `(account_id, trade_date)`

Effet :

- le run porte déjà ses métadonnées de positionnement Sprint 1.

---

## 2.7 Orchestrateur branché sur les nouvelles fondations

Fichier modifié : `execution_engine/executor.py`

Changements :

- résolution d’un `resolved_account_id`
- acquisition du lock au démarrage
- abandon propre si le lock est déjà pris via l’événement `RUN_LOCKED`
- lecture des targets via `account_id`
- insertion de `execution_profile` / `submission_window` dans `execution_runs`
- snapshot des targets après création du run
- libération du lock garantie dans le `finally`

Fichier modifié : `execution_engine/models.py`

- ajout de `EventType.RUN_LOCKED`

Effet :

- le run nominal s’appuie déjà sur les primitives Sprint 1 sans casser le comportement existant plus profond.

---

## 5. Limites assumées du Sprint 1

Ce sprint ne réalise pas encore :

- la refonte `execution_order_requests` / `execution_broker_orders` / `execution_broker_fills`
- la suppression du legacy `execution_orders` / `execution_fills`
- la reconstruction canonique des positions et des lots
- la nouvelle réconciliation analytique à 5 axes
- la bascule IHM complète
- le retrait définitif du watcher du paysage global

Autrement dit :

> Sprint 1 pose les fondations correctes, mais ne constitue pas encore la refonte complète du moteur.

---

## 6. Recommandation immédiate pour la suite

La meilleure suite logique est maintenant de passer au **Sprint 2**, avec cet ordre :

1. créer `execution_order_requests`
2. créer `execution_broker_orders`
3. créer `execution_broker_fills`
4. créer `broker_account_snapshots`
5. corriger l’idempotence en séparant :
   - clé métier stable
   - tentative de soumission
6. sortir progressivement `execution_orders` / `execution_fills` du chemin principal
