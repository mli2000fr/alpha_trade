## 2) Ce que ça veut dire

### Conclusion immédiate
Le résultat catastrophique précédent en `swing_only` venait bien **du bug d’exécution**, pas d’un problème de score.

Après correction :
- le mode standard reste bon
- le mode swing devient même **beaucoup meilleur**
- donc l’ancien `-64.8%` était clairement une conséquence de la mauvaise simulation

Autrement dit :

> l’hypothèse “le swing_only casse la stratégie” était fausse dans les anciens runs, parce que le moteur l’achetait à un prix incohérent.

## 3) Ce qui a changé structurellement

Avant :
- standard = chemin plus favorable
- swing = chemin punitif, entrée au `high`
- comparaison invalide

Maintenant :
- les deux runs utilisent la convention :
  - **signal en J**
  - **entrée à J+1 open**
- `swing_only` ne change plus le prix d’entrée
- il change seulement la sortie same-day

J’ai vérifié ça sur les nouveaux trades :

- **269 entrées communes**
- **100% des entrées communes ont exactement le même prix d’entrée**
- environ **74.3%** ont ensuite une date de sortie différente

👉 Donc maintenant, la différence entre standard et swing vient bien du **comportement de stratégie**, pas d’un fill incohérent.

---

## 4) Pourquoi le swing est maintenant meilleur

C’est le point le plus intéressant.

Le mode standard a :
- **384 day trades**
- beaucoup de sorties très rapides
- drawdown bien plus élevé

Le mode swing a :
- **0 day trade**
- **223 sorties same-day bloquées**
- durée moyenne plus longue
- win rate et profit factor nettement meilleurs

### Interprétation
Une fois l’entrée corrigée à un vrai `next_open`, bloquer les sorties le jour d’entrée :
- ne pénalise plus artificiellement le trade
- évite de couper trop tôt des mouvements qui continuent le lendemain
- laisse courir plus de gagnants

Exemples vus dans les trades :
- `DFDV`
- `GRPN`
- `TRON`
- `SPRB`

Sur plusieurs cas, le standard sort le jour même avec petit gain ou petite perte, alors que le swing sort plus tard avec gain beaucoup plus fort.

Donc maintenant, le message du backtest devient :

> la stratégie semble en fait mieux fonctionner en vrai swing qu’en rotation ultra-courte, au moins sur cette période et avec cette convention d’exécution.

## 7) Vérification du point sur le biais temporel

Tu m’as demandé de vérifier ceci :

> “Les scores sont reconstruits sur la date `trade_date`, puis exécutés sur cette même date.  
> Si ces scores sont calculés à partir de données de clôture du jour, il peut y avoir un biais temporel supplémentaire.”

### Réponse courte
#### Avant correction
Oui, c’était un vrai risque.

#### Après correction
**Ce n’est plus vrai dans le moteur d’exécution.**
Les scores datés `trade_date=J` sont désormais exécutés à **J+1 open**.

Donc l’énoncé :
> “reconstruits sur `trade_date`, puis exécutés sur cette même date”

est désormais **faux pour le backtest corrigé**.

---

## 8) Ce que j’ai vérifié dans le code sur ce point

### A. Le backtest exécute bien à J+1 open
Dans `backtesting/simulator.py` :
- les signaux sont planifiés via `_schedule_signals_for_execution(...)`
- cette logique fait explicitement :
  - signal en `trade_date = J`
  - exécution sur la **prochaine séance disponible**

Donc côté moteur :
- pas d’exécution le jour même
- pas de lookahead via le prix d’entrée

---

### B. Les snapshots de scores PIT utilisent bien les données jusqu’à J
Dans `backtesting/backfill_scores_history.py` :
- `build_snapshot_for_date(as_of_date)` construit un snapshot pour la date `J`

Dans `screener/db_io.py` :
- `load_prices_for_chunk(..., as_of_date=J)` fait :
  - `date <= as_of_date`

Dans `screener/pipeline.py` :
- `compute_scores_from_prices(..., as_of_date=J)` filtre :
  - `timestamp <= J`
- puis utilise :
  - le dernier `close`
  - le range historique
  - la force relative
  jusqu’à cette date

Dans `selector/alpha_scanner.py` :
- `_load_market_data(..., as_of_date=J)` charge aussi :
  - `date <= J`
- `compute_factors(...)` prend le **dernier close disponible**, donc celui de `J`

### Conclusion sur les scores quantitatifs
Oui :
- le snapshot `trade_date=J` utilise bien la barre journalière complète de `J`
- donc il incorpore bien le `close/high/low` de `J`

Mais comme le backtest entre maintenant à **J+1 open**, ce n’est **pas** un lookahead, **si** l’hypothèse métier est :

> “le score est calculé après la clôture de J, puis exécuté à l’ouverture de J+1”

Et cette hypothèse est cohérente avec la convention actuelle.

## 9) Vérification du sentiment
Côté sentiment, c’est plutôt conservateur.

Dans `event_sentiment/trading_calendar.py` :
- `regular_session_maps_to_same_day` vaut par défaut **`False`**
- donc une news pendant la séance régulière est mappée au **jour de trading suivant**
- le post-market aussi va au jour suivant
- seul le pré-market peut être pris sur le jour même

Donc le sentiment n’introduit pas, a priori, un biais agressif.
Au contraire, il est plutôt décalé prudemment.

---

## 10) Le vrai statut du “risque secondaire”

### Pour les scores quant / selector
Je dirais maintenant :

- **pas de biais temporel problématique détecté**
- **à condition d’assumer que le signal est calculé après clôture J**
- et exécuté à `J+1 open`

Donc sur cette partie, le risque est plutôt **maîtrisé** avec le correctif.

### Nuance importante
Le snapshot `trade_date=J` utilise les données de clôture de `J`.  
Donc si, métierment, tu voulais un signal “tradable pendant J” ou “avant la clôture de J”, alors oui il y aurait biais.

Mais pour une stratégie :
- calcul fin de journée
- exécution lendemain matin

c’est correct.

### Ce que je peux dire

- pour le **sentiment**, l’alignement est plutôt conservateur

Vu qu’il n’y a que **196 prédictions ML** pour **12500 lignes de scores**, ce n’est probablement pas le facteur principal ici, mais c’est la dernière zone à vérifier pour un backtest “research-grade”.

## 12) Conclusion finale

### Sur les nouveaux backtests
Le correctif a fonctionné.

- l’ancien effondrement du mode `swing_only` était un artefact de simulation
- après correction, `swing_only` devient même **meilleur** que le mode standard
- l’écart observé maintenant est un **vrai effet de stratégie**, pas un bug d’exécution

### Sur le biais temporel
Le point que tu voulais vérifier donne ceci :

- **avant** : risque réel, car l’exécution n’était pas propre
- **maintenant** : le backtest n’exécute plus les scores de `J` sur `J`
- les scores PIT de `J` utilisent bien la clôture de `J`
- donc il n’y a pas de lookahead **si** on interprète correctement le signal comme :
  - calculé **après close J**
  - tradé à **J+1 open**

### Verdict
- **problème principal résolu**
- **risque secondaire quantitatif acceptable dans la convention actuelle**
- **point restant à auditer surtout côté ML timestamps**, pas côté scores PIT quant classiques
