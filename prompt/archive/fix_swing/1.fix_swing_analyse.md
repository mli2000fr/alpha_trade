# Analyse complète — écart massif entre backtests `swing_only=True` et `swing_only=False`

## Checklist de l’investigation

- Lire les logs et localiser le point de divergence
- Vérifier si `swing_only` change les scores/signaux
- Auditer le moteur d’exécution et les contraintes
- Comparer des trades réels entre les deux runs
- Identifier la cause la plus probable et dire quoi faire pour un vrai compte cash de 2 000 $

J’ai lu le projet côté backtesting, comparé le code aux artefacts de tes deux runs, et la conclusion est assez nette.

## Verdict court

Le problème principal ne vient **ni des scores**, **ni de la sélection de candidats**.  
Il vient du **moteur d’exécution / de simulation**, avec en plus une stratégie qui semble **très dépendante des sorties intraday**.

En clair :

- `swing_only` ne change pas les signaux
- `swing_only` bascule vers un autre moteur de simulation
- ce moteur n’utilise pas les mêmes prix d’entrée/sortie que le mode standard
- donc le `+88%` sans `swing_only` est très probablement **sur-optimiste**
- et le `-64.8%` avec `swing_only` révèle que la stratégie est **peu robuste sans intraday**

---

## 1) Ce que j’ai vérifié dans le projet

### A. Les signaux sont identiques avant exécution

Dans les logs, avant simulation, les deux runs chargent exactement :

- même OHLCV
- mêmes scores
- mêmes prédictions ML
- mêmes signaux reconstruits

On le voit ici :

- `OHLCV chargé : 2860799 lignes, 12434 symboles`
- `Scores candidats chargés depuis stock_scores_history : 12500 lignes`
- `Prédictions ML chargées : 196 lignes`
- `Signaux reconstruits : 250 jours, 1250 entrées sélectionnées`

Donc avant le backtest, les deux runs partent du même matériau.

Et côté code, c’est cohérent :

- `backtesting/data_loader.py` charge les scores sans lien avec `swing_only`
- `backtesting/signal_replay.py` calcule `conviction`, `rank`, `selected` sans jamais regarder `swing_only`

👉 Donc ce n’est **pas** un problème de calcul de score ou de sélection de candidats pour expliquer cet écart-là.

---

## 2) Là où le projet diverge vraiment

Le point clé est ici :

- `backtesting/trading_constraints.py:48-49`
- `backtesting/simulator.py:190-192`

Quand `swing_only=True`, le code active `restrict_same_day_exit`, et ça force le moteur à passer par :

- `BacktestEngine._run_with_constraints(...)`

Quand `swing_only=False`, il passe par le chemin :

- `vectorbt.Portfolio.from_signals(...)`

👉 Donc tu n’as pas juste « la même stratégie avec une contrainte en plus ».

Tu as en réalité **deux moteurs d’exécution différents**.

Et c’est là que se cache l’écart majeur.

---

## 3) Le vrai bug / incohérence majeure : les prix d’entrée ne sont pas les mêmes

### Chemin standard (`swing_only=False`)

Dans `backtesting/simulator.py`, le mode standard fait :

```python
pf = vbt.Portfolio.from_signals(
    close=close,
    ...
    open=high,
    high=high,
    low=low,
    ...
)
```

Donc :

- il passe `close=close`
- il passe `open=high`, ce qui est déjà très suspect
- il n’utilise **pas** les vrais `open`, alors qu’ils sont bien chargés dans `pivot_ohlcv`

Et dans `backtesting/cli.py`, on voit bien que les `open` existent :

- `pivot_ohlcv(ohlcv_df)` retourne `open/high/low/close`
- mais `BacktestEngine.run(...)` ne reçoit que `close/high/low`

Donc les vrais `open` sont chargés puis ignorés.

### Chemin contraint (`swing_only=True`)

Dans `_run_with_constraints`, l’entrée est faite explicitement à :

```python
entry_price = float(high.at[trade_day, symbol])
```

👉 Donc en mode swing, tu achètes **au plus haut du jour**.

### Preuve concrète sur les artefacts

J’ai comparé les trades exportés des deux runs, pour des mêmes symboles aux mêmes dates d’entrée.

Exemples :

- `SPRB` — entrée `2025-12-01`
  - mode standard : entrée `83.11`
  - mode swing_only : entrée `104.4589`
- `TRON` — entrée `2025-07-24`
  - mode standard : entrée `8.74`
  - mode swing_only : entrée `9.95`
- `DFDV` — entrée `2025-06-13`
  - mode standard : entrée `25.73`
  - mode swing_only : entrée `31.51`

Ça, c’est décisif.

👉 Même signal, même date, même symbole, mais pas le même prix d’entrée.

Donc l’écart massif ne peut pas être attribué aux scores ou au ranking.

Il vient du simulateur.

## 5) Pourquoi le run sans `swing_only` paraît « trop beau »

Le run standard à `+88%` semble gonflé par la mécanique de simulation.

### Raisons techniques

#### a) utilisation de `open=high`

C’est anormal.

Le `open` transmis à `vectorbt` n’est pas le vrai `open`, mais le `high` du jour.

Ça peut fausser :

- les entrées
- les sorties de stop
- les fills intrabar

#### b) chemin vectorbt plus favorable que le stateful

Le moteur standard ne se comporte pas comme le moteur contraint.

Donc la comparaison n’est pas propre.

#### c) signaux probablement exploités trop tôt

Les scores sont reconstruits sur la date `trade_date`, puis exécutés sur cette même date.

Si ces scores sont calculés à partir de données de clôture du jour, il peut y avoir un biais temporel supplémentaire.

Je le mets en risque secondaire, moins prouvé ici que l’incohérence d’exécution, mais à surveiller.

---

## 6) Pourquoi le mode `swing_only` s’effondre

Là il y a deux effets cumulés.

### Effet 1 — la stratégie dépend énormément des sorties same-day

Le log `swing_only` montre :

- `blocked_same_day_exits = 219`
- `executed_day_trades = 0`

Donc 219 fois, une sortie aurait eu lieu le jour même, mais elle a été bloquée.

C’est énorme.

👉 Ça veut dire que la stratégie « gagne » une grosse partie de son edge grâce à des résolutions intraday :

- take profit touché dans la journée
- trailing stop touché dans la journée
- rotation rapide

Quand tu interdis ça, tu gardes les positions pendant la nuit, et elles se dégradent.

### Effet 2 — le moteur swing achète très souvent trop haut

Comme il entre au `high` du jour, tu payes souvent le pire prix possible.

Puis, comme tu ne peux pas sortir le jour même :

- tu absorbes le retour à la moyenne
- tu te fais sortir le lendemain / jours suivants au trailing stop
- sur des small/mid caps volatiles, c’est violent

Et c’est exactement ce qu’on voit dans les stats de trades du run swing :

- `306` trades
- `win rate 22.2%`
- `302` sorties sur `306` par trailing stop
- seulement `4` take profits

Ça ressemble moins à un problème de sélection qu’à une stratégie momentum courte + simulation punitive/incohérente.

## 8) Cause la plus probable, classée par importance

### 1. Problème d’exécution / simulation — très probable, principal

C’est la cause n°1.

#### Symptômes

- `swing_only` change de moteur
- moteur standard et moteur contraint n’utilisent pas les mêmes prix
- `open=high` dans le chemin vectorbt
- chemin contraint : entrée explicite au `high`
- artefacts réels : mêmes trades, prix d’entrée très différents

👉 C’est le cœur du problème.

### 2. Stratégie non robuste sans intraday — très probable

Le `blocked_same_day_exits=219` montre que la performance dépend énormément des sorties jour même.

Pour un compte cash/swing, c’est un énorme warning.

👉 Même avec un simulateur corrigé, il est possible que la stratégie reste médiocre en pur swing.

### 3. Risk management insuffisant — probable mais secondaire

Le backtest applique surtout :

- `max_positions`
- TP / trailing stop
- frais

Mais sur les noms vus (`DFDV`, `SBET`, `WOLF`, `SPRB`, `CELC`, etc.), on est clairement sur des actifs très nerveux.

Pour un compte de `2 000$` cash :

- `5` positions max, c’est probablement trop fragmenté
- l’univers semble trop spéculatif
- il manque probablement des filtres :
  - prix minimum
  - volume dollar minimum
  - ATR/volatilité max
  - exclusion des penny / microcaps
  - limite de concentration par secteur/type d’actif

👉 Ça aggrave le problème, mais ça n’explique pas à lui seul l’écart `+88%` vs `-65%`.

### 4. Problème de score / sélection — peu probable ici

Vu les logs + la lecture du code, je le mets loin derrière.

Les deux runs ont :

- mêmes scores chargés
- mêmes prédictions
- mêmes signaux reconstruits
- même nombre d’entrées sélectionnées

Donc non, le gros écart n’est pas « d’abord » là.

## 9) Pour un cas réel : 2 000$ en cash, pas d’intraday

Le vrai setup n’est pas « margin sans swing », ni même « margin avec swing ».

Le setup réaliste, c’est plutôt :

- `account_type = cash`
- `swing_only = True`
- idéalement entrée au prochain `open`
- pas de réutilisation immédiate du cash
- peu de positions simultanées

Et honnêtement :

avec le code actuel, je ne ferais confiance à aucun des deux résultats.

- le `+88%` est probablement trop optimiste
- le `-64.8%` est peut-être plus proche du réel dans l’esprit, mais il reste contaminé par une logique d’exécution incohérente

Donc avant de juger la stratégie, il faut corriger le backtest.

---

## 10) Ce qu’il faut corriger en priorité

### Priorité 1 — unifier la convention d’exécution

Le moteur standard et le moteur contraint doivent utiliser :

- la même règle d’entrée
- la même règle de sortie
- les vrais `open`

Concrètement :

- `backtesting/cli.py` doit passer aussi `pivoted["open"]`
- `BacktestEngine.run()` doit accepter `open`
- il faut arrêter `open=high`

### Priorité 2 — choisir une convention réaliste

Pour un backtest journalier PIT correct, le plus réaliste est souvent :

#### Option recommandée

- score calculé à la clôture du jour J
- entrée au `open` du jour J+1
- TP/SL évalués à partir de J+1 et suivants
- si `swing_only=True`, aucune sortie le jour d’entrée

Ça évite :

- le lookahead implicite
- les achats au `high` du même jour
- les comparaisons absurdes entre moteurs

### Priorité 3 — ajouter un test d’équivalence

Il manque un test du type :

> « à contraintes égales, les deux chemins donnent les mêmes prix d’entrée / même logique de fill »

Aujourd’hui, les tests existants valident le comportement actuel, mais pas sa cohérence.

### Priorité 4 — adapter la stratégie au cash 2k

Après correction du simulateur :

- `account_type="cash"`
- `swing_only=True`
- `max_positions=2` ou `3`, pas `5`
- filtrer les tickers trop volatils / trop bas prix
- revoir TP/TS si le modèle n’est pas intraday
- vérifier que les gagnants restent gagnants en `next_open` execution

---

## 11) Conclusion simple

### Conclusion finale

Si je devais répondre à la question en une phrase :

> L’écart catastrophique vient d’abord d’un problème de simulation/exécution, pas d’un problème de scores. Le mode `swing_only` utilise un autre moteur, avec des prix d’entrée beaucoup plus défavorables, tandis que le mode standard semble artificiellement optimiste. En plus, la stratégie dépend fortement de sorties intraday, donc elle n’est pas robuste telle quelle pour un vrai compte cash de 2 000$.
