## 2) Mais il reste une hypothèse de sortie trop favorable

Dans `backtesting/simulator.py`, la logique actuelle fait ceci pour une position ouverte :

- elle prend le `day_high`
- elle met à jour `peak_high` avec ce `day_high`
- elle calcule un `trailing_stop_price` à partir de ce nouveau plus haut
- puis elle vérifie si `day_low <= trailing_stop_price`
- et si oui, elle sort au `trailing_stop_price`

En pratique, ça veut dire qu’avec une simple bougie journalière, le moteur peut supposer sur **la même séance** :

1. le prix monte très haut,
2. ce nouveau plus haut remonte le trailing stop,
3. puis le prix redescend,
4. et on est exécuté à ce stop remonté.

Le problème :

### on ne connaît pas l’ordre intraday réel entre `high` et `low`
Avec des données daily OHLC :
- on connaît `open`, `high`, `low`, `close`
- mais on **ne connaît pas la séquence**
- donc on ne sait pas si :
  - le `high` est venu avant le `low`
  - ou l’inverse

Or le moteur actuel suppose très souvent le scénario le plus favorable.

---

# Le point exact dans le code

Dans `backtesting/simulator.py`, la logique critique est :

- `peak_high = max(position.peak_high, day_high)`
- `trailing_stop_price = peak_high * (1.0 - cfg.trailing_stop_pct)`
- `hit_trailing_stop = day_low <= trailing_stop_price`
- puis priorité au trailing stop :
  - `if hit_trailing_stop: exit_price = trailing_stop_price`
  - `else: exit_price = take_profit_price`

Donc la simulation autorise implicitement :

> “le jour a d’abord fait son plus haut, puis a touché le trailing stop calculé sur ce plus haut”

C’est **très optimiste** sur des small caps volatiles.

# 9) Ce que je ferais pour rendre la simulation crédible

## Correctif recommandé n°1
### Ne pas utiliser le `high` du jour courant pour remonter le trailing stop et déclencher ce même stop sur la même barre

Version plus prudente :
- calculer le trailing stop du jour avec le **peak précédent**
- tester le stop
- **puis seulement ensuite** mettre à jour `peak_high` avec le `day_high`

Ça évite le scénario :
- “le plus haut du jour est déjà connu avant la décision de sortie”

---

## Correctif recommandé n°2
### Si `take_profit` et `trailing_stop` sont tous les deux touchés sur la même barre, choisir une politique conservatrice

Par exemple :
- soit prendre le **pire prix plausible**
- soit interdire les doubles déclenchements favorables sur bougie daily
- soit définir explicitement une politique intrabar :
  - pessimiste
  - optimiste
  - neutre

Aujourd’hui, on est trop proche du cas optimiste.

---

## Correctif recommandé n°3
### Ajouter un mode “daily conservative”
Très utile pour comparer :

- `optimistic_daily`
- `conservative_daily`

Si le `+336%` retombe à quelque chose comme `+80%` ou `+120%`, tu sauras tout de suite que la différence vient du modèle d’exécution intrabar.
