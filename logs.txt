En usage IHM standard actuel, le step 7 fait en réalité :
candidats du jour pour l’import news
+ backlog pending plus large pour le scoring / backfill
Autrement dit, ce n’est pas un “candidats du jour seulement” de bout en bout.
 
Détail sous-étape par sous-étape
L’étape 7 lance une chaîne de 4 sous-commandes :
Import news + scoring FinBERT standard
Relevance backfill
History backfill
Scoring contextuel
1) Import news brut
Quand le champ Event Sentiment — symboles (CSV) est vide :
le backend résout les symboles via load_candidate_symbols()
donc l’import brut provider cible les candidats du jour (stock_scores.is_candidate = 1)
C’est la partie “candidats du jour”.
 
2) Scoring FinBERT standard sur le backlog pending
Là, c’est plus large.
Dans event_sentiment.pipeline.EventSentimentPipeline.run() :
si tu n’as pas fourni de symbols explicites,
alors le chargement des articles pending se fait avec :
pas de filtre symboles
filtre provider uniquement
et filtre dates seulement si tu as rempli start UTC / end UTC
Donc le scoring standard ne se limite pas automatiquement aux candidats importés juste avant.
Il peut scorer :
tous les articles pending du même provider
éventuellement bornés par la fenêtre de dates
même si ces articles concernent d’autres symboles que les candidats du jour
 
3) relevance_backfill
Même logique :
si tu n’as pas mis de CSV symboles,
la commande step 7 ne transmet ni --symbols ni --symbol-source candidates
donc le backfill de relevance_score travaille sur un scope plus large :
provider
dates si renseignées
pas limité aux candidats

4) history_backfill
Cette sous-étape reconstruit les features journalières à partir des dates scorées :
elle travaille par trade dates scorées
pas par “liste de candidats du jour”
Donc là aussi, ce n’est pas restreint aux seuls candidats du jour.

5) Scoring contextuel
Même comportement que le scoring standard :
si pas de CSV symboles explicite,
alors filtre :
provider
dates si renseignées
mais pas de filtre automatique “candidats”

Conclusion simple
Si tu lances le step 7 depuis l’IHM sans renseigner de symboles CSV :
Import brut news → candidats du jour seulement
Puis scoring/backfill/contextuel/features → backlog plus large, pas limité aux candidats
Donc la réponse la plus exacte est :
“candidats + backlog pending plus large”

Cas où ça devient “candidats du jour seulement”
Seulement si tu fournis explicitement une liste de symboles dans le champ CSV correspondant aux candidats voulus.
Sinon, en l’état actuel :
l’ingestion est candidate-only,
mais le traitement aval ne l’est pas automatiquement.

Oui, tu as raison
Si on raisonne sur la sous-étape calcul des features (ticker_daily_sentiment_features / sector_daily_sentiment_features), un mode strictement “candidats seulement” n’est pas très cohérent, surtout pour la partie secteur.
Pourquoi ?
1. Les candidats sont une sous-population très petite
Les candidates du jour :
sont peu nombreux,
sont filtrés par le screener,
sont déjà biaisés par la stratégie,
ne représentent pas l’ensemble du secteur.
Donc si tu calcules un score secteur uniquement à partir des candidats :
tu n’obtiens pas un sentiment sectoriel réel,
tu obtiens plutôt un sentiment du sous-ensemble déjà sélectionné.
Exemple :
secteur Tech avec 200 valeurs réellement actives dans les news,
mais seulement 4 candidats aujourd’hui,
alors le score secteur basé sur ces 4 titres devient très fragile et biaisé.

2. Un score secteur doit représenter le secteur, pas juste les candidats
Fonctionnellement, un feature secteur sert à capter :
le climat news du secteur,
le bruit macro sectoriel,
les événements qui touchent plusieurs titres,
la tonalité globale au-delà du seul screener.
Donc pour la partie sectorielle, il est plus cohérent d’avoir un univers plus large que les candidats.

Donc ton observation mène à une conclusion importante
Le vrai sujet n’est pas juste :
“step 7 doit-il être candidats-only ?”
Le vrai sujet est :
quel sous-scope doit être appliqué à chaque sous-étape du step 7 ?
Et là, tout le monde ne devrait probablement pas avoir le même scope.

Schéma plus juste métierment
Import news brut        -> candidats ou watchlist élargie
Scoring article/ticker  -> candidats / symboles utiles
Features ticker         -> candidats ou univers piloté
Features secteur        -> univers plus large, représentatif du secteur
Donc :
ticker-level peut raisonnablement être proche des candidats,
sector-level ne devrait probablement pas être limité aux seuls candidats.
Ce que ça veut dire sur le step 7 actuel
Le step 7 actuel est en fait hybride :
au début, il se comporte comme un run ciblé candidats ;
ensuite, pour le backlog / relevance / contextual / features, il repart sur un scope plus large.
Ce n’est pas absurde techniquement
Parce que pour les features secteur, un scope plus large est même plutôt logique.
Mais ce n’est pas propre sémantiquement
Parce que l’étape est présentée comme si elle suivait un seul périmètre métier.
En clair :
Le problème du step 7 actuel n’est pas forcément qu’il est “trop large”.
Le problème, c’est qu’il est mélangé sans explicitation.

La formulation la plus juste
Pour le ticker sentiment
Un scope candidats est défendable.
Pour le sector sentiment
Un scope candidats est insuffisant et potentiellement biaisé.
Donc un design plus cohérent serait :
ingestion/scoring ticker sur un scope ciblé,
features secteur sur un scope élargi et représentatif,
puis application finale aux candidats dans le step 8.

Résumé ultra court
Candidate-only pour les features secteur = peu cohérent
car les candidats ne représentent pas le secteur.

Donc :
- ticker feature -> peut être ciblé candidats
- sector feature -> doit plutôt rester sur un univers plus large

Le souci actuel du step 7 n’est pas seulement la largeur du scope,
c’est surtout l’absence de séparation claire entre :
1) scope de trading (candidats)
2) scope d’estimation du contexte secteur
Conclusion
Tu pointes exactement la bonne incohérence :
si on force tout le step 7 en candidate-only, on casse la logique des features secteur.
Donc la bonne cible métier n’est probablement pas “candidate-only partout”, mais plutôt :
“candidats pour le signal actionnable, univers plus large pour le contexte sectoriel.”
